# OpenAPI·JSON Schema·DBML 검증 CI 작업 로그

## 날짜

2026-09-14

## 문제 상황

Issue #69의 목표는 계약과 schema drift를 PR 단계에서 차단하는 것이다. 기존 CI는
R1 계약 검증과 DBML/Azimutt 생성물 diff를 일부 수행했지만, `docs/contracts/openapi`
전체와 일반 fixture/schema 쌍을 공통 규칙으로 검증하는 작은 단위 테스트가 없었다.

## 오류명 또는 실패 증상

- RED 테스트 실패 1: `FileNotFoundError: scripts/validate_contracts.py`
- RED 테스트 실패 2: `scripts/verify-contracts --root ... --contracts-only`가 깨진 fixture를
  실패시키지 못하고 exit code 0으로 끝났다.
- 리뷰 후 추가 RED: 같은 schema 이름이 여러 OpenAPI에 있을 때 fixture가 다른 문서의
  schema로 검증될 수 있었고, `/hanoks/monthly`처럼 고정 경로가 `/hanoks/{placeId}`와
  함께 매칭되면 ambiguous 실패가 발생했다.
- 잠재 실패 증상: OpenAPI 또는 fixture body가 schema와 어긋나도 R1 전용 검증 밖의
  계약 파일은 CI에서 놓칠 수 있었다.

## 기존 구조나 방식의 한계

`scripts/verify-contracts`는 `scripts/test/validate-r1-contract.py`를 실행한 뒤
`dbml2sql docs/database/schema.dbml --postgres`와 `scripts/azimutt-export.mjs` 생성물을
임시 디렉터리에 만들고, 커밋된 SQL 산출물과 `diff -u`로 비교했다. 이 구조는 DBML
compile과 generated artifact stale 상태를 잘 막지만, R1 이외의 OpenAPI·fixture가
늘어날 때 공통 fixture/schema 검증이 재사용되기 어려웠다.

## 관련 코드 맥락

- `scripts/validate_contracts.py`
  - 담당 로직: repository root를 입력받아 `docs/contracts/openapi`의 OpenAPI 문서를
    lint하고, `components.schemas`를 JSON Schema validator가 이해할 수 있는 `$defs`
    형태로 변환한 뒤 `docs/contracts/fixtures`의 `response.schema`와 `response.body`를
    대조한다.
  - 입력: `--root`로 받은 저장소 형태의 디렉터리.
  - 출력: 문제가 없으면 메시지를 출력하고 종료, OpenAPI/JSON Schema/fixture mismatch가
    있으면 `AssertionError`로 실패한다.
  - 핵심 분기: fixture의 `request.method`, `request.path`, `response.status`로 해당
    OpenAPI operation을 찾고, operation의 response `$ref`와 fixture의 `response.schema`가
    같은지 먼저 확인한다. 고정 path segment가 path parameter보다 우선되며, 같은
    specificity의 여러 path가 매칭될 때만 ambiguous로 실패한다.

- `scripts/verify-contracts`
  - 담당 로직: 계약 검증의 CI 단일 진입점이다.
  - 입력: 기본은 실제 repository root이며, 테스트에서는 `--root <임시 repo>`와
    `--contracts-only`를 받아 DBML/Azimutt 단계 없이 계약 검증만 실행한다.
  - 추가 입력: `--artifacts-only --generated-output-dir <dir>`는 테스트에서 이미 생성된
    SQL 산출물 디렉터리를 커밋된 `docs/database/azimutt/*.sql`과 비교해 stale 상태를
    실제 `diff -u` 경로로 검증한다.
  - 핵심 분기: `--contracts-only=true`면 `validate_contracts.py`만 실행하고 종료한다.
    실제 CI에서는 이후 R1 전용 검증, DBML compile, Azimutt/Postgres SQL diff까지 이어간다.

- `scripts/test/test_contract_validation.py`
  - 담당 로직: 임시 계약 트리를 만들어 positive/negative fixture와 stale generated
    artifact 실패를 TDD로 고정한다.
  - 핵심 케이스: 유효 OpenAPI+fixture 통과, schema와 맞지 않는 fixture body 실패,
    generated artifact mismatch 실패, `verify-contracts --contracts-only` negative mode 실패.

## 검토한 선택지

1. R1 전용 `validate-r1-contract.py`에 모든 검증을 더 넣기
   - 장점: 기존 파일 재사용.
   - 단점: Journey, VisitReview 등 새 계약이 R1 규칙에 묶인다.

2. `scripts/verify-contracts`에 Python 코드를 inline으로 넣기
   - 장점: 파일 수가 적다.
   - 단점: 테스트와 재사용이 어려워지고 실패 메시지가 거칠어진다.

3. 공통 검증기 `scripts/validate_contracts.py`를 추가하고 bash 진입점에서 호출하기
   - 장점: OpenAPI/fixture 공통 규칙을 독립 테스트할 수 있고, 기존 DBML/generated diff
     흐름을 유지한다.
   - 단점: 새 Python 파일과 pytest dependency가 추가된다.

## 판단 기준

- Issue #69 acceptance criteria인 “유효 계약 통과와 깨진 fixture 실패”, “생성물 stale
  상태 실패”를 로컬과 CI에서 모두 재현할 수 있어야 한다.
- R1 전용 규칙과 repository-wide 계약 검증 책임을 분리해야 한다.
- 기존 DBML compile과 generated artifact diff 흐름을 깨지 않아야 한다.

## 최종 결정

공통 검증기 `scripts/validate_contracts.py`를 추가하고, `scripts/verify-contracts`가
이를 먼저 호출하도록 했다.

## 해결 방식

- `scripts/validate_contracts.py`를 추가해 OpenAPI lint, JSON Schema check, fixture
  `response.schema`/`response.body` 검증을 수행하게 했다.
- `scripts/verify-contracts`에 `--root`, `--contracts-only` 옵션을 추가했다. 테스트는
  임시 repository tree로 negative fixture를 만들고, 실제 CI는 기존처럼 DBML compile과
  generated SQL diff까지 수행한다.
- `scripts/test/test_contract_validation.py`를 RED 먼저 작성했다. 처음에는
  `FileNotFoundError`와 negative fixture 미검출로 실패했고, 이후 리뷰 지적에 따라
  schema collision, OpenAPI response mismatch, static path 우선순위, generated artifact
  diff 경로 테스트까지 추가해 7개 테스트가 통과했다.
- `.github/workflows/ci.yml`에 `python3 -m pytest scripts/test/test_contract_validation.py`
  단계를 추가해 PR에서 검증기 자체의 positive/negative 동작을 확인한다.
- `scripts/test/requirements-r1-contract.txt`에 `pytest==8.4.2`를 추가했다.

## 결과

- Issue #69 범위의 OpenAPI lint, JSON fixture/schema 검증, DBML compile, generated
  artifact diff가 `scripts/verify-contracts`와 CI에 연결됐다.
- 로컬 검증:
  - `python3 -m pytest scripts/test/test_contract_validation.py` 7 passed
  - `bash scripts/verify-contracts` 통과
  - `node --test scripts/test/*.test.mjs` 통과
  - `node scripts/verify-planning-inputs.mjs && node scripts/validate-odii-fixtures.mjs` 통과
  - `./gradlew test --no-daemon` 통과
  - `cd ai && uv run pytest` 통과
  - `git diff --check` 통과
- 남은 과제: PR 생성 후 GitHub Actions CI 통과와 review를 확인하고, merge 시 #69를 닫는다.
