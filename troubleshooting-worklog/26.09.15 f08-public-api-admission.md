# F08 public api admission

날짜: 2026-09-15

## 문제 상황

Issue #136은 로그인·작성·신고·여정 command 남용을 공통 admission 계층에서 제한하고, 비신뢰 proxy header 위조를 막으며 429 응답 계약을 통일하라고 요구했다.

## 오류명 또는 실패 증상

TDD RED에서 `AdmissionService`, `AdmissionPolicy`, `InMemoryAdmissionStore`, `TrustedProxyProperties` 등 admission 타입이 없어 컴파일 실패했다. 구현 중 Java record component `allowed`와 같은 이름의 static factory `allowed()`가 accessor와 충돌해 `invalid accessor method in record AdmissionDecision` 컴파일 오류가 났고, `allow()`로 고쳤다. Spring web test에서는 test config bean 이름이 production bean 이름과 겹쳐 `BeanDefinitionOverrideException`이 발생해 test bean을 `@Primary`와 별도 이름으로 분리했다.

## 기존 구조나 방식의 한계

공통 오류 envelope와 CSRF/ownership web boundary는 있었지만, public command admission은 없었다. 또한 `docs/database/modules/operations.dbml`에는 `operations_admission`이 있었으나 실제 V004 Flyway migration에는 빠져 있어 DB concurrency 검증을 직접 걸 수 없었다.

## 관련 코드 맥락

- `modules/operations/src/main/java/com/yrootlab/onmaru/operations/admission/AdmissionService.java`
  - `AdmissionRequest(operation, subject)`와 `AdmissionPolicy(window, budgets)`를 받아 현재 clock 기준 window를 계산한다.
  - `AdmissionStore.tryConsume(...)`에 scope, windowStart, limit, retryAfter를 넘겨 atomic consume을 위임한다.
- `InMemoryAdmissionStore`
  - synchronized map으로 같은 scope/window의 consumed counter를 원자적으로 증가시킨다.
  - limit 이상이면 consume하지 않고 `AdmissionDecision.rejected(retryAfter)`를 반환한다.
- `apps/spring-api/src/main/java/com/yrootlab/onmaru/web/admission/AdmissionFilter.java`
  - `/api/admission/login` POST를 `login.start` operation으로 매핑한다.
  - 거절 시 `RATE_LIMITED` envelope, `Retry-After`, `details.retryAfterMs`를 반환한다.
- `ClientIdentityResolver`
  - `X-Forwarded-For`는 `TrustedProxyProperties`에 등록된 remote address에서 온 요청일 때만 신뢰한다.
  - 비신뢰 remote의 forwarded header는 무시하고 `request.getRemoteAddr()`를 subject key로 사용한다.
- `V004__d07_sync_operations_schema.sql`
  - `operations_admission(scope_key, window_start, consumed, active_count)` 테이블과 non-negative check를 추가했다.

## 검토한 선택지

1. Spring filter 안에 counter map과 proxy 판단을 모두 둔다.
2. operations module에 admission application policy/store를 두고 Spring은 web adapter만 맡는다.
3. PostgreSQL repository adapter까지 이번 PR에서 완성한다.

## 판단 기준

admission은 로그인, 후기, 신고, 여정 command가 공유할 정책이므로 Spring web filter에 묶으면 재사용과 테스트가 어려워진다. 반면 repository adapter는 아직 persistence 모듈 구조가 없으므로, 이번에는 application port와 DB schema/concurrency contract를 먼저 고정하는 편이 안전했다.

## 최종 결정

`modules:operations`를 추가해 admission application 경계를 만들고, Spring web adapter는 trusted proxy client identity와 429 envelope만 담당하게 했다.

## 해결 방식

- `modules:operations`를 Gradle에 추가하고 CI에 `Operations module tests`를 넣었다.
- fake clock 기반 테스트로 같은 operation/member scope에서 동시 요청 20개 중 limit 5개만 승인되는지 검증했다.
- Spring MockMvc 테스트로 비신뢰 `X-Forwarded-For` 위조가 무시되고 같은 remote address budget으로 429가 나는지 검증했다.
- trusted proxy remote address에서는 forwarded chain의 첫 client IP를 사용해 서로 다른 client budget으로 처리되게 했다.
- `ApiErrorCode.RATE_LIMITED`를 추가해 공통 error envelope를 사용했다.
- DB migration과 Testcontainers concurrency matrix에 `operations_admission` consumed CAS를 추가했다.
