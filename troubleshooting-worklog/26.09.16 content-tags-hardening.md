# Content Tags 고도화 작업 기록

## 날짜

2026-09-16

## 문제 상황

Issue #208의 첫 구현은 관광지·한옥·Odii 응답에 `contentTags`를 붙이는 데 성공했지만, 구조적으로는 MVP에 가까웠다.
FE가 바로 사용할 `string[]` 계약은 생겼지만, 운영·동기화·품질관리 관점에서는 “요청 시점 계산”에 머물러 있었다.

이번 추가 요청은 “좀 더 고도화해야 한다. 전부 추가해 달라”였다.
여기서 말하는 고도화는 단순히 태그 몇 개를 더 잘 뽑는 일이 아니라, 다음 요구를 포함한다.

- 추출 결과의 점수와 출처를 내부적으로 추적할 수 있어야 한다.
- Odii처럼 revision sync 경로가 있는 데이터는 publish 전 단계에서 태그를 생성해야 한다.
- API 응답 시점마다 다시 계산하는 구조를 줄이고, 저장된 projection을 우선해야 한다.
- DB에 revision별 태그 저장 공간이 있어야 한다.
- 운영자가 태그를 숨기거나 고정할 수 있는 override 구조가 있어야 한다.
- FE 공개 계약은 단순한 `contentTags: string[]`를 유지해야 한다.

## 오류명 또는 실패 증상

작업 중 확인된 구체적인 실패는 세 가지였다.

1. `cannot find symbol: extractRanked`
   - `ContentTagExtractorTests`가 점수/출처/version이 있는 내부 tag model을 요구했지만 extractor는 `List<String>`만 반환했다.

2. `cannot find symbol: OdiiStoryVersion.contentTags()`
   - Odii sync 결과인 `OdiiStoryVersion`이 생성된 태그를 보관하지 못했다.
   - 따라서 publish-time 저장 우선 구조로 갈 수 없었다.

3. 잘못된 한국어 정규화
   - `한옥마을`이 `한옥마`로 잘렸다.
   - 원인은 `을`을 항상 조사로 보고 제거한 규칙이었다.
   - `마을`은 명사 어미인데도 마지막 글자 `을`이 조사처럼 제거된 것이다.

## 기존 구조나 방식의 한계

기존 MVP는 다음 흐름이었다.

```text
API query service
  -> projection 텍스트 수집
  -> ContentTagExtractor.extract(...)
  -> List<String>
  -> 공개 응답 contentTags
```

이 방식은 빠르게 FE 계약을 만들기에는 좋았다.
하지만 다음 한계가 있었다.

- 같은 API 응답을 만들 때마다 계산한다.
- 태그가 왜 선택됐는지 점수·source를 추적할 수 없다.
- revision publish 단위 검증이 어렵다.
- 운영자가 특정 태그를 숨기거나 고정할 저장 구조가 없다.
- Odii sync pipeline이 이미 있는데도 태그가 story version에 포함되지 않았다.
- DB schema가 없어서 검색/필터/운영자 검수로 확장하기 어렵다.

특히 `contentTags`는 FE에서는 단순한 chip이지만, BE 입장에서는 “콘텐츠 요약 projection”이다.
따라서 시간이 지나면 검색, 추천, 필터, 품질검수, 운영자 수정과 연결될 가능성이 높다.
초기부터 revision과 algorithm version을 고려하지 않으면 나중에 태그 품질을 바꿀 때 “왜 바뀌었는지”를 설명하기 어렵다.

## 관련 코드 맥락

### `ContentTagExtractor`

경로:

```text
modules/catalog/src/main/java/com/yrootlab/onmaru/catalog/application/tags/ContentTagExtractor.java
```

역할:

- 장소명, 카테고리, 설명문, 하이라이트, Odii 대본 같은 텍스트를 입력받는다.
- 한국어/영문/숫자 token으로 정규화한다.
- 1gram과 2gram 후보를 만든다.
- 빈도, 위치, 하이라이트 출처, 도메인 phrase boost로 점수화한다.
- 최대 7개 태그를 반환한다.

이번 변경:

- 기존 `extract(...) -> List<String>`는 공개 API용으로 유지했다.
- 새 `extractRanked(...) -> List<ContentTag>`를 추가했다.
- `ContentTag`는 `label`, `score`, `position`, `source`, `algorithmVersion`을 가진다.
- `ContentTagSourceType`은 `TITLE`, `CATEGORY`, `BODY`, `HIGHLIGHT`, `DICTIONARY`를 표현한다.

이렇게 분리한 이유:

- FE 공개 응답은 계속 단순 배열이어야 한다.
- 내부 저장/운영/검증은 점수와 출처가 필요하다.
- public contract와 internal projection을 분리해야 나중에 운영자 UI를 붙일 수 있다.

### `OdiiSourceMapper`

경로:

```text
modules/audio/src/main/java/com/yrootlab/onmaru/audio/sync/OdiiSourceMapper.java
```

역할:

- 외부 Odii source item을 내부 `OdiiMappedStory`로 변환한다.
- spot/story identity, title, script, audio URL, image URL, duration, coordinate, content hash를 만든다.

이번 변경:

- `ContentTagExtractor`를 주입 가능하게 했다.
- source title, story title, script로 `contentTags`를 계산한다.
- 계산된 태그를 `OdiiStoryVersion`에 저장한다.

중요한 점:

- 이 경로는 API 요청 시점이 아니라 sync mapping 단계다.
- 즉 Odii는 publish 전에 태그가 story version에 실린다.
- API query service는 저장된 태그를 우선 사용한다.

### `OdiiStoryVersion`

경로:

```text
modules/audio/src/main/java/com/yrootlab/onmaru/audio/sync/OdiiStoryVersion.java
```

역할:

- 특정 revision의 Odii story content를 표현한다.
- title, script, audioUrl, imageUrl, duration, status, contentHash 등을 가진다.

이번 변경:

- `List<String> contentTags`를 추가했다.
- record compact constructor에서 null을 빈 배열로 방어하고 copy한다.

왜 필요한가:

- story version이 content tag를 가져야 revision publish 단위로 태그가 고정된다.
- tombstone/deleted story를 만들 때도 기존 태그를 유지하거나 비공개 처리 흐름에 실을 수 있다.

### `ActiveRevisionOdiiStoryQueryStore`

경로:

```text
modules/audio/src/main/java/com/yrootlab/onmaru/audio/query/ActiveRevisionOdiiStoryQueryStore.java
```

역할:

- active published audio revision에서 public query projection을 만든다.
- `OdiiStoryVersion` + `OdiiSpotVersion`을 `OdiiStoryProjection`으로 변환한다.

이번 변경:

- `story.contentTags()`를 `OdiiStoryProjection`으로 전달한다.

왜 필요한가:

- sync 단계에서 생성된 태그가 공개 query service까지 이어져야 한다.
- 그렇지 않으면 여전히 응답 시점 계산만 하게 된다.

### `OdiiStoryQueryService`

경로:

```text
modules/audio/src/main/java/com/yrootlab/onmaru/audio/query/OdiiStoryQueryService.java
```

역할:

- list/detail API 응답 DTO를 만든다.
- 언어 fallback, cursor, saved state, linked place, public URL policy를 처리한다.

이번 변경:

- `OdiiStoryProjection.contentTags()`가 비어 있지 않으면 그 값을 그대로 사용한다.
- 비어 있으면 기존 runtime extraction fallback을 사용한다.

이 fallback이 필요한 이유:

- 기존 테스트 fixture와 in-memory projection은 아직 저장 태그가 없을 수 있다.
- catalog와 audio 모두 실제 DB-backed projection adapter가 완성되기 전까지 호환성이 필요하다.

### `PlaceProjection`과 `PlaceDetailQueryService`

경로:

```text
modules/catalog/src/main/java/com/yrootlab/onmaru/catalog/application/query/detail/PlaceProjection.java
modules/catalog/src/main/java/com/yrootlab/onmaru/catalog/application/query/detail/PlaceDetailQueryService.java
```

역할:

- `PlaceProjection`은 공개 가능한 장소 상세 read projection이다.
- `PlaceDetailQueryService`는 canonical place detail과 hanok detail 응답을 만든다.

이번 변경:

- `PlaceProjection`에 `contentTags` 저장 슬롯을 추가했다.
- `PlaceDetailQueryService`는 projection에 저장된 태그가 있으면 우선 사용한다.
- 저장 태그가 없으면 기존처럼 name/category/description/highlights에서 fallback 계산한다.

왜 fallback인가:

- catalog 쪽은 아직 Odii처럼 완성된 DB-backed revision query adapter가 없다.
- 따라서 publish-time 저장 구조를 완전히 연결하기보다, projection이 저장 태그를 받을 수 있는 계약을 먼저 열어 두는 것이 안전하다.

## DB schema 맥락

새 migration:

```text
apps/spring-api/src/main/resources/db/migration/baseline/V009__content_tag_projection_schema.sql
```

추가한 enum:

- `content_tag_source`: `GENERATED`, `PINNED`, `OPERATOR`
- `content_tag_override_target`: `PLACE`, `ODII_STORY`
- `content_tag_override_action`: `PIN`, `HIDE`

추가한 table:

- `catalog_place_content_tag_versions`
- `audio_story_content_tag_versions`
- `content_tag_overrides`

`catalog_place_content_tag_versions`는 `(revision_id, place_id, position)`을 PK로 한다.
`catalog_place_versions`에 composite FK를 걸어, 존재하는 장소 version에만 태그가 붙도록 했다.

`audio_story_content_tag_versions`는 `(revision_id, story_id, position)`을 PK로 한다.
`audio_story_versions`에 composite FK를 걸어, 존재하는 story version에만 태그가 붙도록 했다.

`content_tag_overrides`는 polymorphic target이다.
`PLACE`와 `ODII_STORY`를 모두 다뤄야 하므로 단일 FK로 표현하지 않고 application 검증 대상으로 둔다.

## 검토한 선택지

### 선택지 1: 계속 응답 시점 계산만 유지

가장 단순하다.
하지만 revision publish 검증, 운영자 override, 검색/필터 확장에 약하다.
사용자 요청의 “전부 고도화”와 맞지 않는다.

### 선택지 2: 공개 API에 score/source까지 노출

운영 디버깅에는 편하다.
하지만 FE 계약이 불필요하게 복잡해진다.
FE는 chip을 그리면 되고, 점수·source는 내부 운영 정보다.

### 선택지 3: 내부는 구조화하고 공개 API는 `string[]` 유지

이번에 선택한 방향이다.
운영/저장 확장성을 얻으면서 FE 계약은 안정적으로 유지한다.

### 선택지 4: 형태소 분석기를 바로 도입

품질은 좋아질 수 있다.
하지만 Java dependency, 사전 배포, CI lockfile, 한국어 tokenizer 운영 부담이 늘어난다.
현재 repository는 문서/계약과 Spring module scaffold 중심이라, 먼저 lightweight deterministic extractor를 고도화하는 편이 안전하다.

### 선택지 5: 운영자 override API까지 한 번에 추가

DB table은 추가할 수 있지만, API와 권한 경계까지 만들면 범위가 커진다.
이번 변경에서는 schema를 준비하고, 실제 운영 API는 별도 후속으로 두는 것이 낫다.

## 판단 기준

- FE 공개 계약은 안정적으로 유지해야 한다.
- revision publish 흐름으로 옮길 수 있어야 한다.
- Odii처럼 이미 sync path가 있는 곳은 실제로 publish-time에 가깝게 생성해야 한다.
- catalog는 아직 DB-backed query adapter가 없으므로 저장 슬롯과 fallback을 병행해야 한다.
- 운영자 override는 schema부터 준비하되, 권한/관리 API는 후속으로 분리한다.
- LLM은 사용하지 않는다.

## 최종 결정

내부는 구조화하고, 공개 API는 `contentTags: string[]`를 유지한다.
Odii는 sync mapping 단계에서 태그를 생성해 story version에 저장하고, 장소/한옥은 projection 저장 태그 우선 + runtime fallback으로 운영한다.
DB에는 revision별 generated tag table과 override table을 추가한다.

## 해결 방식

1. `ContentTag`와 `ContentTagSourceType`을 추가했다.
2. `ContentTagExtractor.extractRanked(...)`를 추가해 label, score, position, source, algorithm version을 반환하게 했다.
3. 기존 `extract(...)`는 public API용 `List<String>` 반환으로 유지했다.
4. `한옥마을`이 `한옥마`로 잘리는 문제를 고쳤다.
   - `마을`, `서울`, `전통마을` 같은 보호 명사 어미는 조사 제거 대상에서 제외했다.
5. `OdiiSourceMapper`가 story title, source title, script에서 태그를 생성하게 했다.
6. `OdiiStoryVersion`에 `contentTags`를 추가했다.
7. `ActiveRevisionOdiiStoryQueryStore`가 저장된 story tag를 query projection으로 전달하게 했다.
8. `OdiiStoryQueryService`는 저장된 태그를 우선하고, 없으면 runtime fallback을 사용한다.
9. `PlaceProjection`에 저장 태그 슬롯을 추가했다.
10. `PlaceDetailQueryService`는 projection 태그 우선, 없으면 fallback 계산을 사용한다.
11. V009 migration으로 content tag 저장/override schema를 추가했다.
12. DBML과 Azimutt artifacts를 재생성했다.
13. FE 문서에 업데이트 시점, DB 저장 테이블, 공개 API와 내부 정보의 분리를 보강했다.

## 결과

이번 변경으로 `contentTags`는 더 이상 단순 응답 장식이 아니다.
Odii는 sync/revision 경로에서 태그가 생성되어 story version과 함께 이동한다.
장소/한옥은 저장된 projection tag를 받을 수 있는 구조가 생겼고, 기존 데이터에는 fallback 계산이 유지된다.
DB는 revision별 generated tag와 운영자 override를 저장할 준비가 됐다.

## 남은 과제

- 실제 catalog DB-backed publish adapter가 생기면 `catalog_place_content_tag_versions`에 태그를 저장하도록 연결해야 한다.
- `content_tag_overrides`를 DB에서 읽어 pipeline override 입력으로 넘기는 adapter가 필요하다.
- 운영자 override API는 인증/권한/감사 로그 설계와 함께 별도 Issue로 구현하는 것이 맞다.
- 태그 기반 검색/필터 API는 FE UX와 함께 별도 계약으로 확장해야 한다.
- 한국어 형태소 분석기 도입은 품질 평가셋을 만든 뒤 결정하는 것이 안전하다.

## 2차 고도화: 자동 품질 중심 pipeline

사용자 피드백에서 중요한 방향 전환이 있었다.

처음에는 `PIN`/`HIDE` override를 운영 기능처럼 설명했지만, 사용자는 “나중에 내가 따로 관리 다 해야 하느냐, 너무 수동적인 것 아니냐”는 우려를 제기했다.
이 우려는 타당하다.
콘텐츠 수가 늘어나면 운영자가 관광지와 오디오마다 태그를 직접 고치는 방식은 유지되지 않는다.

따라서 2차 고도화에서는 override를 핵심 기능이 아니라 예외 안전장치로 재정의했다.
기본 flow는 자동 추출과 자동 품질 필터링이며, override는 금칙어, 명백한 오탐, 캠페인성 대표 태그 같은 일부 사례에만 적용한다.

새 설계 문서:

```text
docs/superpowers/specs/2026-09-16-content-tags-pipeline-hardening-design.md
```

새 구현 계획:

```text
docs/superpowers/plans/2026-09-16-content-tags-pipeline-hardening.md
```

추가된 핵심 코드:

```text
modules/catalog/src/main/java/com/yrootlab/onmaru/catalog/application/tags/ContentTagPipeline.java
modules/catalog/src/main/java/com/yrootlab/onmaru/catalog/application/tags/ContentTagPipelineResult.java
modules/catalog/src/main/java/com/yrootlab/onmaru/catalog/application/tags/ContentTagQualityReport.java
modules/catalog/src/main/java/com/yrootlab/onmaru/catalog/application/tags/ContentTagOverride.java
modules/catalog/src/main/java/com/yrootlab/onmaru/catalog/application/tags/ContentTagOverrideAction.java
```

`ContentTagPipeline`은 이제 tag 생성의 표준 진입점이다.
기존에는 query service나 sync mapper가 `ContentTagExtractor`를 직접 호출했다.
이 방식은 빠르지만 source hash, 자동 품질 필터, override 적용 순서, 품질 리포트가 흩어질 위험이 있었다.

새 pipeline 흐름은 다음과 같다.

```text
ContentTagSource
  -> sourceHash 계산
  -> ContentTagExtractor.extractRanked(...)
  -> 자동 generic/filler tag 제거
  -> HIDE override 제거
  -> PIN override 앞쪽 배치
  -> 최대 7개 제한
  -> ContentTagPipelineResult
```

`ContentTagPipelineResult`는 공개 label과 내부 metadata를 분리한다.
FE API에는 계속 `publicLabels()`만 내려가며, `sourceHash`, `algorithmVersion`, `qualityReport`는 내부 저장/검증/운영 관측성을 위한 값이다.

`ContentTagQualityReport`는 다음 정보를 가진다.

- 생성된 후보 수
- 최종 태그 수
- 자동 제거된 generic tag 수
- HIDE override 적용 수
- PIN override 적용 수
- 빈 결과 여부
- 낮은 신뢰도 여부
- 경고 코드 목록

이 리포트는 FE에 노출하지 않는다.
나중에 sync run summary나 운영 dashboard에 붙이면 “태그가 0개인 콘텐츠”, “일반어가 많이 제거된 콘텐츠”, “override가 적용된 콘텐츠”를 관측할 수 있다.

구현 중 발견한 오류:

```text
java.lang.NullPointerException
at java.base/java.util.List.of(List.java:937)
at ContentTagPipeline.sourceHash(ContentTagPipeline.java:194)
```

원인은 `sourceHash`에서 nullable field를 `List.of(null)`로 감싼 것이었다.
설계상 null은 빈 문자열로 정규화되어야 하므로 `nullToBlank(...)`를 적용해 해결했다.

2차 고도화 검증:

```text
./gradlew :modules:catalog:test --tests '*ContentTagPipelineTests' --no-daemon
./gradlew :modules:catalog:test :modules:audio:test --no-daemon
./gradlew :apps:spring-api:test --tests '*PlaceDetailWebBoundaryTests' --tests '*OdiiStoryWebBoundaryTests' --tests '*SavedOdiiResourceWebBoundaryTests' --no-daemon
node --test scripts/test/migration-policy.test.mjs
bash scripts/verify-contracts

```

모두 통과했다. `bash scripts/verify-contracts`에서는 로컬 Python SSL 빌드가 LibreSSL이라는 warning이 출력됐지만, contract와 fixture 검증은 정상 완료됐다.

## 3차 고도화: Odii sync 품질 요약 연결

2차 고도화에서 `ContentTagQualityReport`를 만들었지만, 처음에는 pipeline result 내부에만 머물렀다.
즉 테스트로는 품질 정보를 볼 수 있었지만, 실제 Odii sync 결과에서는 “이번 revision의 태그 품질이 어땠는지”를 확인하기 어려웠다.

그래서 다음 단계를 추가했다.

새 코드:

```text
modules/audio/src/main/java/com/yrootlab/onmaru/audio/sync/OdiiContentTagQualitySummary.java
```

변경된 흐름:

```text
OdiiSourceStory
  -> OdiiSourceMapper
  -> ContentTagPipelineResult
  -> OdiiStoryVersion.contentTags
  -> OdiiStoryVersion.contentTagQualityReport
  -> OdiiRevisionSyncService
  -> OdiiSyncResult.contentTagQuality
```

`OdiiContentTagQualitySummary`는 story별 report를 다음 항목으로 집계한다.

- 전체 story 수
- 태그가 빈 story 수
- low confidence story 수
- 자동 제거된 generic tag 수
- HIDE override 적용 수
- PIN override 적용 수

이 값은 공개 API로 내려가지 않는다.
sync/publish 관측성에 쓰기 위한 내부 결과다.
예를 들어 특정 Odii revision에서 `emptyStoryCount`가 급증하면 원본 대본이 비었거나 provider 응답 shape가 바뀌었을 수 있다.
`removedGenericCount`가 급증하면 대본이 지나치게 일반적인 안내 문구만 포함됐거나 stopword/domain phrase 설정을 재검토해야 한다.

호환성을 위해 `OdiiStoryVersion`에는 기존 생성자 signature를 유지하는 보조 생성자를 두었다.
기존 test fixture와 tombstone 생성 경로는 그대로 동작하고, mapper로 들어오는 새 story만 실제 pipeline report를 가진다.

검증:

```text
./gradlew :modules:audio:test --tests '*OdiiRevisionSyncServiceTests.summarizesContentTagQualityForPublishedRevision' --no-daemon
./gradlew :modules:catalog:test :modules:audio:test --no-daemon
```

두 명령 모두 통과했다.

## 4차 고도화: lexicon resource 분리와 품질 threshold 명문화

추가 검토 결과, 여전히 튜닝 데이터가 코드 상수에 남아 있었다.
`ContentTagExtractor`의 stopword/domain phrase와 `ContentTagPipeline`의 generic label이 Java 코드에 박혀 있으면, 태그 품질을 조정할 때마다 코드 diff를 만들어야 한다.

따라서 다음 resource 파일로 분리했다.

```text
modules/catalog/src/main/resources/content-tags/stopwords.txt
modules/catalog/src/main/resources/content-tags/generic-phrases.txt
modules/catalog/src/main/resources/content-tags/domain-phrases.txt
modules/catalog/src/main/resources/content-tags/generic-labels.txt
```

새 코드:

```text
modules/catalog/src/main/java/com/yrootlab/onmaru/catalog/application/tags/ContentTagLexicon.java
modules/catalog/src/main/java/com/yrootlab/onmaru/catalog/application/tags/ContentTagQualityPolicy.java
```

`ContentTagLexicon`은 resource 파일을 UTF-8로 읽는다.
빈 줄과 `#` 주석은 무시한다.
resource가 없거나 비어 있으면 fallback set을 사용하므로 테스트나 packaging 문제에서도 기본 동작이 무너지지 않는다.

`ContentTagQualityPolicy`는 품질 경고 기준을 명시한다.

- `finalCount == 0`: `EMPTY_RESULT`
- `finalCount < 3`: `LOW_CONFIDENCE`
- `removedGenericCount >= 5`: `GENERIC_HEAVY`

이번 보완으로 `추천` 같은 일반어는 generic label resource에서 제거 대상이 되고, `전통 정원` 같은 도메인 phrase는 domain phrase resource에서 boost 대상이 된다.
운영적으로는 “태그 품질을 개선하려면 어느 Java 조건문을 바꿔야 하는가”가 아니라 “어떤 lexicon 파일을 검토해야 하는가”로 문제가 단순해진다.

검증:

```text
./gradlew :modules:catalog:test --tests '*ContentTagExtractorTests.loadsDomainPhrasesFromResourceLexicon' --tests '*ContentTagPipelineTests.loadsGenericLabelsFromResourceLexicon' --no-daemon
./gradlew :modules:catalog:test --tests '*ContentTagPipelineTests.reportsGenericHeavyWhenAutomaticFilterRemovesManyGenericCandidates' --no-daemon
./gradlew :modules:catalog:test :modules:audio:test --no-daemon
```

모두 통과했다.
