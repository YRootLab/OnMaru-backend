# Odii–canonical place 검수 연결 구현

## 문제

Odii spot과 canonical place의 이름이나 거리가 비슷하다는 이유만으로 연결을 공개하면 동명 장소, 좌표 결측, 삭제된 장소가 잘못 노출될 수 있다. 기존 DB migration은 `audio_place_odii_links`와 `verified_at`을 제공하지만, 후보와 검수 상태를 다루는 application 경계 및 현재 공개 canonical projection을 다시 확인하는 조회 경계는 없었다.

Issue #104는 후보를 검수 전 상태로 유지하고 명시 승인된 링크 하나만 canonical place card로 제공해야 한다. 병렬 Issue #103이 audio query를 구현하므로 기존 `audio.sync` 모델, R2 OpenAPI, migration, build 파일은 수정하지 않는 조건도 함께 적용했다.

## 진행

1. #96의 revision/tombstone 구현, #99의 `PlaceDetailQueryService`, R2 `linkedPlaceId` 계약, `audio_place_odii_links` migration을 확인했다.
2. 같은 이름의 여러 후보와 `NAME_ONLY` 후보가 모두 PENDING이며 공개 projection이 비어 있는 domain test를 먼저 작성했다. 새 production type 부재로 compile RED를 확인했다.
3. 명시 승인 시 다른 후보를 REJECTED로 전환하고, 한 spot에 승인 projection 하나만 남기는 `AudioPlaceLinkService`와 in-memory store를 구현했다.
4. 승인 시점과 승인 link 공개 조회 시점 모두 `CanonicalPlaceLinkLookup`을 사용하도록 해 hidden/deleted/ambiguous canonical place가 노출되지 않게 했다.
5. catalog adapter test를 먼저 작성해 RED를 확인한 뒤, #99의 public detail query를 audio-owned `CanonicalPlaceLinkCard`로 변환하는 `CatalogPlaceLinkLookup`을 추가했다.

## 결과

- 후보는 `PENDING`, `APPROVED`, `REJECTED` 상태를 가진다.
- `NAME_ONLY`, `NAME_DISTANCE_ONLY`, `MANUAL_REFERENCE`는 모두 명시 승인 전에는 공개되지 않는다.
- 한 후보 승인 시 같은 spot의 다른 후보는 거절되어 동명 후보가 동시에 노출되지 않는다.
- 승인 대상이 공개 canonical place가 아니면 승인이 거부되고, 승인 후 place가 삭제되거나 숨겨져도 projection에서 즉시 제외된다.
- #103은 `ApprovedAudioPlaceLinkQuery.findApprovedPlace(...)`만 소비하면 검수 정책이나 catalog 내부 타입에 결합되지 않는다.
