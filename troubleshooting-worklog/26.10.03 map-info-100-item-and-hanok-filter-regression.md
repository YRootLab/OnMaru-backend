# 지도 정보모드 100건 제한과 한옥 필터 회귀

- 날짜: 2026-10-03
- 상태: 원인 진단 완료, 코드 수정 미적용
- 관련 작업: OnMaru-Frontend #246·PR #250·PR #275, OnMaru-backend #493·#553·#566

## 문제 상황

운영 `https://www.onmaru.site/map` 정보모드가 활성 지도 카탈로그 전체를 사용하지 않고
100건 이하만 보여준다. 사용자가 `한옥` 칩을 눌러도 한옥 관련 canonical category를
SQL에서 묶어 조회하지 않고, 제한된 표본을 브라우저에서 다시 거르는 상태다.

## 오류명 또는 실패 증상

- `ALL` 운영 map-info API의 `totalCount`는 23,675인데 기존 지도 화면 응답은 최대 100건이다.
- 구형 지도 API는 요청 `limit=1000`에도 100건만 반환한다.
- 중심 `36.35,127.75` 기준 구형 FE API 결과는 반경에 따라 50km 87건, 100km 77건,
  150km 64건으로 줄었다. DB count가 아니라 먼저 잘린 100건을 반경으로 다시 거른 결과다.
- `category=hanok`은 서버 SQL 필터가 되지 않고, 구형 FE route에서 무효 category로 제거된다.
- 신규 `/api/v1/map/info/places`의 `nextCursor`를 그대로 보내도
  `400 INVALID_REQUEST`, `details.field=cursor`가 발생한다.

## 기존 구조나 방식의 한계

신규 정보모드 경로는 전국 목록, `totalCount`, cursor pagination, PostGIS viewport 집계를
분리해 구현했지만 2026-10-02 프론트 커밋 `8468e52`에서 실제 렌더 트리 연결이 제거됐다.
이 커밋은 원래 목록 UI와 feed를 복구하면서 데이터 경로까지 구형 `useMapData`와
TourAPI/legacy API로 되돌렸다. PR #275 본문에는 이 선택의 원인과 검증 결과가 없다.

그 결과 신규 파일은 저장소에 남아 있지만 운영 화면에서는 사용되지 않는다.

- `useInfoMapData.ts`: 신규 list/viewport API 호출과 상태 갱신 책임, 현재 미호출
- `InfoPlaceList.tsx`: `totalCount` 표시와 cursor 추가 로딩 책임, 현재 미렌더링
- `ViewportOverlays.tsx`: REGION/DISTRICT/CLUSTER/PLACE 응답 렌더링 책임, 현재 미렌더링

## 관련 코드 맥락

### 프론트 데이터 경로 회귀

- `OnMaruFE/src/features/map/MapPage.tsx`의 `MapPage()`는 정보모드에서도
  `useMapData()`만 호출한다. 신규 `useInfoMapData()` 호출은 `8468e52`에서 삭제됐다.
- `OnMaruFE/src/features/map/components/ListPanel.tsx`와 `BottomSheet.tsx`는 정보모드에도
  구형 `PlaceList`를 렌더링한다. 이 목록은 서버 전체 count가 아니라 현재 `items.length`를
  제목에 표시하고 10개씩 클라이언트 페이지로 나눈다.
- `OnMaruFE/src/features/map/services/place.service.ts`의 `fetchFromBackend()`는 bbox와
  `limit=1000`을 `/map/places`에 보내지만, 받은 page를 다시 중심 반경으로 필터링한다.
  응답이 이미 100건으로 잘린 뒤이므로 결과는 100건보다 더 작아질 수 있다.
- `OnMaruFE/src/app/api/map/places/route.ts`는 `PLACE_CATEGORIES`에 없는 `hanok`을
  `null`로 바꾼다. 따라서 한옥 칩 요청은 무필터 전체 100건 요청이 된다.
- `PlaceList.tsx`의 `category === 'hanok'` 분기는 그 표본에 `isHanok()`을 적용한다.
  `isHanok.ts`는 건축물·등록 정보가 없으면 장소명의 `한옥/고택/종택/재실/종가` 문자열을
  사용하므로 SQL category union을 대체하지 못한다.

### 백엔드 legacy 제한과 신규 cursor 오류

- `MapInfoLegacyQueryAdapter.MAX_LEGACY_LIMIT`는 100이며 `list()`가 요청 limit에
  `Math.min(limit, 100)`을 적용한다. 구형 호환 API이므로 대용량 정보모드의 주 경로로
  사용하면 안 된다.
- `MapInfoQueryService`는 신규 목록의 기본 page size 30, 최대 100과 signed cursor를 제공한다.
  그러나 `encode()`가 payload와 서명을 `.`으로 연결하고, `decode()`는 전체 문자열을
  `split("\\.")`한다. payload의 거리 필드 `0.0`에도 점이 있어 정상 cursor가 세 조각으로
  나뉘며 `parts.length != 2`로 항상 거부된다.
- cursor round-trip과 실제 두 번째 page를 검증하는 테스트가 없어 이 오류를 막지 못했다.

### 한옥 category 계약 불일치

- 한옥 전용 `HanokListQueryService`는 검색어가 `한옥`이면 `HANOK`, `HANOK_STAY`,
  `HANOK_CAFE`, `HANOK_EXPERIENCE` 네 범주를 한옥 관련 범위로 인정한다.
- 지도 `MapInfoCategory`에는 `HANOK`이 없고 `SPOT`, `STAY`, `CAFE`, `EXPERIENCE`가
  분리돼 있다. 운영 `category=HANOK` 요청은 400이다.
- `MapInfoCategoryMapping.applied(SPOT)`의 설명 목록과 실제 publication SQL도 완전히 같지 않다.
  SQL은 `HANOK→SPOT`, `HANOK_STAY→STAY`, `HANOK_CAFE→CAFE`,
  `HANOK_EXPERIENCE→EXPERIENCE`로 한 개의 조회 scope에 배치한다. 따라서 `SPOT`만으로
  한옥 관련 네 범주를 모두 조회할 수 없다.

## 재현 및 확인 명령

```bash
curl -sS 'https://api.onmaru.site/api/v1/map/info/places?category=ALL&limit=30' \
  | jq '{totalCount, itemCount:(.items|length), hasNext:(.nextCursor != null)}'

curl -sS 'https://api.onmaru.site/api/v1/map/places?bbox=124,33,132,39&limit=1000' \
  | jq '{itemCount:(.items|length), hasMore}'

curl -sS 'https://www.onmaru.site/api/map/places?lat=36.35&lng=127.75&radius=500000&category=hanok' \
  | jq '{itemCount:(.items|length), degraded, error}'

curl -sS -o /dev/null -w '%{http_code}\n' \
  'https://api.onmaru.site/api/v1/map/info/places?category=HANOK&limit=30'
```

cursor 오류는 첫 응답의 `nextCursor`를 같은 category와 limit으로 URL encode해 다시 보내면
재현된다. `ALL`, `SPOT`, `STAY`에서 모두 400을 확인했다.

## 검토한 선택지

1. 구형 API limit만 1,000 이상으로 늘린다.
   - 전체 count, 안정적인 paging, 줌별 집계를 해결하지 못해 제외한다.
2. 프론트만 신규 API에 다시 연결한다.
   - 두 번째 cursor가 400이고 `HANOK` 계약이 없어 불완전하다.
3. 백엔드 cursor만 고친다.
   - 운영 프론트가 신규 API를 호출하지 않으므로 사용자 증상이 그대로다.
4. 한옥 칩을 임시로 `SPOT`에 연결한다.
   - 한옥 숙소·카페·체험이 빠지므로 사용자 의미와 다르다.
5. BE 계약을 보완한 뒤 신규 FE 경로를 복구한다.
   - 전체 데이터, 한옥 의미, 목록·지도 분리를 함께 회복하므로 채택한다.

## 판단 기준과 최종 결정

단순 marker 수 확대가 아니라 전체 count의 정확성, cursor 안정성, 한옥 검색 의미,
줌 단계별 화면 밀도, 구형 API 회귀 방지를 기준으로 판단한다.

최종 결정은 **백엔드의 cursor와 한옥 통합 category 계약을 먼저 고친 뒤, 프론트 정보모드를
`useInfoMapData`·`InfoPlaceList`·`ViewportOverlays` 경로로 다시 연결하는 것**이다.

## 해결 방식과 남은 과제

Issue #566의 `fix/566-map-info-cursor-hanok` 브랜치에서 다음 백엔드 수정을 완료했다.

1. cursor decoder가 전체 `.`을 분리하지 않고 마지막 separator만 서명 경계로 사용한다.
   거리값 `0.0`을 포함한 첫 page cursor로 두 번째 page를 조회하는 회귀 테스트를 추가했다.
2. 지도 public category에 `HANOK`을 추가하고 `HANOK`, `HANOK_STAY`, `HANOK_CAFE`,
   `HANOK_EXPERIENCE` 네 원천 category를 동일한 union으로 정의했다.
3. 목록·근거리 PLACE·CLUSTER SQL은 원천 `display_category`와 기존 category projection을
   함께 조회한다. 원거리 DISTRICT·REGION은 네 원천 category만 직접 집계해 일반 문화재,
   일반 숙소·카페·체험이 섞이지 않게 했다.
4. OpenAPI와 contract fixture, controller·service·PostgreSQL/PostGIS 통합 테스트를 갱신했다.

남은 과제는 FE 신규 경로 복구, staging·운영 배포 후 `totalCount=23,675`, 100건 초과 unique
pagination, 한옥 union count, broad zoom aggregate, TourAPI 직접 호출 부재를 확인하는 것이다.

## 결과

현재 증상은 단일 저장소 문제가 아니다. 100건 이하 노출의 직접 원인은 FE 데이터 경로
회귀였다. 신규 경로를 막던 BE cursor 오류와 한옥 category 계약은 코드 수준에서 수정됐고,
FE 변경 및 BE 배포·운영 검증이 끝나야 사용자 증상이 완전히 해결된다.
