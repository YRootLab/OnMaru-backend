# GitHub develop PR 이슈 자동 종료 누락 정리

## 날짜

2026-09-14

## 문제 상황

최근 PR 본문에 `Closes #...`가 있었고 커밋 로그상 작업도 완료되어 보였지만, GitHub Issues 일부가 계속 Open 상태로 남아 있었다. 사용자가 “git log를 보면 작업한 이슈들인데 왜 안 닫혔는지”를 확인 요청했다.

## 오류명 또는 실패 증상

실패 증상은 GitHub Issue auto-close 미동작이다. PR #145, #148, #149, #150 본문에는 각각 `Closes #61`, `Closes #133`, `Closes #132`, `Closes #69`가 있었지만 `closingIssuesReferences`가 비어 있었고, merge된 #61/#132/#133이 Open으로 남아 있었다.

## 기존 구조나 방식의 한계

이 저장소는 Git Flow를 사용한다. 기본 브랜치는 `main`이고 통합 브랜치는 `develop`이다. 일반 feature/fix/docs PR은 `develop`으로 merge한다. GitHub의 issue auto-close는 기본 브랜치 기준 동작에 의존하기 때문에, `develop`으로 merge된 PR의 `Closes #...` 문구만 믿으면 이슈가 닫히지 않을 수 있다.

또한 GitHub가 가끔 close keyword를 인식하지 못하는 경우도 있으므로 PR 본문에 keyword가 있다는 사실과 실제 Issue state는 별도로 확인해야 한다.

## 관련 코드 맥락

- `AGENTS.md`
  - Source Of Truth와 Work Logs And Cleanup 절에서 GitHub Issue 운영 규칙을 정의한다.
  - 기존에는 “PR은 관련 Issue를 reference하고, Issue close 전 AC와 merge state를 확인한다” 수준이었다.
  - 이번 케이스를 막기 위해 `develop` merge 후 `gh issue view <number> --json state`로 실제 상태를 확인하고, 필요하면 수동 close comment를 남기도록 보강했다.

- GitHub CLI 확인 흐름
  - `gh repo view YRootLab/OnMaru-backend --json defaultBranchRef`로 기본 브랜치가 `main`임을 확인했다.
  - `gh pr view <pr> --json baseRefName,state,mergedAt,body,closingIssuesReferences`로 PR base가 `develop`이고 `closingIssuesReferences`가 비어 있음을 확인했다.
  - `gh issue view <issue> --json state`로 #61/#132/#133이 Open, #69가 Open임을 확인했다.

## 검토한 선택지

1. PR body의 `Closes #...`만 믿고 그대로 둔다.
2. 모든 열린 이슈를 일괄 종료한다.
3. merge된 PR과 acceptance criteria, 검증 명령을 확인한 이슈만 수동 종료한다.
4. `main` release PR까지 기다렸다가 자동 종료를 기대한다.

## 판단 기준

- GitHub Issues가 source of truth이므로 완료된 이슈가 Open으로 남으면 다음 agent가 중복 작업할 수 있다.
- 아직 merge되지 않은 PR의 관련 이슈는 닫으면 안 된다.
- acceptance criteria와 검증이 끝난 이슈만 닫아야 한다.
- 수동 close 시 다음 세션이 이해할 수 있도록 PR 번호와 검증 명령을 comment에 남겨야 한다.

## 최종 결정

merge 완료와 검증이 확인된 #61, #132, #133만 수동 종료하고, PR #150이 아직 Open인 #69는 유지한다. 재발 방지를 위해 `develop` merge 후 closing keyword가 가리키는 Issue를 reconcile하는 GitHub Actions workflow를 추가한다.

## 해결 방식

1. PR과 Issue 상태를 확인했다.
   - PR #145, #147, #148, #149는 `develop`에 merge됨.
   - PR #150은 Open이고 merge state는 clean.
   - #61/#132/#133은 Open으로 남아 있었고 #69도 Open이었다.

2. acceptance evidence를 확인했다.
   - #61: `testing/fixtures/provider/odii` fixture 8개, `docs/reference-snapshots/odii` snapshot 2개 확인.
   - #132: `docs/contracts/openapi/identity-saved.openapi.yaml`, `docs/contracts/fixtures/identity-saved` fixture 20개 확인.
   - #133: `docs/contracts/openapi/r2-map-audio-insights.openapi.yaml`, `docs/contracts/fixtures/r2` fixture 13개 확인.

3. 검증 명령을 실행했다.
   - `node scripts/validate-odii-fixtures.mjs`
   - `node --test scripts/test/odii-fixture-validation.test.mjs`
   - `python3 scripts/test/validate-identity-saved-contract.py`
   - `python3 scripts/test/validate-r2-contract.py`

4. 수동 close comment와 함께 이슈를 닫았다.
   - #61: PR #145/#147과 Odii fixture/redaction 검증 근거를 남기고 close.
   - #132: PR #149와 identity-saved contract 검증 근거를 남기고 close.
   - #133: PR #148과 R2 contract 검증 근거를 남기고 close.

5. `AGENTS.md` 운영 규칙을 보강했다.
   - `develop` merge PR의 `Closes #...`는 자동 종료가 안 될 수 있음을 명시.
   - merge 후 실제 Issue state 확인과 수동 close 기준을 추가.
   - 수동 close comment에 merged PR, auto-close 미동작 이유, 검증 명령을 남기도록 추가.

6. post-merge 자동화를 추가했다.
   - `.github/workflows/issue-reconcile.yml`은 `pull_request.closed` 이벤트 중 `develop` 대상 PR이 실제 merge된 경우에만 실행된다.
   - `scripts/print-closing-issues.mjs`가 PR body에서 `Closes/Fixes/Resolves #...` 번호만 출력한다.
   - workflow는 각 Issue state를 `gh issue view`로 확인하고 Open인 경우에만 comment와 함께 close한다.
   - `scripts/lib/issue-autoclose-reconcile.mjs`와 `scripts/test/issue-autoclose-reconcile.test.mjs`로 keyword parsing, develop merge 조건, close comment 문구를 테스트한다.

## 결과

- #61, #132, #133은 Closed 상태가 되었다.
- #69는 PR #150이 아직 Open이라 유지했다.
- 앞으로 agent는 PR merge 후 `Closes/Fixes/Resolves #...` 문구만 보지 않고 실제 Issue state를 확인해야 한다.
- `develop`에 merge된 PR이 Issue를 닫아야 하는 완료 PR이라면 Issue Reconcile workflow가 먼저 처리하고, workflow가 실패하거나 scope 밖이면 acceptance criteria와 검증 명령을 확인한 뒤 수동 close한다.
