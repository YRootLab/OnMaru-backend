# 26.09.20 Kakao 인증·인가 및 Render callback troubleshooting

## 목적

OnMaru의 Kakao 로그인에서 인증(authentication)과 인가(authorization)가 어디서 처리되는지, 프론트엔드·Spring API·Kakao 사이의 실제 요청 흐름과 Render 배포 시 Redirect URI 설정을 기록한다.

## 현재 구현 결론

Kakao OAuth callback은 프론트엔드가 아니라 Spring API가 직접 받는다. 브라우저에는 Kakao access token을 반환하지 않고, Spring API가 `HttpOnly` opaque session cookie를 발급한다.

Render 백엔드 주소가 `https://onmaru-backend.onrender.com`일 때 Kakao Redirect URI는 다음 값이어야 한다.

```text
https://onmaru-backend.onrender.com/auth/kakao/callback
```

이 값은 다음 두 곳에서 완전히 동일해야 한다.

1. Kakao Developers 애플리케이션의 Redirect URI
2. Render Spring API 서비스의 환경변수

```text
ONMARU_OAUTH_KAKAO_REDIRECT_URI=https://onmaru-backend.onrender.com/auth/kakao/callback
```

Redirect URI는 비밀값이 아니지만, Kakao `client_secret`, OnMaru OAuth secret, session token은 공개하거나 프론트의 `localStorage`에 저장하지 않는다.

## 실제 로그인 흐름

```text
FE
  -> GET https://onmaru-backend.onrender.com/auth/kakao/login
Spring API
  -> state, nonce, PKCE verifier 생성
  -> state/nonce/verifier cookie 설정
  -> 302 https://kauth.kakao.com/oauth/authorize?...&redirect_uri=...
Kakao
  -> GET https://onmaru-backend.onrender.com/auth/kakao/callback?code=...&state=...
Spring API
  -> state, nonce, 만료, 미소비 상태 검증
  -> code + PKCE verifier로 Kakao token endpoint 호출
  -> Kakao user info 조회
  -> provider/issuer/subject로 OnMaru member 연결
  -> __Host-onmaru-session HttpOnly cookie 발급
  -> 303 /discover?auth=success
FE
  -> 이후 API 요청에 백엔드 cookie를 포함
```

구현 위치:

- `apps/spring-api/src/main/java/com/yrootlab/onmaru/security/oauth/kakao/KakaoOAuthController.java`
  - `GET /auth/kakao/login`
  - `GET /auth/kakao/callback`
- `apps/spring-api/src/main/java/com/yrootlab/onmaru/security/oauth/kakao/RestClientKakaoOAuthClient.java`
  - Kakao authorization code 교환
  - Kakao user info 조회
- `modules/identity/src/main/java/com/yrootlab/onmaru/identity/oauth/OAuthLoginService.java`
  - OAuth state 검증·소비
  - 외부 identity와 내부 member 연결
  - OnMaru session 발급

## 인증과 인가의 구분

### 인증(authentication)

“이 사용자가 누구인가?”를 확인하는 과정이다.

1. Kakao가 발급한 `code`를 백엔드가 검증한다.
2. 백엔드가 Kakao access token으로 Kakao 사용자 ID를 조회한다.
3. `KAKAO + https://kauth.kakao.com + subject`를 OnMaru 외부 계정으로 연결한다.
4. 내부 member를 찾거나 생성한다.
5. Kakao token 대신 OnMaru opaque session cookie를 발급한다.

### 인가(authorization)

“이 사용자가 이 리소스를 사용할 권한이 있는가?”를 확인하는 과정이다.

- 공개 장소·지도·후기 조회: 비회원도 허용
- `GET /members/me`: 유효한 member session 필요
- 장소/오디오 저장, saved journey, 후기 작성: member session 및 해당 리소스 정책 필요
- POST/PUT/PATCH/DELETE 같은 cookie 인증 요청: CSRF token 필요
- exploration: 소유 guest, 소유 member 또는 유효한 guest-to-member grant만 허용
- 다른 사용자의 private resource: 404 또는 표준 인증 오류로 노출하지 않음

프론트는 Kakao subject나 이메일을 사용자 식별자로 사용하지 않고, 응답의 `savedByMe`, `likedByMe`, `mine` 같은 서버 계산 상태를 사용한다.

## 프론트 로그인 호출

프론트는 Kakao authorize URL을 직접 조립하지 않고 백엔드 로그인 시작 endpoint로 이동한다.

```ts
window.location.href =
  "https://onmaru-backend.onrender.com/auth/kakao/login?returnTo=/discover";
```

현재 구현의 `returnTo`는 허용된 내부 경로(`/discover`)를 뜻한다. 외부 URL을 그대로 전달하는 open redirect로 사용하지 않는다.

프론트가 백엔드 API를 `fetch`로 호출할 때는 백엔드 세션 cookie가 전송되도록 credentials 정책을 맞춰야 한다.

```ts
fetch("https://onmaru-backend.onrender.com/members/me", {
  credentials: "include",
});
```

## 로컬과 Render 설정 비교

| 환경 | Redirect URI | 로그인 시작 |
|---|---|---|
| Local | `http://localhost:8080/auth/kakao/callback` | `http://localhost:8080/auth/kakao/login` |
| Render | `https://onmaru-backend.onrender.com/auth/kakao/callback` | `https://onmaru-backend.onrender.com/auth/kakao/login` |

기존 프론트 변수인 `NEXT_PUBLIC_KAKAO_REDIRECT_URI=http://localhost:3000/auth/kakao/callback`는 현재 백엔드 callback 구현과 맞지 않는다. 프론트는 callback을 처리하지 않으므로 해당 변수를 로그인 시작 URL로 대체하거나, API 주소를 나타내는 `NEXT_PUBLIC_API_BASE_URL`로 정리한다.

## 자주 발생하는 증상과 확인 순서

### `KOE006` 또는 Redirect URI mismatch

다음 세 문자열을 한 글자씩 비교한다.

1. Kakao Developers에 등록한 URI
2. Render의 `ONMARU_OAUTH_KAKAO_REDIRECT_URI`
3. Spring API가 authorization URL과 token 교환 form에 넣는 `redirect_uri`

`http`/`https`, 포트, 경로, 마지막 slash가 다르면 실패한다.

### 로그인 후 백엔드의 `/discover`로 이동함

현재 callback 성공 응답은 상대 경로 `Location: /discover?auth=success`를 사용한다. 프론트와 백엔드가 서로 다른 호스트라면 브라우저가 백엔드 호스트의 `/discover`로 이동할 수 있다. 배포 전에는 프론트 landing URL을 별도 allowlist 설정으로 두고 callback 성공 시 프론트 origin으로 redirect하는 작업이 필요하다.

### 로그인은 성공했지만 `401`이 반환됨

- API 요청에 `credentials: "include"`가 있는지 확인한다.
- 브라우저 Application/Storage에서 `__Host-onmaru-session`이 발급되었는지 확인한다.
- cookie의 `Secure`, `HttpOnly`, `SameSite`, host 범위를 확인한다.
- 프론트와 API가 서로 다른 site인 경우 CORS allowlist와 credential 응답 헤더를 확인한다.
- Render 로그에서 callback 직후 session 발급과 후속 API 요청의 cookie 전송 여부를 확인한다.

### `auth=failed`로 돌아옴

- Kakao 사용자가 로그인을 취소했는지 확인한다.
- callback에 `code`, `state`가 모두 있는지 확인한다.
- OAuth state가 만료되었거나 이미 소비되었는지 확인한다.
- nonce/verifier cookie가 브라우저에 남아 있는지 확인한다.
- Render secret provider가 Kakao client secret 및 OAuth signing secret을 정상적으로 제공하는지 확인한다.

callback 실패는 guest cookie와 guest exploration을 삭제하지 않아 재로그인할 수 있게 하는 것이 의도된 동작이다.

## 보안 경계

- Kakao access/refresh token은 브라우저 응답과 localStorage에 노출하지 않는다.
- DB에는 session/state 원문이 아니라 hash를 저장한다.
- OAuth callback은 `state`, browser nonce, PKCE verifier, 만료, 미소비 조건을 검증한다.
- 세션 cookie는 `Secure; HttpOnly; SameSite=Lax; Path=/` 및 `__Host-` prefix를 사용한다.
- Cookie 기반 unsafe 요청에는 CSRF token을 사용한다.
- 로그인 성공만으로 guest 탐색 결과를 자동 저장하지 않는다. 로그인 후 프론트가 보존한 intent에 대해 회원용 저장 API를 다시 호출한다.

## 경로 불일치 참고

문서와 fixture 일부는 `/api/v1/auth/kakao/...`를 표기하지만, 현재 Spring Controller의 실제 매핑은 `/auth/kakao/...`이다. Render 앞단 reverse proxy가 `/api/v1` prefix를 추가하지 않는 한 운영 호출은 `/auth/kakao/login`과 `/auth/kakao/callback`을 사용해야 한다. 배포 전 gateway prefix 정책과 OpenAPI 문서를 하나의 실제 경로로 정리한다.
