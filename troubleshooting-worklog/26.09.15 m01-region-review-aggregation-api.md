# M01 행정구역 resolve·VisitReview 지역 집계 API 작업 로그

날짜: 2026-09-15

## 문제 상황

#102는 지도 진입 시 후기 본문을 바로 내려주지 않고, 행정구역별 공개 후기 수와 좌표→행정구역 후보만 제공해야 하는 작업이었다. #137에서 만든 경계 revision import 포트를 재사용하되, `community` 모듈이 `catalog` 모듈을 직접 참조하지 않도록 모듈 경계를 지켜야 했다.

## 오류명 또는 실패 증상

TDD 첫 실행은 `RegionCatalog`, `VisitReviewRegionReadService`, `RegionCountPage`, `RegionResolution` 등 타입이 없어 compile RED가 났다. 구현 후 첫 community 테스트 실패는 `reviewCount` 기대값이 `int`였고 실제 record 필드는 `long`이라 AssertJ tuple 비교가 실패한 것이어서 테스트 기대값을 `1L`, `2L`로 맞췄다. Spring boundary 테스트는 endpoint 미구현 상태에서 404/AssertionError로 RED를 확인했다.

## 기존 구조나 방식의 한계

기존 `VisitReviewQueryService`는 후기 목록 페이지를 제공하지만, 지도 marker용 지역 집계와 위치 동의 좌표 resolve는 별도 책임이다. 또한 `VisitReviewProjection`에는 leaf `regionCode`만 있어 부모 시·도 집계는 region catalog의 parent 관계가 필요했다. 이를 review query에 직접 섞으면 목록 cursor와 지역 집계 책임이 뒤섞인다.

## 관련 코드 맥락

- `modules/community/src/main/java/com/yrootlab/onmaru/community/region/RegionCatalog.java`
  - `activeRevisionId()`, `regions()`, `resolve(lat,lng)` 포트만 정의한다.
  - community는 catalog boundary 구현을 모르고, region projection만 받아 집계한다.

- `modules/community/src/main/java/com/yrootlab/onmaru/community/region/VisitReviewRegionReadService.java`
  - `listRegions(parentRegionCode)`는 현재 region revision과 published review snapshot을 읽어 child region별 count를 계산한다.
  - root 요청은 시·도 단위로 child leaf count를 합산하고, 알 수 없는 regionCode의 published review는 `unassignedCount`로 센다.
  - leaf region을 `parentRegionCode`로 받으면 `VisitReviewRegionInvalidRequestException("parentRegionCode")`를 던져 400으로 매핑한다.
  - `resolve(lat,lng)`는 좌표 범위를 검증하고 catalog 포트의 후보를 confidence `0.99`와 함께 반환한다.

- `apps/spring-api/src/main/java/com/yrootlab/onmaru/web/map/region/CatalogRegionCatalogAdapter.java`
  - #137의 `RegionBoundaryStore`를 community `RegionCatalog` 포트로 변환한다.
  - catalog의 `SIDO/SIGUNGU`를 공개 계약의 `PROVINCE/CITY`로 매핑한다.

- `apps/spring-api/src/main/java/com/yrootlab/onmaru/web/map/region/VisitReviewRegionController.java`
  - `/api/v1/visit-review-regions`, `/api/v1/regions/resolve`를 제공한다.
  - resolve 응답은 위치 정보 캐시를 막기 위해 `Cache-Control: no-store`를 붙인다.

## 검토한 선택지

1. `community`에서 catalog boundary 타입을 직접 import한다.
2. 기존 `VisitReviewQueryService`에 지역 집계를 추가한다.
3. `community.region`에 별도 read service와 `RegionCatalog` 포트를 두고 Spring에서 adapter로 연결한다.
4. regionRevision을 구현에서 빼고 기존 R2 fixture 그대로 둔다.

## 판단 기준

- 모듈 간 의존 방향을 깨지 않아야 한다.
- 후기 목록 API와 지도 집계 API의 책임을 분리해야 한다.
- #102 scope의 `regionRevision`, `unassignedCount`, 좌표 resolve를 공개 계약과 테스트로 확인해야 한다.

## 최종 결정

`community.region` read service + `RegionCatalog` 포트 + Spring adapter 구조를 선택했다. 이 방식이면 PostGIS repository가 들어와도 adapter만 교체하고 지역 집계 도메인 로직은 유지할 수 있다.

## 해결 방식

- root/child region count, leaf parent 400, unassigned count, hidden review 제외를 community 테스트로 고정했다.
- `/visit-review-regions`와 `/regions/resolve` MockMvc 테스트를 추가했다.
- #137의 `InMemoryRegionBoundaryStore`를 Spring bean으로 seed하고 `CatalogRegionCatalogAdapter`로 연결했다.
- R2 OpenAPI `RegionResolution`과 fixture에 `regionRevision`을 추가해 구현과 계약을 맞췄다.
