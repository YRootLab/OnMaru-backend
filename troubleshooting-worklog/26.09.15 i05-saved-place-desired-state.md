# I05 canonical place saved-state 구현

날짜: 2026-09-15

## 문제 상황

Issue #108은 한옥 상세, 지도 카드, Odii 연결 카드가 동일한 canonical `placeId` 저장 상태를 공유하도록 PUT/DELETE desired-state API를 구현하는 작업이었다. 원본 `contentId`나 provider row를 저장하면 화면별 저장 상태가 갈라질 수 있으므로 저장 단위는 공개 canonical place여야 했다.

## 오류명 또는 실패 증상

- RED 테스트 실패: `modules:journey`와 `SavedPlaceService`, `SavedPlaceState`, `InMemorySavedPlaceStore`가 없어 saved-place command 테스트가 컴파일 실패했다.
- 웹 RED 테스트 실패: `InMemorySavedPlaceStore` bean과 `/api/v1/saved-resources/places/{placeId}` controller가 없어 Spring context 테스트가 실패했다.

## 기존 구조나 방식의 한계

V006에는 `journey_saved_resources` schema가 있었지만 Java module 경계는 없었다. #99에서 detail projection의 `savedByMe`는 임시 in-memory lookup을 사용했기 때문에, 실제 save/unsave command와 상세 조회 projection이 같은 저장소를 바라보지 못했다.

## 관련 코드 맥락

- `modules/journey/.../SavedPlaceService`
  - 입력: member UUID, canonical `placeId`
  - 처리: command마다 `PlaceSaveEligibility`로 공개 projection 여부를 재검증하고, save limit을 넘지 않으면 store에 desired state를 저장한다.
  - 출력: `SavedPlaceState`, DELETE는 idempotent void
- `InMemorySavedPlaceStore`
  - `(memberId, placeId)`를 key로 저장해 반복 PUT이 같은 row/state를 반환한다.
  - 반복 DELETE는 존재하지 않아도 성공한다.
- `apps/spring-api/.../SavedPlaceController`
  - opaque session을 `MemberLifecycleService`로 해석한다.
  - 미인증은 `AUTH_REQUIRED`, 비공개/없는 place는 `NOT_FOUND`, limit 초과는 `SAVE_LIMIT` envelope으로 변환한다.
- `CatalogDetailConfiguration`
  - place detail `savedByMe` lookup을 journey saved store에 연결해 save 이후 상세 조회가 같은 상태를 읽도록 했다.

## 검토한 선택지

1. catalog module에 saved command를 넣는다.
2. identity module에 saved resource를 넣는다.
3. issue의 expected touch point대로 `modules:journey`를 추가하고 saved-resource command boundary를 둔다.
4. Spring controller에서만 in-memory map을 직접 관리한다.

## 판단 기준

- saved resource는 journey/saved-resource schema와 같은 수명주기를 가진다.
- catalog는 공개 장소 eligibility를 제공하고, 저장 command의 소유권과 desired state는 별도 application boundary가 낫다.
- 상세 projection과 저장 command가 같은 store를 바라봐야 `savedByMe`가 흔들리지 않는다.

## 최종 결정

3번을 선택했다. `modules:journey`에 saved-place command service를 만들고, Spring API에서 catalog eligibility와 identity session을 조합했다.

## 해결 방식

- `settings.gradle.kts`와 `apps:spring-api` dependency에 `modules:journey`를 추가했다.
- `SavedPlaceServiceTests`로 중복 PUT 한 row, 반복 DELETE 성공, command별 eligibility 재검증, limit conflict를 먼저 고정했다.
- `SavedPlaceWebBoundaryTests`로 PUT/DELETE API, auth required, private place 404, limit 409, save 후 detail `savedByMe=true` 연결을 검증했다.
- CI에 `Journey module tests` 단계를 추가해 새 모듈 테스트가 PR마다 자동 실행되게 했다.

## 결과

- 동일 member/place 반복 PUT은 한 row로 유지된다.
- DELETE는 이미 없는 saved place에도 204로 성공한다.
- 비공개/삭제/불명확 place는 저장되지 않고 404로 응답한다.
- 저장 상태는 place detail projection의 `savedByMe`와 공유된다.
