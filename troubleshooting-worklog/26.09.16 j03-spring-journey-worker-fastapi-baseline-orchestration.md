## Implemented

- `modules/journey/worker`에 worker core application service와 port를 추가했다.
- `JourneyWorkerService`는 다음 흐름을 보장한다.
  - durable run claim
  - `RETRIEVING -> VALIDATING -> PERSISTING` stage advance
  - candidate payload 조회
  - correlation-aware FastAPI/AI proposal port 호출
  - `AI_TIMEOUT`, `AI_QUOTA_EXCEEDED` 등 AI 실패 시 baseline plan fallback
  - result persistence port 호출
  - result persist가 terminal/expired discard를 반환하면 run terminal overwrite 없이 중단
  - 성공 시 run을 `COMPLETED`로 finish
- 관측성 이벤트를 추가했다.
  - `journey.worker.completed`: `run.id`, `engine`, `degraded.reason`
  - `journey.worker.late_result_discarded`: `run.id`, `reason`
- 민감정보 방지를 위해 telemetry attribute는 run id, engine, degraded reason, discard reason만 기록하고 query/candidate evidence/body/token은 기록하지 않는다.
- `adapters:persistence-jdbc`에 `JdbcJourneyResultStore`를 추가했다.
  - `RUNNING` run, `deadline_at > CURRENT_TIMESTAMP`, exploration `state_version = baseVersion`을 모두 만족할 때만 board를 CAS update한다.
  - terminal 상태면 `DISCARDED_TERMINAL`, deadline이 지난 run이면 `DISCARDED_EXPIRED`를 반환해 worker가 terminal overwrite를 하지 않게 한다.
- `DefaultBaselinePlanner`를 추가해 AI timeout/quota fallback이 실제 deterministic board plan을 만들 수 있게 했다.
  - 후보 순서를 보존하고 최대 3개만 선택한다.
  - 후보가 없으면 `NO_RESULTS`를 반환한다.
- Spring 내부 AI boundary의 `X-Revision` 누락을 보완했다.
  - `InternalAiTokenRequest`가 revision을 포함한다.
  - token claim과 internal request headers에 revision을 함께 싣는다.
- `SpringJourneyWorkerTelemetry`를 추가해 worker core event를 기존 Spring `TelemetrySink`로 연결했다.
- `HttpAiProposalClient`를 추가해 Spring worker가 FastAPI internal proposal endpoint를 호출할 수 있게 했다.
  - 요청 body는 `schemaVersion/requestId/runId/candidateCount`만 포함해 raw query와 evidence body를 보내지 않는다.
  - `Authorization`, `X-Request-Id`, `X-Run-Id`, `X-Revision`, `traceparent`를 전송한다.
  - 429는 `AI_QUOTA_EXCEEDED`, timeout은 `AI_TIMEOUT`, invalid response는 `AI_INVALID_RESPONSE`, 기타 5xx/IO는 `AI_SERVICE_UNAVAILABLE`로 매핑한다.
  - 성공/실패 모두 `journey.worker.ai_call` telemetry를 남긴다.
- worker wiring을 추가했다.
  - `JourneyWorkerQueue`, `InMemoryJourneyWorkerQueue`, `JourneyWorkerRunner`로 deterministic queue drain을 제공한다.
  - `JourneyWorkerConfiguration`이 queue, candidate provider, baseline planner, JDBC run store, JDBC result store, HTTP AI client, worker service, runner를 Spring bean으로 연결한다.
  - `apps:spring-api`가 `adapters:persistence-jdbc`를 runtime implementation dependency로 갖도록 조정했다.
- candidate provider를 추가했다.
  - `InMemoryJourneyCandidateProvider`는 dataset revision + region code 기준으로 deterministic candidate payload를 반환한다.
- FastAPI internal contract를 동기 proposal response로 정렬했다.
  - response: `schemaVersion`, `runId`, `orderedRefs`, `outcome`
  - OpenAPI `InternalJourneyProposalResponse`도 같은 shape로 갱신했다.
  - FastAPI fake endpoint가 service token 인증 뒤 Pydantic request contract를 검증한다.
  - body `requestId/runId`와 correlation header가 불일치하면 `INTERNAL_AI_CONTRACT_INVALID`로 422를 반환한다.
- worker core 관측성을 확장했다.
  - `journey.worker.started`
  - `journey.worker.candidates_retrieved` with `candidate.count`
- 문서 경계를 정리했다.
  - `docs/ai/journey-guardrails.md`의 internal path를 `/internal/v1/journey/proposals`로 맞췄다.
  - J03 baseline contract는 `schemaVersion/requestId/runId/candidateCount`만 전송하고, richer proposal reason/evidence/action/stateVersion은 #120 계열 후속으로 남긴다고 명시했다.

## Remaining Risks

- 현재 `JdbcJourneyResultStore`는 baseline/board persistence의 최소 JSON snapshot만 저장한다. `discovery_proposals` preview persistence와 richer proposal reason/evidence/action/stateVersion은 열린 #120에 맡긴다.
- candidate provider는 deterministic in-memory adapter다. #97은 Closed지만 실제 catalog/baseline ranking projection adapter로 교체하는 작업은 별도 integration follow-up이 필요하다.
- public exploration scaffold와 durable `discovery_runs` 생성 흐름은 아직 완전히 통합되지 않았다. 이번 작업은 worker claim/persist/orchestration port와 Spring bean wiring까지 닫았고, create API에서 durable run 생성까지 합치는 일은 별도 이슈로 분리하는 편이 안전하다.
- branch parser가 Issue #114를 반환하지 않으므로 PR 전 브랜치 정책 정리가 필요하다.
