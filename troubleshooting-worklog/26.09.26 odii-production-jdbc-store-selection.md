# Odii 운영 API 503와 JDBC 저장소 선택 오류 트러블슈팅

- 날짜: 2026-09-26
- 관련 이슈: #307, #382
- 대상 환경: Render Spring API `production` profile, Neon PostgreSQL
- 결론: 공공데이터 응답 장애가 아니라 Spring bean 등록 순서에 따라 운영 서버가 in-memory `AudioRevisionStore`를 선택한 것이 직접 원인이었다.

## 문제 상황

공공데이터 Odii 원천에서는 데이터를 조회할 수 있었지만 OnMaru 운영 서버의 Odii 계열 API는 모두 `503 SERVICE_UNAVAILABLE`을 반환했다. 애플리케이션 health는 `UP`이어서 단순 프로세스 장애나 전체 DB 연결 실패로 보기 어려웠다.

영향을 확인한 경로는 다음과 같다.

- `GET /api/v1/odii/stories`
- `GET /api/v1/home/trending-sounds`
- `GET /api/v1/home/popular-sounds`
- `GET /api/stories`
- `GET /api/stories/nearby`
- `GET /api/recommendation`
- `GET /api/v1/odii/regions`

## 오류명과 실패 증상

- 외부 증상: HTTP `503`, 오류 코드 `SERVICE_UNAVAILABLE`
- 내부 상태 불일치: `operations_sync_leases`의 `odii-audio` generation은 증가하지만 revision과 story 관련 테이블은 비어 있음
- 비어 있던 핵심 테이블:
  - `catalog_dataset_revisions`
  - `catalog_active_datasets`
  - `audio_revision_stages`
  - `audio_story_versions`
  - `operations_sync_runs`
- 따라서 스케줄러는 살아 있고 PostgreSQL lease도 획득하지만, 조회 API가 읽을 published active revision은 존재하지 않았다.

## 정상 데이터 흐름

운영 Odii 데이터는 요청 시 공공데이터를 직접 조회하지 않고 다음 순서로 제공한다.

1. `OdiiSyncSchedulingAdapter`가 PostgreSQL lease를 획득한다.
2. `OdiiRevisionSyncService`가 `storyBasedSyncList` 페이지들을 수집하고 매핑한다.
3. `AudioRevisionStore`가 stage, story version, active revision을 원자적으로 게시한다.
4. `ActiveRevisionOdiiStoryQueryStore`가 published active revision snapshot을 읽는다.
5. 컨트롤러가 조회 결과를 반환하며, active dataset이 없으면 fail-closed로 `503`을 반환한다.

즉 공공데이터 응답이 정상이더라도 2~3단계가 영속 저장소로 연결되지 않으면 OnMaru API는 데이터를 제공할 수 없다.

## 관련 코드 맥락

### `AudioPersistenceConfiguration.jdbcAudioRevisionStore()`

- 경로: `apps/spring-api/src/main/java/com/yrootlab/onmaru/persistence/audio/AudioPersistenceConfiguration.java`
- 책임: production의 `DataSource`로 `JdbcAudioRevisionStore`를 생성하고 `initializeDataset()`을 호출한다.
- 입력: production `DataSource`, `onmaru.audio.dataset`
- 출력과 side effect: JDBC store bean을 제공하고 bootstrap revision과 active pointer를 DB에 생성한다.
- 원인 연결: 이 bean이 실제로 생성됐다면 운영 DB가 완전히 0행일 수 없으므로, 0행 상태는 bean 자체가 선택되지 않았다는 강한 증거였다.

수정 전 이 bean에는 `@ConditionalOnBean(DataSource.class)`와 `@ConditionalOnMissingBean(AudioRevisionStore.class)`가 함께 있었다. Spring 설정 처리 순서에 따라 DataSource가 아직 bean definition으로 보이지 않거나 in-memory store가 먼저 등록되면 JDBC store가 조용히 생략될 수 있었다.

### `OdiiStoryConfiguration.odiiAudioRevisionStore()`

- 경로: `apps/spring-api/src/main/java/com/yrootlab/onmaru/web/audio/OdiiStoryConfiguration.java`
- 책임: 개발·테스트 환경에서 빈 bootstrap snapshot을 제공하는 fallback 저장소다.
- 입력: dataset 설정
- 출력: `InMemoryAudioRevisionStore`
- 원인 연결: 수정 전에는 profile 제한 없이 `@ConditionalOnMissingBean`만 사용했다. 설정 등록 순서상 이 bean이 먼저 보이면 production에서도 in-memory store가 선택될 수 있었다.

### `OdiiStoryConfiguration.odiiStoryQueryStore()`

- 책임: `AudioRevisionStore`의 active published snapshot을 읽는 query store를 조립한다.
- 수정 전 한계: `ObjectProvider`로 store를 선택하고, 없으면 메서드 내부에서도 in-memory fallback을 생성했다. 운영 설정 오류가 기동 실패로 드러나지 않고 빈 dataset으로 숨을 수 있었다.
- 조회 결과: 빈 active snapshot은 상위 컨트롤러에서 `503 SERVICE_UNAVAILABLE`로 변환된다.

### `OdiiSyncSchedulingAdapter`

- 경로: `apps/spring-api/src/main/java/com/yrootlab/onmaru/scheduling/audio/OdiiSyncSchedulingAdapter.java`
- 책임: 동기화 lease를 PostgreSQL에서 획득한 뒤 revision store와 sync service를 호출한다.
- 원인 연결: lease 저장은 별도 JDBC 경로였기 때문에 `operations_sync_leases`만 증가하는 현상이 가능했다. lease 증가는 전체 Odii 영속화 성공을 뜻하지 않았다.

## 진단 과정

1. 운영 health와 API 응답을 분리해 확인했다. health는 `UP`, Odii 소비 API만 일관되게 `503`이었다.
2. CORS 오류나 잘못된 endpoint 문제를 배제했다. 정상 허용 origin의 preflight는 성공했고 여러 Odii 경로가 동일 증상을 보였다.
3. 배포 버전을 확인했다. 초기화 로직 이후 추가된 API가 존재해 단순 구버전 배포만으로 설명되지 않았다.
4. Neon 테이블을 확인했다. lease generation만 증가하고 bootstrap revision조차 없었다.
5. `JdbcAudioRevisionStore.initializeDataset()`의 보장 조건과 DB 상태를 대조해 JDBC store 미선택으로 범위를 좁혔다.
6. Spring configuration 등록 순서를 뒤집은 테스트로 in-memory store 선점 문제를 재현했다.
7. DataSource configuration을 나중에 처리한 테스트로 `@ConditionalOnBean(DataSource.class)`의 추가 순서 의존성도 재현했다.

## 검토한 선택지

### 1. 운영 API에서 공공데이터를 직접 호출

조회는 일시 복구될 수 있지만 timeout, rate limit, 장애 전파, 원자 snapshot/LKG 정책을 우회한다. 기존 설계와 맞지 않아 제외했다.

### 2. 빈 데이터셋을 HTTP 200으로 반환

장애를 정상 응답으로 숨기고 FE가 실제 빈 결과와 적재 장애를 구분하지 못한다. 기존 fail-closed 계약을 유지하기 위해 제외했다.

### 3. bean 등록 순서만 조정

현재 순서에서는 동작할 수 있지만 configuration scan이나 import 변경 시 재발한다. 순서 의존성을 제거하지 못해 제외했다.

### 4. production과 non-production 저장소 책임을 profile로 분리

운영은 JDBC store를 필수로 등록하고, in-memory fallback은 비운영에서만 허용한다. 설정 오류도 시작 시 드러나므로 이 방식을 선택했다.

## 판단 기준

- production에서 저장소 선택이 configuration 등록 순서와 무관해야 한다.
- 운영 DB 설정이 잘못되면 빈 메모리 저장소로 조용히 기동하지 않고 fail-fast 해야 한다.
- 기존 개발·테스트 환경의 in-memory 편의는 유지해야 한다.
- public API의 `503` fail-closed 계약과 revision/LKG 게시 구조를 보존해야 한다.

## 최종 결정과 해결 방식

1. `odiiAudioRevisionStore()`에 `@Profile("!production")`을 적용했다.
   - production에서 in-memory store가 JDBC store를 선점할 수 없다.
2. production의 `jdbcAudioRevisionStore()`에서 두 조건부 annotation을 제거했다.
   - production profile이면 DataSource를 필수 주입해 JDBC store를 항상 구성한다.
   - DataSource가 없으면 시작 단계에서 실패하므로 잘못된 fallback 기동을 막는다.
3. `odiiStoryQueryStore()`가 `AudioRevisionStore`를 직접 주입받도록 변경했다.
   - 메서드 내부의 두 번째 in-memory fallback을 제거해 운영 설정 누락을 숨기지 않는다.
4. configuration 순서와 늦은 DataSource 등록을 각각 검증하는 통합 테스트를 추가했다.
   - 수정 전에는 `NoSuchBeanDefinitionException` 또는 잘못된 store 선택으로 실패했고, 수정 후 모두 `JdbcAudioRevisionStore`를 확인한다.

## 민감정보 조치

기존 worklog에 있던 평문 DB password는 `<Render secret에서 주입>`으로 교체했다. 현재 working tree에서는 해당 credential 패턴이 검출되지 않는다.

다만 이미 생성된 Git commit 이력에는 과거 값이 남아 있다. 문서 수정만으로 과거 노출을 무효화할 수 없으므로 다음 운영 조치가 필요하다.

1. 노출된 credential 폐기 및 새 credential 발급
2. Render secret 교체와 재배포
3. 영향 범위와 접근 로그 확인
4. 협의된 maintenance window에서 Git 이력 정리 여부 결정

보고서, Issue, PR, 로그에는 기존 값을 다시 기록하지 않는다.

## 해결 범위와 남은 과제

- 코드 수준의 저장소 선택 오류는 해결했다.
- 아직 production 재배포 전이므로 운영 `503` 복구를 완료로 판정하지 않는다.
- 재배포 후 `catalog_dataset_revisions` → `audio_revision_stages` → `audio_story_versions` → `catalog_active_datasets` 순서로 확인한다.
- stage가 `SOURCE_FAILED`이면 그때 provider 요청/응답, timeout, pagination, 인증 설정을 별도로 진단한다.
- 모든 Odii API가 `200`을 반환하고 active revision에 story가 존재할 때 #307을 종료한다.
- #382의 durable sync run 이력과 단계별 관측성은 이번 저장소 선택 수정과 별개의 후속 구현으로 유지한다.
