# PostgreSQL/PostGIS 로컬 통합 테스트 기반 구축 기록

## 날짜

2026-09-14

## 문제 상황

Issue #65의 목표는 migration과 공간 SQL을 나중에 실제 DB에서 검증할 수 있도록, H2 같은 in-memory DB가 아니라 PostgreSQL/PostGIS 컨테이너 기반 테스트 환경을 먼저 만드는 것이었다.

이번 작업의 산출 PR은 #144이며, PR #144는 Issue #144가 아니라 Issue #65를 구현한 Pull Request다. 저장소 기본 브랜치가 `main`이고 PR base가 Git Flow 정책상 `develop`이라 GitHub 자동 close 연결은 잡히지 않았다. 그래서 PR 본문은 `Refs #65`로 두고, merge 후 acceptance criteria를 다시 확인한 뒤 #65를 수동 close하기로 했다.

## 오류명 또는 실패 증상

- `Could not find org.testcontainers:junit-jupiter:.`
- `Could not find org.testcontainers:postgresql:.`
- `Failed to verify that image 'postgis/postgis:17-3.5-alpine' is a compatible substitute for 'postgres'`
- `Could not find a valid Docker environment`

처음에는 Spring Boot의 dependency management가 Testcontainers 부가 모듈 버전을 자동으로 잡아줄 것처럼 보였지만, 실제로는 버전 없는 dependency가 resolve되지 않았다. 이후 Testcontainers 1.x 부가 모듈과 Spring Boot 4.1.1이 관리하는 Testcontainers core 2.0.5가 섞이면서 이미지 호환성/버전 조합을 다시 판단해야 했다. 마지막 실패는 코드 문제가 아니라 Docker Desktop daemon이 꺼져 있어 `/var/run/docker.sock`과 Docker Desktop socket을 찾지 못한 환경 문제였다.

## 기존 구조나 방식의 한계

기존 Spring API scaffold는 Actuator health test만 있었고 DB 의존성이 없었다. ADR-0004는 환경당 PostgreSQL 하나와 PostGIS를 선택했지만, 실제 PostGIS extension이 올라오는지 검증하는 테스트나 로컬 compose readiness는 없었다.

즉 문서상 결정은 있었지만, 다음 Flyway/migration 작업에서 공간 타입이나 공간 SQL을 넣었을 때 “실제 DB에서 깨지는지”를 미리 잡아주는 바닥이 없었다.

## 관련 코드 맥락

- `apps/spring-api/build.gradle.kts`
  - 담당 로직: Spring API 테스트 classpath에 Testcontainers core와 PostgreSQL JDBC driver를 추가한다.
  - 입력과 출력: Gradle dependency 선언을 입력으로 받아 `testCompileClasspath`와 `testRuntimeClasspath`를 구성한다.
  - 문제 연결: JDBC driver가 없으면 `DriverManager.getConnection(...)`이 PostgreSQL URL을 열 수 없고, Testcontainers가 없으면 실제 DB 컨테이너를 띄울 수 없다.

- `gradle/libs.versions.toml`
  - 담당 로직: repository 전체에서 재사용할 dependency version alias를 정의한다.
  - 결정: `org.testcontainers:testcontainers`는 Spring Boot 4.1.1과 맞는 core `2.0.5`로 두고, PostgreSQL JDBC는 `42.7.13`으로 고정했다.
  - 문제 연결: 처음 `junit-jupiter`, `postgresql` Testcontainers 부가 모듈을 넣었을 때 버전 resolve와 core 버전 충돌이 생겼다. 그래서 부가 모듈 대신 core `GenericContainer`를 직접 사용해 의존성 표면을 줄였다.

- `apps/spring-api/src/test/java/com/yrootlab/onmaru/testing/postgres/PostgresContainerSmokeTests.java`
  - 담당 로직: `postgis/postgis:17-3.5-alpine` 실제 Docker image를 Testcontainers로 띄우고, JDBC로 접속해 PostGIS extension과 reset 동작을 검증한다.
  - 입력과 출력: container 환경 변수 `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`를 넣고, mapped port로 만든 JDBC URL을 반환한다.
  - 핵심 분기: `@BeforeAll`에서 컨테이너를 시작하고, `@AfterAll`에서 정리한다. 테스트 본문은 `CREATE EXTENSION IF NOT EXISTS postgis` 후 `SELECT PostGIS_Version()`을 호출한다.
  - 왜 중요한가: 이 테스트가 깨지면 “PostGIS 포함 실제 DB에서 migration/spatial SQL을 검증할 수 있다”는 #65의 첫 acceptance criteria가 깨진다.

짧은 핵심 흐름은 다음과 같다.

```java
statement.execute("CREATE EXTENSION IF NOT EXISTS postgis");
try (var resultSet = statement.executeQuery("SELECT PostGIS_Version()")) {
    assertThat(resultSet.next()).isTrue();
    assertThat(resultSet.getString(1)).isNotBlank();
}
```

- `apps/spring-api/src/test/java/com/yrootlab/onmaru/testing/postgres/PostgresTestDatabase.java`
  - 담당 로직: 테스트가 남긴 table/data를 지우기 위해 `public` schema를 통째로 drop/create하고, `postgis` extension을 다시 만든다.
  - 입력과 출력: 이미 열린 `Connection`을 입력받고, 같은 DB 연결 안에서 schema reset side effect를 만든다. 별도 값을 반환하지 않는다.
  - 핵심 분기: 기존 auto-commit 값을 보존하고, reset 작업은 transaction으로 묶는다. SQL 실패 시 rollback하고 예외를 다시 던진다.
  - 왜 중요한가: 반복 테스트에서 이전 실행의 table/data가 남으면 migration test가 우연히 통과하거나 실패할 수 있다. 이 helper는 “테스트마다 깨끗한 public schema”를 만든다.

```java
statement.execute("DROP SCHEMA IF EXISTS public CASCADE");
statement.execute("CREATE SCHEMA public");
statement.execute("GRANT ALL ON SCHEMA public TO public");
statement.execute("CREATE EXTENSION IF NOT EXISTS postgis");
```

- `infra/local/postgres/compose.yaml`
  - 담당 로직: 로컬 개발용 PostgreSQL/PostGIS 컨테이너를 띄운다.
  - 입력과 출력: `ONMARU_POSTGRES_PORT`, `ONMARU_POSTGRES_DB`, `ONMARU_POSTGRES_USER`, `ONMARU_POSTGRES_PASSWORD` 환경 변수를 입력처럼 사용하고, healthy 상태의 PostGIS DB를 제공한다.
  - 핵심 분기: init SQL을 `/docker-entrypoint-initdb.d`에 mount해 최초 DB 생성 시 `postgis` extension을 만든다. healthcheck는 `pg_isready`와 `pg_extension`의 `postgis` 등록 여부를 같이 확인한다.
  - 왜 중요한가: `pg_isready`만 통과하면 PostgreSQL은 떠 있어도 PostGIS가 실제로 생성됐는지 알 수 없다. 이번 healthcheck는 “DB가 열림”과 “PostGIS extension이 등록됨”을 함께 본다.

## 검토한 선택지

1. Testcontainers의 `PostgreSQLContainer` + `postgis/postgis` compatible substitute 선언
2. Testcontainers `junit-jupiter`, `postgresql` 부가 모듈 사용
3. Testcontainers core `GenericContainer` + PostgreSQL JDBC 직접 접속
4. Docker compose만 두고 Java integration test는 나중으로 미루기
5. Docker가 없을 때 테스트를 skip 처리하기

## 판단 기준

- Issue #65는 “container integration smoke”가 verification method이므로 Java test에서 실제 컨테이너를 띄워야 한다.
- in-memory DB 대체는 명시적으로 금지되어 있다.
- 현재 Spring Boot 4.1.1 dependency management와 충돌하지 않는 단순한 dependency 구성이 필요하다.
- Docker가 없는 환경에서 조용히 skip하면 acceptance criteria가 CI/로컬에서 빠질 수 있으므로, smoke test는 실패를 드러내는 편이 낫다.

## 최종 결정

Testcontainers core `GenericContainer`로 PostGIS 이미지를 직접 띄우고, PostgreSQL JDBC로 연결해 extension과 reset을 검증하는 방향을 선택했다.

이유는 `PostgreSQLContainer` 전용 부가 모듈 없이도 실제 DB container와 JDBC 경로를 검증할 수 있고, Spring Boot 4.1.1이 관리하는 Testcontainers core 2.0.5와 버전 충돌을 줄일 수 있기 때문이다.

## 해결 방식

1. 먼저 실패하는 테스트를 추가했다.
   - `startsPostgresWithPostgisExtension()`은 PostGIS extension이 없거나 컨테이너가 실제 PostgreSQL/PostGIS가 아니면 실패한다.
   - `resetLeavesDatabaseCleanForRepeatedRuns()`는 reset 후 이전 테이블이 남거나 PostGIS extension이 다시 보장되지 않으면 실패한다.

2. dependency resolve 실패를 정리했다.
   - 처음에는 Testcontainers `junit-jupiter`, `postgresql` 모듈을 넣었으나 버전 resolve와 core 버전 조합이 꼬였다.
   - 이후 `org.testcontainers:testcontainers:2.0.5` core만 사용하고, `org.postgresql:postgresql:42.7.13` JDBC driver를 runtime에 추가했다.
   - `apps/spring-api/gradle.lockfile`은 `./gradlew :apps:spring-api:dependencies --write-locks`로 갱신했다.

3. Docker daemon 문제를 환경 문제로 분리했다.
   - `docker --version`은 통과했지만 `docker info`가 socket 없음으로 실패했다.
   - Docker Desktop을 시작한 뒤 daemon이 올라왔고, 같은 smoke test가 통과했다.

4. local compose readiness를 강화했다.
   - `infra/local/postgres/init/001-postgis.sql`에서 `CREATE EXTENSION IF NOT EXISTS postgis;`를 실행한다.
   - healthcheck는 `pg_isready`만 보지 않고 `pg_extension WHERE extname = 'postgis'`까지 확인한다.

5. PR 전 기록과 검증을 맞췄다.
   - `handoff.md`에 #65 세션, 검증 명령, PR close 방식을 기록했다.
   - `CHANGELOG.md`에 PostGIS/Testcontainers smoke와 local compose readiness 추가를 기록했다.
   - PR #144를 열고 Issue #65에 검증 근거 comment를 남겼다.

## Java top-down 학습 관점 메모

이번 작업은 “Spring API 기능 구현”이라기보다 “나중에 Spring repository/migration 테스트가 믿을 수 있는 DB 바닥을 만든 작업”이다.

Top-down으로 보면 흐름은 이렇게 잡으면 된다.

1. 제품/아키텍처 결정: OnMaru는 공간 검색과 관계형 불변식을 위해 PostgreSQL/PostGIS를 쓴다.
2. 테스트 목표: DB 관련 코드는 H2가 아니라 실제 PostgreSQL/PostGIS에서 검증해야 한다.
3. Java 테스트 구조: JUnit test class가 Testcontainers로 DB를 띄우고 JDBC로 SQL을 실행한다.
4. helper 책임: `PostgresTestDatabase.reset(Connection)`은 테스트 사이 DB 상태를 초기화한다.
5. 다음 단계 연결: Issue #67 Flyway migration이 들어오면 이 컨테이너 테스트 기반 위에서 migration 적용과 공간 SQL을 검증할 수 있다.

처음부터 JDBC나 Testcontainers API를 바닥부터 외우기보다, “왜 실제 DB 테스트가 필요한가 → 어떤 class가 컨테이너 lifecycle을 맡는가 → 어떤 helper가 DB 상태를 reset하는가 → 어떤 SQL이 acceptance를 증명하는가” 순서로 보면 훨씬 덜 막힌다.
