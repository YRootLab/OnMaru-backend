# D01 Flyway migration baseline 작업 기록

## 날짜

2026-09-14

## 문제 상황

Issue #67은 문서 DBML에 머물러 있던 OnMaru DB 설계를 실제 PostgreSQL에서 실행 가능한 Flyway migration 기준으로 바꾸는 작업이다. 빈 DB와 기존 DB를 같은 baseline schema 상태로 올리고, 후속 migration이 충돌 없이 version을 예약할 수 있어야 했다.

## 오류명 또는 실패 증상

- `org.flywaydb.core` package가 없어 `FlywayMigrationBaselineTests` compile이 실패했다.
- `db/migration/registry/migrations.json`이 없어 Node migration policy test가 `ENOENT`로 실패했다.
- `baselineOnMigrate=true`의 기본 `baselineVersion=1` 때문에 기존 객체가 있는 DB에서 `V001`이 baseline 처리되고 실제 SQL이 실행되지 않았다.
- 초기 리뷰에서 checksum marker만 확인하면 SQL 본문 drift를 잡지 못하고, migration SQL에 고정 password를 넣으면 운영 secret이 classpath에 배포될 수 있다는 문제가 확인됐다.

## 기존 구조나 방식의 한계

`docs/database/schema.dbml`과 Azimutt export SQL은 논리 설계와 시각화 보조 산출물이었다. Spring Boot scaffold와 PostGIS Testcontainers는 있었지만, Flyway 실행 SQL, version registry, runtime role DDL 거부 검증은 없었다. 따라서 후속 D02-D09 업무 table migration이 각자 version을 만들면 충돌이나 기존 SQL 수정이 CI에서 걸리지 않는 상태였다.

## 관련 코드 맥락

- `apps/spring-api/src/main/resources/db/migration/baseline/V001__d01_flyway_migration_baseline.sql`
  - Flyway가 classpath에서 읽는 실제 baseline SQL이다.
  - `onmaru`, `onmaru_registry` schema를 만들고, `migration_version_reservations`에 `V001` 예약을 기록한다.
  - `onmaru_migration`, `onmaru_runtime`, `onmaru_readonly`, `onmaru_backup`은 비밀번호 없는 `NOLOGIN` group role로 만든다. 환경별 login role과 secret은 운영 provisioning에서 만들고 이 group role에 membership을 준다.
  - runtime role에는 schema `CREATE` 권한을 주지 않아 DDL이 거부된다.

- `apps/spring-api/src/test/java/com/yrootlab/onmaru/testing/postgres/FlywayMigrationBaselineTests.java`
  - PostGIS Testcontainers DB에 Flyway를 직접 실행한다.
  - `migratesEmptyDatabaseToD01Baseline`은 빈 DB에서 schema, registry, NOLOGIN role 4종이 생기는지 확인한다.
  - `upgradesDatabaseWithExistingBaselineMarker`는 기존 table이 있는 DB에서도 `baselineVersion=0`으로 `V001`이 적용되는지 확인한다.
  - `runtimeRoleCannotCreateTables`는 테스트용 login role을 `onmaru_runtime` member로 만들고 `CREATE TABLE onmaru...`가 permission denied 되는지 확인한다.
  - `futureMigrationTablesGrantRuntimeAndReadonlyAccess`는 후속 table에 runtime DML, readonly SELECT가 적용되고 readonly INSERT가 거부되는지 확인한다.

- `scripts/test/migration-policy.test.mjs`
  - `db/migration/registry/migrations.json`과 실제 Flyway SQL 파일 목록을 비교한다.
  - registry에 없는 SQL 파일, 등록만 있고 없는 SQL 파일, 중복 version, 파일명 version과 registry version 불일치, SQL SHA-256 drift를 CI에서 실패시킨다.

## 검토한 선택지

1. DBML에서 생성한 전체 PostgreSQL SQL을 바로 Flyway baseline으로 넣기
2. D01에서는 namespace, role, registry만 만들고 업무 table은 후속 issue로 분리하기
3. role login/password를 migration SQL에서 직접 만들기
4. NOLOGIN group role만 migration에서 만들고 login role은 환경별 provisioning으로 분리하기
5. checksum marker 문자열만 검사하기
6. 실제 SQL SHA-256을 registry에 저장해 본문 변경을 감지하기

## 판단 기준

- Issue #67의 out of scope인 모든 업무 table은 만들지 않는다.
- 운영 secret이 repository와 application classpath에 들어가지 않아야 한다.
- 후속 migration 작성자가 실수로 같은 version을 만들거나 병합된 SQL을 수정하면 CI가 실패해야 한다.
- 검증은 H2나 mock이 아니라 PostgreSQL/PostGIS Testcontainers로 해야 한다.

## 최종 결정

D01은 실행 가능한 최소 baseline으로 좁히고, Flyway SQL에는 `NOLOGIN` group role과 권한만 둔다. version/checksum 정책은 registry JSON과 Node CI 테스트로 강제한다.

## 해결 방식

- Gradle에 `flyway-core`, `flyway-database-postgresql`, PostgreSQL runtime 의존성을 추가하고 lockfile을 갱신했다.
- Spring 설정에 runtime datasource env와 Flyway migration user/password env를 분리했다.
- `baselineVersion=0`을 설정해 기존 객체가 있는 DB에서도 `V001`이 건너뛰어지지 않게 했다.
- Testcontainers 테스트를 먼저 추가해 실패를 확인한 뒤 migration SQL과 설정을 구현했다.
- 리뷰에서 나온 보안/정책 결손을 반영해 고정 password를 제거하고, checksum 테스트를 marker 검사에서 SHA-256 검사로 강화했다.
- Issue #67에 실제 comment로 migration 추가 절차와 운영 login role provisioning 기준을 남겼다.

## 결과

- empty migrate와 baseline upgrade가 통과한다.
- runtime role 계열은 DDL을 실행하지 못한다.
- readonly role은 SELECT만 가능하고 INSERT는 거부된다.
- registry에 없는 migration 파일, 중복 version, 파일명/registry version 불일치, SQL 본문 checksum drift가 CI에서 실패한다.
- 업무 table 구현은 D02-D09와 D09/D135 후속 issue 범위로 남겼다.
