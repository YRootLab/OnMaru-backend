# Backend 설계 입력 snapshot 검증 작업 기록

## 날짜

2026-09-14

## 문제 상황

Issue #131의 목표는 `docs/specs`와 `docs/backend_schema_design_guide.md`가 개인 로컬 절대경로에 의존하지 않도록 고정하는 것이었다. 기존에는 두 경로가 각자 개발자 장비의 checkout을 가리키는 symlink라서, 다른 Agent나 GitHub Actions가 같은 backend 설계 입력을 재현할 수 없었다.

자바를 top-down으로 보면 이번 작업의 핵심은 "Spring 코드를 짜기 전, Spring이 따라야 할 요구사항 입력을 CI가 항상 같은 파일로 읽게 만드는 기반 작업"이다. 즉 Java class나 controller 구현보다 위 단계의 입력 안정화다.

## 오류명 또는 실패 증상

- 재현성 실패: 원본 checkout이 없으면 `docs/specs`와 schema guide를 읽을 수 없음.
- 검증 공백: CI가 `test -L docs/specs`처럼 symlink 존재만 확인하고, 개인 절대경로를 가리키는지는 확인하지 못함.
- 변조 감지 공백: snapshot 파일이 바뀌거나 manifest 밖 파일이 추가되어도 초기 구조만으로는 CI 실패를 보장하지 못함.
- secret fixture 위험: snapshot 또는 fixture에 key/token 형태 문자열이 들어와도 자동 차단 장치가 필요했음.

## 기존 구조나 방식의 한계

기존 CI는 repository hygiene 수준이었다.

```bash
test -L docs/backend_schema_design_guide.md
test -L docs/specs
```

이 방식은 "symlink가 있다"만 증명한다. symlink target이 `/Users/...` 같은 개인 경로인지, repo-local snapshot인지, snapshot 파일이 manifest와 같은 내용인지, backend 요구 추출에 필요한 핵심 문서가 빠지지 않았는지는 증명하지 못했다.

## 관련 코드 맥락

- `.github/workflows/ci.yml`
  - 담당 로직: PR과 `develop`/`main` push에서 repository hygiene와 planning input 검증을 실행한다.
  - 변경 이유: CI가 단순 파일 존재 확인에서 실제 검증 스크립트 실행으로 내려가야 했다.
  - 최종 흐름: `node --test scripts/test/*.test.mjs`로 테스트를 돌리고, `node scripts/verify-planning-inputs.mjs`로 현재 repo snapshot 상태를 검증한다.

- `scripts/verify-planning-inputs.mjs`
  - 담당 로직: CLI entrypoint다.
  - 입력: 현재 repository root.
  - 출력: 검증 성공 시 메시지 출력, 실패 시 오류 목록을 stderr에 출력하고 exit code 1.
  - top-down 위치: CI가 직접 호출하는 가장 바깥 경계다.

- `scripts/lib/planning-inputs-verifier.mjs`
  - 담당 로직: 실제 검증 규칙을 함수로 가진다.
  - 핵심 함수: `verifyPlanningInputs(root)`
  - 입력: 검사할 repository root 경로.
  - 출력: `{ ok: boolean, errors: string[] }`
  - 주요 검증:
    - `manifest.json` 존재와 JSON parse 가능 여부
    - manifest entry의 `snapshot_path`, `source_repository`, `source_commit`, `source_path`, `sha256` 필수 여부
    - snapshot 파일의 SHA-256이 manifest와 같은지
    - snapshot 폴더에 manifest 밖 파일이 없는지
    - `docs/backend_schema_design_guide.md`, `docs/specs`가 정확한 repo-local symlink target을 가리키는지
    - backend 요구 추출에 필요한 필수 입력이 manifest에 포함됐는지
    - snapshot과 `docs/contracts/fixtures`에 secret-like 값이 없는지

- `scripts/test/planning-inputs-verifier.test.mjs`
  - 담당 로직: verifier가 실패시켜야 할 회귀 케이스를 임시 repo fixture로 검증한다.
  - 핵심 테스트:
    - 정상 manifest/hash 통과
    - hash 변조 실패
    - provenance 필드 누락 실패
    - 필수 backend planning input 누락 실패
    - 개인 절대경로 symlink 회귀 실패
    - manifest 밖 snapshot 파일 실패
    - secret-like fixture 실패

## 검토한 선택지

1. 기존 symlink를 유지하고 README에만 원본 경로를 기록한다.
   - 장점: 변경이 작다.
   - 한계: checkout 없는 CI와 다른 Agent가 재현할 수 없다.

2. 외부 repository를 CI에서 자동 checkout한다.
   - 장점: 원본과 가까운 흐름이다.
   - 한계: private repo 권한, 네트워크, commit 고정, secret 노출 경계가 복잡해진다.

3. repo-local snapshot과 provenance manifest를 둔다.
   - 장점: clean checkout만으로 읽을 수 있고, hash로 변조를 감지할 수 있다.
   - 한계: 원본이 바뀔 때 수동 갱신 절차가 필요하다.

4. snapshot만 두고 hash 검증은 생략한다.
   - 장점: 구현이 더 단순하다.
   - 한계: 내용 변조와 누락을 CI가 잡지 못해 #131 Acceptance Criteria를 충족하지 못한다.

## 판단 기준

- 원본 checkout 없이 읽을 수 있어야 한다.
- upstream repository, commit, source path, content hash가 남아야 한다.
- CI가 변조, 누락, secret-like fixture를 실패시켜야 한다.
- 후속 backend Issue들이 같은 입력 문서를 기준으로 OpenAPI, DB, Spring 구현을 시작할 수 있어야 한다.
- #131 범위를 넘는 Gradle/Python 전체 CI 확장은 #69로 넘긴다.

## 최종 결정

repo-local snapshot + manifest + verifier + CI 테스트 조합을 선택했다.

이 방향은 Spring/FastAPI 구현 전 단계의 입력 안정화를 작게 끝내면서도, 후속 Java/Spring 작업이 읽는 요구사항 문서의 재현성을 CI에서 보장한다.

## 해결 방식

1. `docs/reference-snapshots/planning-inputs`를 만들고 FE specs와 backend schema guide를 복사했다.
2. `manifest.json`에 각 파일의 원본 repository, commit, source path, SHA-256을 기록했다.
3. 기존 개인 절대경로 symlink를 repo-local 상대 symlink로 바꿨다.
   - `docs/backend_schema_design_guide.md -> reference-snapshots/planning-inputs/backend_schema_design_guide.md`
   - `docs/specs -> reference-snapshots/planning-inputs/specs`
4. `verifyPlanningInputs(root)`를 추가했다.
   - 파일 해시가 바뀌면 `sha256 mismatch`로 실패한다.
   - manifest 밖 파일이 생기면 `not listed in manifest`로 실패한다.
   - symlink가 개인 절대경로로 돌아가면 target mismatch로 실패한다.
   - 필수 backend 입력이 빠지면 `required planning input is missing`으로 실패한다.
   - secret-like 문자열이 발견되면 `contains a secret-like value`로 실패한다.
5. CI에 Node test와 verifier 실행을 연결했다.
6. PR #142 본문에는 `Refs #131`을 사용했다. repository default branch가 `main`이라 `develop` 대상 PR에서는 GitHub auto-close가 잡히지 않기 때문이다. merge 후 AC 확인 뒤 #131은 수동 close한다.

## 남은 과제

- PR #142를 `develop`에 merge한 뒤 #131 Acceptance Criteria를 다시 확인하고 이슈를 수동 close한다.
- Gradle, Python lint/test, OpenAPI, JSON Schema, DBML 검증을 GitHub Actions에 상시 확장하는 일은 #131이 아니라 #69의 범위다.
- Java top-down 학습 관점에서는 다음 순서로 보면 좋다.
  1. CI가 어떤 명령을 호출하는가: `.github/workflows/ci.yml`
  2. CLI entrypoint가 어떤 library 함수를 호출하는가: `scripts/verify-planning-inputs.mjs`
  3. library가 어떤 입력을 검증하고 어떤 오류를 반환하는가: `verifyPlanningInputs(root)`
  4. 테스트가 어떤 회귀를 실패시키는가: `scripts/test/planning-inputs-verifier.test.mjs`
  5. 이후 Spring 구현에서는 같은 방식으로 Controller -> Service -> Repository 순서로 책임을 내려가며 읽으면 된다.
