# D09 insights observations schema worklog

## 날짜

2026-09-15

## 문제 상황

방문자 수와 관광지 집중률은 실시간 혼잡도나 OnMaru 사용자 수가 아니라 원천 제공자가 산출한 날짜·공간 단위 관측값이다. Issue #135는 이 데이터를 provenance, basis date, region/target FK, metric unit과 함께 저장할 executable Flyway schema를 만드는 작업이다.

## 오류명 또는 실패 증상

TDD 첫 실행에서 `InsightsMigrationTests`가 실패했다.

- `insights_visitor_observations`, `insights_tourism_targets`, `insights_target_place_links`, `insights_concentration_observations` 테이블이 없어 테이블 존재 검증이 0건을 반환했다.
- fixture insert는 `PSQLException`으로 실패했다.

## 기존 구조나 방식의 한계

`docs/database/modules/insights.dbml`과 `docs/spring/catalog-ingestion.md`에는 insights logical schema가 있었지만, 실제 Flyway migration에는 반영되지 않았다. 이 상태에서는 #90 DataLab adapter나 #138 public heatmap API가 값의 단위와 결측 의미를 DB에서 보호받지 못한다. 특히 결측을 0으로 저장하거나, 100을 초과하는 congestion score를 저장하는 실수를 schema 단계에서 막을 필요가 있었다.

## 관련 코드 맥락

- `apps/spring-api/src/main/resources/db/migration/baseline/V005__d09_insights_observations_schema.sql`
  - visitor observation은 `(revision_id, region_id, basis_date, visitor_type)`를 PK로 삼고 `catalog_dataset_revisions`, `catalog_regions`를 FK로 참조한다.
  - tourism target은 `(provider, source_target_key)` unique를 강제해 같은 원천 대상이 중복 생성되지 않게 한다.
  - target-place link는 target을 PK로 두어 미해결 target은 link row를 만들지 않는 정책과 맞춘다.
  - concentration observation은 metric/unit 조합과 value range를 함께 검증한다. `CONGESTION_SCORE`는 `score` 단위와 0..100 범위만 허용한다.
- `apps/spring-api/src/test/java/com/yrootlab/onmaru/testing/postgres/InsightsMigrationTests.java`
  - 실제 PostgreSQL/PostGIS 컨테이너에 전체 Flyway migration을 적용한다.
  - 정상 visitor/concentration insert, duplicate target 거부, 음수 visitor count 거부, orphan revision 거부, 잘못된 unit/range 거부를 검증한다.
- `db/migration/registry/migrations.json`
  - V005 checksum과 sha256을 등록해 migration drift를 CI에서 잡는다.

## 검토한 선택지

1. DBML만 유지하고 adapter 구현 때 DDL을 추가한다.
2. unit/range 검증을 application validator로만 처리한다.
3. Flyway migration에서 FK, unique, check constraint를 함께 강제한다.
4. metric별 별도 테이블을 만든다.

## 판단 기준

- #135 acceptance가 FK·unique·range constraint를 migration으로 재현하라고 요구한다.
- 관측값은 public API에서 오해되기 쉬워 단위와 범위를 DB가 방어해야 한다.
- 현재 데이터 규모와 도메인 폭에서는 metric별 별도 테이블보다 하나의 typed observation table과 check constraint가 단순하다.

## 최종 결정

V005 Flyway migration으로 insights 네 테이블을 추가하고, Testcontainers DB contract test로 unit/range/provenance 제약을 고정했다.

## 해결 방식

1. RED: `InsightsMigrationTests`를 먼저 추가해 schema 부재로 실패하는 상태를 확인했다.
2. GREEN: `V005__d09_insights_observations_schema.sql`을 추가해 visitor observations, tourism targets, target-place links, concentration observations를 만들었다.
3. 제약: 음수 visitor count, 빈 provider/source key, 잘못된 spatial level, 잘못된 unit, metric별 range 위반, orphan revision을 DB에서 거부하게 했다.
4. registry/docs: migration registry에 V005 SHA-256을 등록하고 migration/concurrency 문서에 D09 소유권을 추가했다.
