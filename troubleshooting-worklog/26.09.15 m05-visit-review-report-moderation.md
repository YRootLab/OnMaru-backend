# M05 VisitReview 신고·moderation audit 구현

날짜: 2026-09-15

## 문제 상황

Issue #123은 방문 후기 신고와 운영 판정을 권한·감사 기록과 함께 처리하는 작업이었다. 같은 회원의 열린 신고는 중복 생성하지 않고 기존 receipt를 반환해야 하며, 운영 판정은 actor/reason/before/after audit을 남겨야 했다.

## 오류명 또는 실패 증상

- 도메인 테스트 작성 직후 moderation package 타입이 없어 컴파일 실패했다.
- web boundary 첫 실행에서는 `InMemoryReviewReportStore` bean이 없어 Spring context가 실패했다.
- report id를 고정한 테스트는 Spring context의 shared sequence 영향으로 실패했고, operations endpoint는 `/api/` unsafe 요청이라 CSRF 없이 403이 반환됐다.

## 기존 구조나 방식의 한계

VisitReview 작성/좋아요까지는 있었지만 신고와 운영 판정 데이터는 없었다. 신고 수나 판정 사유는 일반 회원에게 숨겨야 하므로 public receipt와 내부 audit 모델을 분리해야 했다.

## 관련 코드 맥락

- `modules/community/.../moderation/VisitReviewModerationService`
  - `report`는 published review만 대상으로 한다.
  - 본인 신고는 `SelfVisitReviewReportException`, 숨김/삭제/없는 review는 `VisitReviewReportNotFoundException`으로 분리한다.
  - `InMemoryReviewReportStore.saveOrFindOpen`으로 같은 review/reporter의 OPEN report를 dedupe한다.
  - `moderate`는 review 상태를 바꾸고 `ModerationAction`에 actor type/ref, previousStatus, nextStatus, reason, createdAt을 기록한다.
- `VisitReviewModerationController`
  - public report endpoint는 session, CSRF, Idempotency-Key를 기존 공통 컴포넌트로 처리한다.
  - operations endpoint는 `X-OnMaru-Operator` 헤더를 operator actor로 사용하고, moderation detail은 public report response에 포함하지 않는다.

## 검토한 선택지

1. 신고 receipt에 reason/detail까지 노출: 일반 회원에게 moderation detail을 숨긴다는 요구와 맞지 않는다.
2. report와 moderation action을 하나의 record로 합치기: 공개 신고 상태와 운영 audit의 생명주기가 달라진다.
3. report store와 audit log를 같은 moderation store 안에서 분리: 현재 in-memory scaffold에서 dedupe와 audit 검증이 단순하다.

## 판단 기준

- public API는 `{schemaVersion, reportId, status}`만 반환해야 한다.
- duplicate open report는 새 row를 만들지 않아야 한다.
- 운영 상태 전환은 before/after와 actor/reason을 잃지 않아야 한다.

## 최종 결정

`modules/community/moderation`에 신고 receipt와 moderation audit 모델을 분리해 구현하고, Spring web boundary는 public report와 operator transition을 얇게 연결했다.

## 해결 방식

- `VisitReviewModerationServiceTests`로 중복 open report dedupe, self-report, invalid reason, hidden review 404, audit 기록을 먼저 작성했다.
- `VisitReviewModerationWebBoundaryTests`로 `POST /api/v1/visit-reviews/{id}/reports`와 `POST /api/v1/operations/moderation/visit-reviews/{id}`를 검증했다.
- 테스트는 생성 id를 응답에서 캡처해 sequence 순서에 의존하지 않도록 바꿨다.
- operations endpoint도 CSRF 필터 대상이므로 테스트에 CSRF cookie/header를 명시했다.

## 결과

- targeted moderation domain/web boundary 테스트가 통과했다.
- #139 moderation queue·operator drill 작업에서 재사용할 기본 report/audit 모델이 생겼다.
