# 인증·회원·SavedResource 계약 fixture TDD 작업 기록

- 날짜: 2026-09-14
- 관련 이슈: #132 `[F09] 인증·회원·SavedResource OpenAPI·fixture 동결`
- 관련 PR: #149

## 문제 상황

`docs/contracts/rest-api.md`에는 session, CSRF, 회원 lifecycle, 개인 저장 API가
prose로 정의돼 있었지만, 구현 전 Spring/FE가 함께 실행할 수 있는 기계 판독 계약이
없었다. 특히 `auth/csrf`, Kakao login/callback/logout, `members/me`,
PLACE/ODII_STORY 저장, saved-resource 목록, 월간 timeline을 OpenAPI와 fixture로
고정해야 했다.

## 오류명 또는 실패 증상

- 초기 RED: `validate-identity-saved-contract.py` 실행 시
  `missing OpenAPI contract: docs/contracts/openapi/identity-saved.openapi.yaml`
- 리뷰 후 RED: Kakao callback fixture의 `state` 값이 OpenAPI `minLength: 16`보다
  짧았지만 기존 validator가 fixture request query/header/path를 검증하지 못했다.
- 계약 gap: timeline enum에는 `WROTE_VISIT_REVIEW`가 있었지만 대응 target schema가
  없었고, `subtitle`이 기존 R1/FE handoff보다 좁은 non-null string이었다.

## 기존 구조나 방식의 한계

기존 `scripts/test/validate-r1-contract.py`는 R1 bundle에 특화돼 있었다. F09는
R1 파일을 직접 확장하지 않고 별도 bundle인 `identity-saved`로 분리해야 했기 때문에
필수 path/schema/fixture 목록과 request/response 검증을 새로 정의해야 했다.
또 기존 검증 패턴은 response body JSON Schema 검증에 집중돼 있어서 request query,
header, path parameter fixture가 OpenAPI parameter schema와 맞는지는 놓칠 수 있었다.

## 관련 코드 맥락

- `scripts/test/validate-identity-saved-contract.py`
  - 담당 로직: `identity-saved.openapi.yaml`과 `fixtures/identity-saved/*.json`을
    읽어 OpenAPI 3.1 문서 유효성, 필수 path/schema/fixture 존재, fixture request와
    response schema 매칭을 검증한다.
  - 입력: OpenAPI YAML 1개와 JSON fixture 20개.
  - 출력: 계약이 유효하면 `validated identity-saved contract...` 메시지를 출력하고
    exit 0, 누락·불일치가 있으면 `AssertionError`로 실패한다.
  - 핵심 분기: 성공 fixture는 required request parameter 누락을 실패 처리하고,
    400/401/403/404/409 같은 error fixture는 의도적인 누락 요청을 허용하되 제공된
    query/header/path 값은 OpenAPI schema로 검증한다.

- `docs/contracts/openapi/identity-saved.openapi.yaml`
  - 담당 로직: 인증, 회원, 저장, 월간 timeline의 public REST 계약을 OpenAPI 3.1로
    고정한다.
  - 핵심 결정: 모든 개인 응답은 `Cache-Control: no-store`를 명시하고,
    unsafe method는 `X-CSRF-TOKEN` header parameter를 요구한다. `GET /saved-resources`
    는 `type=PLACE|ODII_STORY`를 필수로 하여 두 resource를 섞어 반환하지 않는다.

- `docs/contracts/fixtures/identity-saved/*.json`
  - 담당 로직: FE/Spring serializer contract test가 사용할 정상·권한·멱등 예제를
    고정한다.
  - 핵심 fixture: redirect/no-store, 회원 조회/탈퇴, PLACE/ODII_STORY PUT/DELETE,
    saved-resource type별 page, timeline, 401/403/404/409 오류 예제.

## 검토한 선택지

1. 기존 `r1.openapi.yaml`에 auth/member까지 합친다.
   - 장점: 검증 스크립트 재사용이 쉽다.
   - 단점: Issue #132가 요구한 별도 touch point와 병렬 안전성을 깨뜨린다.
2. OpenAPI만 추가하고 fixture 검증은 나중에 한다.
   - 단점: acceptance의 “fixture schema 검증 통과”를 만족하지 못한다.
3. 별도 OpenAPI + fixture bundle + validator를 만들고 `verify-contracts`에 연결한다.
   - 장점: F09 범위를 독립적으로 닫고 CI에서 drift를 차단할 수 있다.

## 판단 기준

- Issue #132의 out of scope인 runtime endpoint 구현을 추가하지 않는다.
- rest-api prose의 auth/member/saved endpoint가 기계 계약에서 빠지지 않게 한다.
- 정상, 권한, CSRF, not found, save limit, 멱등 DELETE fixture가 실제 schema 검증을
  통과해야 한다.
- CI가 PR에서 같은 검증을 실행해야 한다.

## 최종 결정

별도 `identity-saved` OpenAPI/fixture bundle을 만들고, 전용 validator를
`scripts/verify-contracts`에 연결했다.

## 해결 방식

1. TDD RED
   - 먼저 `scripts/test/validate-identity-saved-contract.py`를 작성하고 실행해
     OpenAPI 파일 부재 실패를 확인했다.
   - 리뷰 후에는 request parameter 검증을 추가해 callback `state` 길이 위반이
     실제 실패로 드러나는 RED를 다시 만들었다.

2. OpenAPI 계약 작성
   - `auth/csrf`, `auth/kakao/login`, `auth/kakao/callback`, `auth/logout`,
     `members/me`, `saved-resources/places`, `saved-resources/odii-stories`,
     `saved-resources`, `me/timeline` path를 정의했다.
   - `CsrfTokenResponse`, `MemberMe`, `MemberDeletingStatus`,
     `SavedResourceState`, `SavedResourcePage`, `MemberTimeline`, `Error` schema를
     추가했다.

3. Fixture 작성
   - redirect/no-store, 회원 lifecycle, PLACE/ODII_STORY 저장 정상·권한·CSRF·404·409,
     멱등 DELETE, type별 saved-resource page, timeline 정상/401 fixture 20개를 추가했다.

4. 검증 강화
   - fixture response body가 OpenAPI component schema와 맞는지 JSON Schema로 검증한다.
   - fixture request의 query/header/path 값도 operation parameter schema에 맞는지
     검증한다. 이 변경으로 짧은 OAuth `state` fixture 같은 계약 위반을 다시 놓치지 않는다.

## 결과

- `bash scripts/verify-contracts`가 R1 계약, identity-saved 계약, DBML/Azimutt 생성물
  검증을 함께 수행한다.
- PR #149 CI `verify`는 최초 생성 시 통과했고, 이후 `develop` 병합 충돌은
  `handoff.md` 최신 기록을 모두 보존하는 방식으로 해결했다.
- 이 이슈에서 runtime endpoint 구현은 아직 하지 않는다. #132 범위는 구현 전 계약
  동결이며, 실제 endpoint 구현은 #86, #93, #108, #113, #126 등이 소비한다.
