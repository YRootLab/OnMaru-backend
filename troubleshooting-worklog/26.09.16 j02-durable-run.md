# J02 Durable run 상태 머신과 command idempotency

## 작업 배경

- 관련 Issue: #109 `[J02] Durable run 상태 머신·command idempotency 구현`
- blocked-by #101이 Closed이고 담당자와 열린 중복 PR이 없음을 확인한 뒤 `feature/109-durable-run`에서 작업했다.
- AI 호출, worker orchestration, SSE, deadline sweeper는 후속 Issue 범위다.

## 구현 경계

- `modules/journey/run`이 `QUEUED -> RUNNING -> terminal` 상태, stage 순서, command envelope와 persistence port를 소유한다.
- `adapters/persistence-jdbc`는 run mutation과 immutable command receipt를 같은 PostgreSQL transaction에서 commit한다.
- command 단위 transaction advisory lock 뒤 actor/operation/key receipt를 조회한다. 같은 request hash는 저장 결과를 replay하고 다른 hash는 conflict로 rollback한다.
- claim은 status와 generation, stage는 status·generation·expected stage, terminal은 active status와 generation을 조건으로 갱신한다.
- V006의 partial unique index가 exploration과 actor별 active run 하나를 최종 강제한다. cancel/complete race는 한 terminal update만 성공하고 후발 FINISH command는 확정된 terminal receipt를 저장해 재시도 응답을 안정화한다.
- 조회는 새 adapter instance에서도 `discovery_runs` snapshot을 다시 읽으며 메모리 상태를 정답으로 사용하지 않는다.

## Migration

- V009에 `discovery_run_commands`와 operation/stage/generation/expiry 제약을 추가했다.
- 기존 V006은 FAILED/CANCELLED에도 non-null outcome을 요구했다. V009는 그 값을 `error_code`로 옮긴 뒤 canonical terminal outcome 제약을 검증해 기존 reason을 잃지 않는다.
- `docs/database/modules/discovery.dbml`, migration registry, schema 안내와 Azimutt 산출물을 함께 갱신했다.

## TDD와 동시성 검증

1. stage skip과 non-terminal finish를 거절하는 module RED를 먼저 추가했다.
2. 실제 PostgreSQL Testcontainers에서 create/claim/stage/complete와 DB snapshot 복구를 고정했다.
3. 두 thread가 같은 command를 동시에 보내도 효과는 한 번이고 다른 호출은 replay임을 확인했다.
4. 같은 key의 다른 payload, 두 active run, stale generation/stage를 conflict로 고정했다.
5. cancel과 complete를 동시에 실행해 terminal 하나만 남고 후발 FINISH도 확정된 terminal receipt를 반환하는지 확인했다.
6. V008 terminal row를 만든 뒤 V009로 올리는 upgrade 회귀 테스트로 legacy reason 보존을 확인했다.
