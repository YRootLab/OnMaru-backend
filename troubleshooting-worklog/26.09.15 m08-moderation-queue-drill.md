# M08 보호된 moderation queue·operator drill 구현

날짜: 2026-09-15

## 문제 상황

Issue #139는 M05에서 만든 신고·moderation command 위에 운영 전용 queue, 인증, SLA projection과 반복 가능한 synthetic drill을 추가하는 작업이다. 기존 operations POST는 `X-OnMaru-Operator` 헤더 존재만 확인해 bearer credential 없이 상태를 바꿀 수 있었고, open report를 한 번에 triage할 내부 조회 경계도 없었다.

## 오류명 또는 실패 증상

- Queue 도메인 테스트를 먼저 추가했을 때 projection 타입, PII system hide, `FALSE_POSITIVE` reason이 없어 컴파일 RED가 발생했다.
- Operator 인증 테스트를 먼저 추가했을 때 authenticator와 401/403 예외 타입이 없어 컴파일 RED가 발생했다.
- Synthetic 통합 테스트는 `testing/e2e/moderation/operator-drill.json`이 없는 상태에서 `NoSuchFileException`으로 RED가 발생했다.
- Spring 전체 테스트에서 새 production package가 `operations -> web -> operations` 순환을 만들어 `ModuleBoundaryArchUnitTests.productionModulesStayAcyclic`가 실패했다.
- 독립 review에서 공개 상태의 표준 신고를 dismiss할 수 없는 same-status 제한, 신고 없는 system PII hide의 queue 누락, report/disposition/snapshot 경쟁, correlation header를 통한 telemetry 민감값 주입, 장소별 public/cache 검증 누락을 Important로 확인했다.

## 기존 구조나 방식의 한계

M05는 report dedupe와 audit action을 제공했지만 queue priority, oldest age, SLA target, report disposition이 없었다. Operator actor 헤더는 감사 주체를 나타낼 뿐 인증 수단이 아닌데도 기존 endpoint가 이를 접근 권한처럼 사용했다. 또한 문서에 요구된 신고·hide·restore·remove 흐름을 한 번에 재현하는 검증이 없어 public exclusion과 telemetry privacy의 회귀를 잡기 어려웠다.

## 관련 코드 맥락

- `modules/community/.../moderation/ModerationQueueService`: open report를 review별로 묶고 high-risk 우선순위, 24/72시간 SLA, age, overdue를 계산한다.
- `VisitReviewModerationService`: system PII hide는 report를 open으로 유지하고, operator 복원은 `DISMISSED`, 숨김·삭제는 `RESOLVED`로 전환한다.
- `apps/spring-api/.../web/moderation/queue/OperatorAuthenticator`: `SecretProvider`의 `moderation.operator-token`과 actor 헤더를 함께 검증한다.
- `SecretBundle.matches`: current와 previous 값을 SHA-256 고정 길이 digest로 만든 뒤 `MessageDigest.isEqual`을 non-short-circuit로 실행한다.
- `ModerationOperatorDrillTests`: public report, protected queue, 내부 system hide, protected disposition, public query, audit와 telemetry를 한 흐름으로 검증한다.
- `InMemoryReviewReportStore.executeAtomically`: JDBC 밖의 현재 scaffold에서 report, system/operator action, report close, queue snapshot을 직렬화하는 coordinator 경계다.

## 검토한 선택지

1. Actor 헤더만 계속 신뢰: caller가 임의 actor를 만들 수 있어 인증과 감사가 모두 무의미하다.
2. 별도 관리자 session/UI 도입: Issue #139 범위를 넘어 일반 공개 관리자 UI와 workflow engine까지 확장된다.
3. 기존 `SecretProvider` token rotation과 actor 헤더 조합: 현재 secret lifecycle을 재사용하면서 접근 권한과 감사 주체를 분리할 수 있다.
4. Queue를 `operations` top-level package에 배치: 기존 `web` package가 operations admission을 사용하므로 web error DTO를 참조하는 순간 module cycle이 생긴다.
5. Queue HTTP boundary를 `web.moderation.queue`에 배치: controller/authenticator가 같은 web adapter 안에 있고 community domain만 아래 방향으로 참조한다.

## 최종 결정

3번 인증 방식과 5번 package 경계를 채택했다. JDBC repository나 관리자 UI를 만들지 않고 in-memory runtime scaffold의 기존 command/store를 재사용한다. Queue response는 reporter ID를 모델에 포함하지 않으며 `Cache-Control: no-store`로 반환한다.

## 해결 방식

- Queue projection record와 service를 추가하고 `PERSONAL_DATA` 또는 system PII action은 24시간, 나머지는 72시간으로 정렬했다.
- Current/previous token을 constant-time 비교하고 missing credential/actor는 401, malformed/invalid credential은 403으로 분리했다.
- `moderation.operator-token`을 기본 필수 secret에 넣어 environment 설정 누락 시 startup이 실패하도록 했다.
- 기존 moderation POST도 같은 authenticator를 사용해 actor-header-only 호출을 차단했다.
- 다섯 report reason, duplicate, PII hide, false-positive restore, confirmed remove, audit/report status, public exclusion, telemetry 비노출을 synthetic fixture로 고정했다.
- 전체 Spring test에서 발견된 module cycle은 queue/auth HTTP 코드를 `web.moderation.queue`로 이동해 해소했다.
- Review 보완으로 `PUBLISHED/FALSE_POSITIVE`와 이미 숨겨진 system PII 확인 판정을 same-status audit disposition으로 허용했다. Unresolved system PII audit 자체도 24시간 queue item이 되며, 같은 timestamp에서는 UUID가 아니라 audit append order로 마지막 판정을 결정한다.
- In-memory moderation command와 queue snapshot을 report store의 단일 coordinator lock으로 묶고 latch 기반 경쟁 테스트로 late OPEN report와 중간 snapshot을 방지했다.
- 공격자 제어 correlation header는 bounded `req-*`, `run-*`, `rev-*` 형식만 수용하고 나머지는 생성값 또는 `unknown`으로 치환한다. Drill은 fixture의 민감값을 해당 header에도 주입해 telemetry 비노출을 검증한다.
- Drill은 세 표준 신고까지 false positive로 종결해 잔여 OPEN 0건을 확인하고, global과 place별 public query 모두에서 `HIDDEN`/`REMOVED` text 배제와 `Cache-Control: no-store`를 확인한다.

## 결과

- Focused community moderation test와 Spring authentication/web/drill test가 통과했다.
- Synthetic drill은 previous token 복원과 current token 삭제를 모두 검증하며 reporter UUID, review text, report detail, actor ref, token이 HTTP telemetry attribute에 없음을 확인한다.
- 운영 절차는 `docs/operations/runbooks/moderation.md`에 queue 조회, SLA, alert 대응, 판정, audit/public 검증, token rotation 순으로 기록했다.
- 독립 review의 Critical finding은 없었고 Important 5건은 focused moderation/observability test로 보완했다.
