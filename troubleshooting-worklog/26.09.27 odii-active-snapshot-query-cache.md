# ODII 상세 조회의 전체 snapshot 반복 로드와 502·503 완화

- 날짜: 2026-09-27
- 관련 Issue: #454
- 작업 브랜치: `fix/454-production-api-latency`
- 대상 서비스: Render Spring API production

## 문제 상황

운영 프론트엔드의 소리마루 화면은 백엔드의 ODII 목록과 상세 API를 사용한다. 화면 진입 시 목록 응답의 각 항목에 대해 상세 API를 추가 호출하는 프론트엔드 N+1 호출이 있었고, 한 번의 화면 진입만으로 상세 요청이 수십 건 동시에 발생했다. 이때 Render 백엔드는 응답 지연, 502, 503을 반복했고 프론트엔드는 10초 timeout 또는 빈 배열 fallback 때문에 데이터가 없는 화면을 표시했다.

백엔드에서 더 큰 문제는 상세 ID 하나를 조회하는 요청도 활성 ODII revision의 전체 데이터를 먼저 읽는 구조였다는 점이다. 운영 활성 revision에는 약 6,205개의 ODII story와 각 story의 script·subtitle line이 포함되어 있다. 따라서 상세 요청 42건이 동시에 들어오면, 요청마다 같은 전체 snapshot을 PostgreSQL에서 읽고 Java 객체와 공개 조회 projection으로 변환하려고 했다.

여기서 “다시 적재한다”는 표현은 DB에 데이터를 INSERT하거나 동일 데이터를 중복 저장한다는 뜻이 아니다. 정확히는 이미 DB에 저장된 활성 revision 전체를 `SELECT`하고, 조회 결과를 매 요청마다 JVM heap의 객체 그래프로 다시 구성한다는 뜻이다. DB 사용량 자체가 요청 수만큼 영구 증가하는 것은 아니지만, 쿼리·네트워크 전송·객체 생성·GC 비용이 동시에 반복된다.

## 오류명 또는 실패 증상

- 운영 Spring API의 502/503 응답 및 Render 프로세스 불안정
- `/api/v1/home/popular-sounds` 응답이 약 6~12초까지 지연
- 일부 ODII/region 요청이 프론트엔드 공통 timeout 10초를 초과
- 소리마루 목록과 지역별 섹션이 `0건` 또는 skeleton 상태에 머무름
- 같은 활성 revision인데도 상세·목록·지역 집계 요청마다 전체 story와 subtitle 조회가 반복됨

502/503과 메모리 한도 초과의 직접 인과를 확정하려면 당시 프로세스의 heap dump 또는 OOM 로그가 필요하다. 이번 조사에서는 그 자료를 확보하지 못했다. 다만 운영 증상, Render의 제한된 JVM heap, 프론트엔드의 동시 fan-out, 그리고 아래 코드 경로에서 확인한 전체 snapshot 반복 생성이 일치하므로 가장 직접적인 백엔드 부하 원인으로 판단했다. 문서에서는 확인된 코드 사실과 운영 장애에 대한 추론을 구분한다.

## 정상 기대 동작

ODII 데이터는 immutable revision으로 발행된다. 같은 active revision ID가 유지되는 동안 story, spot, subtitle 내용도 바뀌지 않는다. 그러므로 같은 revision의 공개 조회 projection은 요청마다 다시 생성할 필요가 없다.

정상적인 흐름은 다음과 같아야 한다.

1. 첫 요청은 현재 active revision ID를 확인한다.
2. 해당 revision의 snapshot이 프로세스 캐시에 없으면 DB에서 한 번 읽고 projection을 만든다.
3. 같은 revision을 사용하는 이후 요청은 동일한 immutable projection을 재사용한다.
4. sync가 새 revision을 publish하여 active revision ID가 바뀌면 새 snapshot을 한 번 읽는다.
5. 실패한 새 snapshot을 기존 캐시 위에 덮어쓰지 않는다.
6. 서버가 재시작되면 프로세스 메모리 캐시가 사라지므로 최초 요청에서 한 번 다시 구성한다.

## 기존 요청 경로

### 웹 경계

`apps/spring-api/src/main/java/com/yrootlab/onmaru/web/audio/OdiiStoryController.java`의 상세 endpoint는 `GET /api/v1/odii/stories/{storyId}`를 받아 `OdiiStoryQueryService.detail()`에 전달한다. Controller 자체는 전체 데이터를 읽지 않는다. 병목은 application query와 persistence adapter 사이의 계약에서 발생했다.

### application query

`modules/audio/src/main/java/com/yrootlab/onmaru/audio/query/OdiiStoryQueryService.java`의 `detail()`은 story ID와 language를 검증한 뒤 다음 순서로 처리한다.

1. `store.activeSnapshot()` 호출
2. 반환된 `snapshot.stories()` 전체 stream 순회
3. 요청한 `storyId`와 같은 projection 필터링
4. 공개·재생 가능 상태 필터링
5. 언어 선택 및 fallback
6. 상세 DTO 생성

즉 `storyId`가 하나여도 query store 계약은 `OdiiActiveSnapshot` 전체를 요구한다. 동일 store는 목록, 검색, 주변 이야기, 추천, 지역별 개수, 저장 항목 조회에서도 사용된다. 따라서 소리마루 여러 섹션이 동시에 로딩되면 같은 전체 데이터 접근이 겹친다.

### 운영 persistence adapter

`apps/spring-api/src/main/java/com/yrootlab/onmaru/tourism/audio/JdbcAudioRevisionStore.java`의 `activePublishedRevision()`은 repeatable-read transaction에서 현재 active revision ID를 구하고 `loadSnapshot()`을 실행한다.

`loadSnapshot()`은 다음 데이터를 읽는다.

1. `audio_spot_versions`와 `audio_odii_spots`를 join하여 활성 revision의 모든 spot 조회
2. `audio_subtitle_lines`에서 활성 revision의 모든 subtitle line 조회
3. `audio_story_versions`와 `audio_odii_stories`를 join하여 활성 revision의 모든 story 조회
4. spot ID, story ID, subtitle line을 Java `Map`과 `List`로 조립
5. `AudioRevisionSnapshot` 생성

그 뒤 `ActiveRevisionOdiiStoryQueryStore`가 모든 story를 다시 `OdiiStoryProjection`으로 변환한다. 이 과정에는 공개 ID 생성, 좌표와 지역 metadata 계산, subtitle을 `OdiiTranscriptLine`으로 변환하는 작업이 포함된다.

## 원인 분석

### 원인 1: immutable revision의 성질을 조회 경계에서 활용하지 못함

데이터 발행 계층은 revision을 immutable snapshot으로 관리했지만 public query store는 이 사실을 이용하지 않았다. 모든 API 요청이 `activePublishedRevision()`을 직접 호출하여 같은 revision을 매번 materialize했다. 쓰기 모델은 revision 단위였지만 읽기 모델의 수명이 HTTP request 단위로 축소되어 있었다.

### 원인 2: 상세 조회와 전체 snapshot 계약의 결합

상세 API는 하나의 story를 반환하지만 `OdiiStoryQueryStore`는 전체 snapshot만 제공한다. 당장 store 계약을 story별 SQL로 전면 교체하지 않는 한 전체 데이터 한 번의 로드는 필요하다. 문제는 그 비용이 요청마다 발생했다는 것이다. 전체 snapshot을 프로세스 수준에서 재사용하면 현재 계약을 유지하면서 반복 비용을 제거할 수 있다.

### 원인 3: 프론트엔드 fan-out이 백엔드 비효율을 증폭

프론트엔드의 기존 adapter는 목록 summary를 받은 뒤 각 카드의 `audioUrl`을 얻기 위해 상세 API를 `Promise.all`로 호출했다. 첫 화면의 두 데이터 경로만 합쳐도 목록 2회와 상세 42회가 발생했다. 백엔드가 요청마다 전체 snapshot을 읽는 구조와 결합되면서 단일 사용자의 화면 진입이 대량 동시 materialization으로 확대됐다.

이 문제는 한쪽만 수정해서 완전히 끝나지 않는다. 백엔드는 정상적인 다중 요청을 견디도록 동일 revision을 재사용해야 하고, 프론트엔드는 카드 목록을 summary page로 렌더링한 뒤 실제 재생 시점에 상세 하나만 조회해야 한다.

## 검토한 선택지

### 선택지 1: 프론트엔드 요청 수만 줄이고 백엔드는 유지

프론트의 42개 상세 호출을 제거하면 즉시 부하는 크게 감소한다. 하지만 상세, 목록, region endpoint 각각이 여전히 같은 전체 snapshot을 다시 읽는다. 다른 클라이언트나 새 화면이 fan-out을 만들면 같은 장애가 재발하므로 백엔드 해결책으로는 불충분하다.

### 선택지 2: 모든 query를 story별·목록별 전용 SQL로 즉시 재설계

장기적으로는 목록 projection, 상세 projection, region aggregate를 PostgreSQL에서 직접 읽는 read model이 메모리 효율 면에서 가장 좋다. 그러나 cursor, 언어 fallback, 공개 URL 정책, 지역 metadata, content tag, saved state 등 기존 query 규칙을 모두 SQL/adapter 경계로 옮겨야 한다. 마감 직전의 긴급 수정으로는 회귀 범위가 너무 크다.

### 선택지 3: HTTP response cache 적용

endpoint별 응답 캐시는 같은 URL의 반복 요청에는 유효하지만 member별 saved state, query parameter, cursor가 섞이면 cache key가 복잡해진다. 또한 목록·상세·지역 endpoint가 각각 같은 원본 snapshot을 별도로 가질 수 있어 핵심 중복을 가장 낮은 계층에서 제거하지 못한다.

### 선택지 4: Redis에 전체 snapshot 저장

Redis를 추가하면 외부 네트워크 왕복과 직렬화 비용이 생기고, 현재 장애 원인 해결을 위해 별도 인프라와 eviction 정책을 도입하게 된다. active revision ID가 이미 명확한 cache key이므로 단일 Render 인스턴스에서는 JVM local cache가 더 단순하다. Render 프로세스가 여러 개로 늘어나더라도 각 인스턴스가 revision당 한 번만 로드하면 정합성에 문제가 없다.

### 선택지 5: active revision 단위 immutable JVM cache

기존 API 계약과 projection 규칙을 유지하면서 가장 큰 반복 비용만 제거한다. 캐시 key가 revision ID 하나라 invalidation 조건이 명확하고, 새 revision publish를 다음 요청에서 감지할 수 있다. 이번 긴급 수정은 이 방법을 선택했다.

## 판단 기준

- 동일 revision에서 DB 전체 snapshot 조회가 정확히 한 번이어야 한다.
- 새 revision이 publish되면 별도 운영 명령 없이 자동으로 전환되어야 한다.
- 미완료 STAGING revision은 public API에 노출되면 안 된다.
- 캐시 생성 실패가 기존 정상 cache를 파괴하면 안 된다.
- 동시 최초 요청이 각자 전체 snapshot을 로드하는 cache stampede를 막아야 한다.
- member별 saved state 같은 요청별 정보는 snapshot cache에 섞지 않아야 한다.
- Redis나 신규 테이블 없이 현재 릴리즈에 안전하게 포함할 수 있어야 한다.

## 최종 결정

`ActiveRevisionOdiiStoryQueryStore`가 active revision ID와 변환 완료된 `OdiiActiveSnapshot`을 한 쌍으로 캐시하고, revision ID가 같을 때 동일 객체를 반환하도록 변경했다. cache miss와 revision 변경 시의 전체 로드는 `synchronized` 구간에서 한 번만 실행하며, fast path의 가시성은 `volatile`로 보장한다.

## 해결 방식

### revision ID 기반 cache hit

각 요청은 먼저 `AudioRevisionStore.activeRevision(dataset)`으로 현재 활성 revision ID 한 행을 확인한다. 캐시에 저장된 revision ID와 같으면 DB의 story·spot·subtitle 전체를 읽지 않고 기존 `OdiiActiveSnapshot`을 반환한다.

요청마다 남아 있는 active revision ID 조회는 전체 6,205건과 subtitle 조회가 아니라 `catalog_active_datasets`의 단일 행 조회다. 새 publish를 즉시 감지하기 위해 이 작은 조회는 유지했다. 추후 측정에서 이 한 행 조회도 병목으로 확인될 때만 짧은 refresh interval 또는 publish event 기반 invalidation을 별도 Issue에서 검토한다.

### cache miss의 단일 로드

캐시가 없거나 revision ID가 다르면 `synchronized (this)`에 진입한다. lock을 기다리는 동안 다른 요청이 snapshot을 이미 구성했을 수 있으므로 lock 안에서 cache를 다시 확인한다. 여전히 miss일 때만 `loadActiveSnapshot()`을 호출한다.

이 double-check 때문에 cold start에 24개의 요청이 동시에 도착해도 첫 요청 하나만 전체 snapshot을 구성하고, 나머지 23개는 구성 완료된 동일 객체를 반환한다. lock은 매 요청에 걸리지 않으며 cache miss 때만 사용된다.

### 안전한 cache publication

`loadActiveSnapshot()`이 정상 완료된 후에만 `cachedSnapshot`을 교체한다. DB 오류, 빈 snapshot, projection 결과 0건 때문에 예외가 발생하면 불완전한 값을 cache하지 않는다. `CachedSnapshot`은 revision ID와 immutable `OdiiActiveSnapshot`을 함께 보관하므로 서로 다른 revision의 ID와 데이터가 섞이지 않는다.

### revision 변경 처리

새 sync가 publish되어 `catalog_active_datasets.revision_id`가 바뀌면 다음 API 요청은 cache miss를 감지한다. 그 요청이 새 published revision을 repeatable-read transaction으로 읽고 projection을 만든 뒤 cache를 원자적으로 교체한다. 이후 요청은 새 revision을 재사용한다.

### 메모리 효과

수정 전에는 동시 요청마다 원본 `AudioRevisionSnapshot`, subtitle map, story list, 변환 중간 객체, 최종 projection이 겹쳐 존재할 수 있었다. 수정 후 정상 상태에서는 변환 완료된 active projection 한 벌만 장기 보존한다. 새 revision 전환 순간에는 기존 cache와 새 snapshot 구성이 잠시 공존할 수 있지만, 교체 후 기존 객체는 진행 중 요청이 끝나는 대로 GC 대상이 된다.

이 수정은 “전체 데이터를 메모리에 절대 올리지 않는다”는 변경은 아니다. 현재 query 계약상 active projection 한 벌은 JVM에 유지한다. 제거한 것은 같은 immutable 데이터의 요청별 반복 조회와 반복 객체화다. 더 낮은 상주 메모리가 필요하면 목록/상세/region 전용 SQL read model로 분리하는 후속 설계가 필요하다.

## 회귀 테스트

`ActiveRevisionOdiiStoryQueryStoreTests`에 다음 동작을 고정했다.

1. 동일 revision을 두 번 조회하면 반환 snapshot이 같은 객체이고 전체 snapshot load count가 1인지 검증
2. active revision ID가 바뀌면 새 snapshot을 다시 읽고 새 title을 반환하는지 검증
3. cold cache에 24개 요청을 동시에 시작해도 모든 요청이 같은 snapshot 객체를 받고 전체 snapshot load count가 1인지 검증

동시성 테스트는 24개 worker가 `CountDownLatch`에서 함께 출발하도록 구성했다. 단순 순차 호출로는 `synchronized` 내부 double-check가 빠졌을 때 발생하는 cache stampede를 잡을 수 없기 때문이다. count 자체도 `AtomicInteger`를 사용하여 test double의 경쟁 조건이 결과를 왜곡하지 않게 했다.

- 명령: `./gradlew :modules:audio:test --tests 'com.yrootlab.onmaru.audio.query.ActiveRevisionOdiiStoryQueryStoreTests.loadsTheSnapshotOnlyOnceWhenConcurrentRequestsArriveOnAColdCache' --no-daemon`

운영 성능은 아직 이 브랜치가 production에 배포되지 않았으므로 개선 완료로 단정하지 않는다. 로컬 테스트는 load 횟수와 invalidation 계약을 검증한 것이며, 실제 Render latency·heap·503 해소는 배포 후 별도 smoke와 관측으로 확인해야 한다.

3. production 배포 완료와 health endpoint 정상 상태를 확인한다.
4. cold start 직후 ODII 목록 API를 한 번 호출하고 최초 응답 시간을 기록한다.
5. 동일 목록·상세·regions 요청을 반복하여 warm response 시간을 기록한다.
6. 12~24개 동시 요청에서 502/503, JVM 재시작, DB connection 고갈 여부를 확인한다.
7. Render memory graph에서 순간 peak와 배포 전 peak를 비교한다.
8. 새 ODII revision을 publish한 뒤 응답 revision과 데이터가 자동으로 전환되는지 확인한다.
9. Vercel Network 탭에서 초기 화면 상세 fan-out이 제거되었는지 별도로 확인한다.

## 프론트엔드와의 책임 경계

백엔드 cache가 적용되어도 프론트엔드가 42개의 상세 요청을 보내는 구조가 정당화되지는 않는다. 각 요청에는 HTTP parsing, 인증/세션 확인, saved state 조회, 응답 직렬화 비용이 남는다. 따라서 목록 카드 렌더링은 `/api/v1/odii/stories` summary page 한 번으로 처리하고, 상세와 audio URL은 사용자가 카드를 선택하거나 재생할 때 한 번만 요청해야 한다.

백엔드 수정은 비정상적인 요청 증폭이 들어와도 동일 원본을 반복 materialize하지 않게 방어한다. 프론트엔드 수정은 불필요한 요청 자체를 제거한다. 두 변경은 대체 관계가 아니라 서로 다른 계층의 필수 수정이다.

## 남은 과제

- production 배포 후 실제 P50/P95 latency와 memory peak 기록
- `activeRevision()` 단일 행 조회 횟수를 metric으로 노출할지 검토
- active snapshot load 성공·실패·revision 교체 횟수 관측 추가
- 상세 조회가 전체 list를 선형 탐색하는 비용을 story ID index 또는 전용 read query로 줄이는 후속 개선
- 목록, region aggregate, 상세를 각 용도에 맞는 PostgreSQL read model로 분리할지 부하 시험 후 결정
- 프론트엔드의 list-summary/detail-lazy-load 전환과 요청 수 회귀 테스트

## 결과

동일 active revision에 대한 전체 ODII snapshot과 subtitle의 DB 조회·projection 변환은 이제 HTTP 요청마다 수행되지 않는다. 프로세스 cold start 또는 새 revision publish 시 한 번 수행되고, 그 외 요청은 revision ID가 같은 동안 immutable snapshot을 재사용한다. 동시 cold-cache 요청에서도 전체 load가 한 번만 발생한다는 테스트를 추가했다.

다만 이 결과는 아직 브랜치 코드와 로컬 검증 단계다. production 장애가 해결됐다고 말하려면 Git Flow를 통한 병합·배포와 Render 운영 측정이 남아 있다. 또한 프론트엔드의 카드별 상세 42회 호출은 별도 프론트 수정으로 제거해야 한다.
