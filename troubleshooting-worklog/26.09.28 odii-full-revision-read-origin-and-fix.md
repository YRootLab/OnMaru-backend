# 왜 오디오 한 건을 찾는데 전체 리비전을 읽었고, 어떻게 필요한 데이터만 조회하게 바꿨는가

- 날짜: 2026-09-28
- 관련 Issue: #454
- 대상: 소리마루 목록·상세·검색·추천·주변·인기 오디오 조회

## 문제 상황

온마루의 소리마루 API는 PostgreSQL에 저장된 한국관광공사 ODII 데이터를 사용한다. 그런데 예전 조회 구조에서는 오디오 카드 12개를 보여주거나 상세 한 건을 여는 요청도 먼저 활성 리비전의 story 6,205건, spot 2,095건, 자막 6,069줄을 데이터베이스에서 읽었다. 이 데이터를 Java 객체로 모두 조립한 다음에야 “최신 12건”, “이 ID 한 건”, “이 검색어와 일치하는 20건”을 골랐다.

비유하면 도서관에서 책 한 권을 빌리려는 사람에게 사서가 서가의 책을 전부 카트에 담아 가져온 뒤 그중 한 권을 찾아 주는 방식이었다. 책이 적고 손님이 한 명일 때는 동작한다. 하지만 책이 수천 권이고 여러 사람이 동시에 요청하면 카트를 만드는 일 자체가 업무의 대부분이 된다. PostgreSQL은 원하는 책의 위치를 바로 찾을 수 있는 도서 검색 시스템인데, 당시 코드는 검색을 데이터베이스에 맡기지 않고 모든 책을 Java 쪽으로 옮긴 뒤 찾고 있었다.

## 실패 증상

- 홈의 `/api/v1/home/popular-sounds`가 약 6.4~12.2초 걸렸다.
- 프론트엔드의 공통 10초 timeout을 넘긴 요청은 빈 화면이나 skeleton으로 남았다.
- 소리마루에서 카드별 상세 요청이 동시에 발생하면 Render 서버가 502 또는 503으로 불안정해졌다.
- 상세 한 건을 조회해도 활성 revision의 story와 자막 전체를 다시 읽었다.
- 인기 6건을 계산하려고 6,205개 공개 ID를 만든 뒤 재생 수와 저장 수를 각각 조회했다.

당시 502/503의 모든 원인을 하나의 heap dump로 확정한 것은 아니다. 다만 운영 지연, 작은 Render JVM 메모리, 동시에 발생한 상세 요청, 그리고 실제 코드에서 확인된 전체 snapshot 반복 생성이 같은 방향을 가리켰다. PostgreSQL cold read를 측정했을 때 spot 전체가 약 146ms, 자막 전체가 약 936ms, story와 script 전체가 약 1,228ms였다. 애플리케이션으로 전송하고 Java 객체로 만드는 시간도 넣기 전인데 DB 작업만 합계 약 2.31초였다.

## 먼저 알아야 할 리비전의 뜻

여기서 리비전은 “매 요청마다 서버로 보내야 하는 데이터 꾸러미”가 아니다. 공공데이터를 새로 동기화할 때 중간 상태가 사용자에게 보이지 않게 하는 게시 단위다. 예를 들어 새벽 동기화가 6,205건 중 3,000건까지 저장된 순간에 사용자가 조회하면 절반만 보일 수 있다. 그래서 새 데이터는 staging revision에 모두 적재하고 검증이 끝났을 때 active pointer를 새 revision으로 한 번에 바꾼다. 사용자는 언제나 직전 완성본이나 새 완성본 중 하나만 보게 된다.

리비전 자체는 옳은 설계다. 문제는 “어느 완성본을 볼 것인가”를 정하는 리비전 개념과 “그 완성본의 모든 내용을 Java에 올린다”는 구현이 하나로 묶였다는 점이다. 활성 리비전 ID만 SQL 조건으로 사용해도 동일한 일관성을 얻을 수 있다. 즉 `WHERE revision_id = 현재_활성_리비전`으로 필요한 행만 찾으면 된다. 리비전을 유지하는 것과 전체 리비전을 전송하는 것은 전혀 다른 문제다.

## 왜 처음에는 전체 snapshot 방식이 만들어졌는가

특정 문서에 “운영에서도 전체 데이터를 매번 읽자”라고 결정한 기록은 발견되지 않았다. 따라서 개발자의 의도를 단정할 수는 없다. 다만 코드의 발전 순서를 보면 왜 이 구조가 자연스럽게 생겼는지는 설명할 수 있다.

첫째, 초기 구현은 메모리 저장소와 동기화 안전성을 중심으로 만들어졌다. `AudioRevisionSnapshot`은 한 revision의 spot과 story를 한 묶음으로 표현한다. `InMemoryAudioRevisionStore`는 이 묶음을 staging하고 publish하는 테스트와 로컬 실행에 편리했다. 한 덩어리를 복사하고 교체하면 “완성된 데이터만 공개한다”는 규칙을 이해하고 검증하기 쉬웠다.

둘째, PostgreSQL 저장소가 추가될 때도 기존 `AudioRevisionStore` 계약을 유지했다. `JdbcAudioRevisionStore.activePublishedRevision()`은 활성 revision ID와 `AudioRevisionSnapshot` 전체를 반환한다. 덕분에 상위 비즈니스 코드는 데이터가 메모리에 있는지 PostgreSQL에 있는지 몰라도 됐다. 이것은 모듈 분리와 초기 기능 완성에는 장점이었다. 하지만 저장 방식만 PostgreSQL로 바뀌고 조회 방식은 여전히 메모리 snapshot 방식을 따라갔다.

셋째, 공개 API에 필요한 가공을 Java에서 하고 있었다. `ActiveRevisionOdiiStoryQueryStore`는 공급자 ID로 공개 UUID를 만들고, 언어 코드를 `ko`에서 `ko-KR`로 바꾸고, 좌표로 지역 metadata를 찾고, 자막을 공개 응답 형태로 변환했다. 이 작업들을 모든 story에 한 번 적용해 `OdiiActiveSnapshot`을 만들면 목록·상세·검색·추천이 같은 결과를 재사용할 수 있었다. 기능 계약을 빠르게 맞추기에는 단순한 길이었다.

넷째, `OdiiStoryQueryService`의 입력 계약도 전체 snapshot이었다. 상세 조회는 story ID 하나를 받았지만 먼저 `store.activeSnapshot()`을 호출한 후 Java stream으로 ID가 같은 항목을 찾았다. 검색은 전체 목록의 문자열을 비교했고, 주변 조회는 모든 좌표의 거리를 계산했으며, 인기는 모든 story ID의 통계를 불러와 정렬했다. 서비스별 SQL이 없으니 새 기능을 추가할 때 Java filter 하나를 더 붙이는 방식이 가장 쉬웠다.

다섯째, 초기 테스트는 정확성과 일관성을 잘 검증했지만 운영과 같은 데이터 크기와 호출 형태를 충분히 드러내지 못했다. 작은 fixture에서는 전체가 세 건이든 열 건이든 즉시 처리된다. 프론트엔드가 카드마다 상세 API를 동시에 요청하는 상황과 384MiB 수준의 Render JVM도 단위 테스트에서는 나타나지 않는다. 데이터가 6천 건으로 채워지고 실제 화면의 동시 요청이 결합된 뒤에야 구조적 비용이 장애로 보였다.

정리하면 처음 설계가 아무 이유 없이 만들어진 것은 아니다. 원자적 게시, 메모리 저장소와 PostgreSQL 저장소의 공통 계약, 빠른 API 기능 개발, 결정론적인 테스트라는 장점이 있었다. 하지만 쓰기와 동기화에 적합한 “전체 snapshot” 모델을 읽기 API에도 그대로 재사용한 것이 문제였다. 개발 초기의 편의가 운영 조회 비용으로 넘어간 것이다.

## 실제로 어떤 코드가 전체를 읽었는가

`apps/spring-api/src/main/java/com/yrootlab/onmaru/tourism/audio/JdbcAudioRevisionStore.java`의 `loadSnapshot()`은 revision ID 하나를 입력받는다. 이름만 보면 안전해 보이지만 내부에서는 그 revision의 spot 전체, 자막 전체, story와 script 전체를 각각 조회한다. 그다음 ID별 `Map`과 `List`를 만들고 story마다 spot과 자막을 연결해 `AudioRevisionSnapshot`을 반환한다. 이 함수는 공공데이터 동기화와 완성본 복원에는 맞지만 카드 목록이나 상세 한 건의 read path로는 너무 큰 단위다.

`modules/audio/src/main/java/com/yrootlab/onmaru/audio/query/ActiveRevisionOdiiStoryQueryStore.java`의 `activeSnapshot()`은 위 snapshot을 받아 모든 story를 다시 공개 `OdiiStoryProjection`으로 변환한다. 공개 ID, 지역, 좌표, 오디오 URL, 이미지 URL, 자막 목록을 포함한 객체를 story 수만큼 만든다. 이후 `OdiiStoryQueryService.detail()`이 그중 ID 하나를 고르므로 선택 작업의 순서가 거꾸로였다.

`OdiiStoryQueryService.popular()`은 더 많은 일을 했다. 전체 snapshot에서 공개 가능한 story를 고르고 6,205개 ID를 만든 뒤 재생 이벤트와 저장 이력을 각각 집계했다. 최종 응답은 몇 건뿐인데 후보 전부를 Java와 DB 사이에서 다루었다. 주변 조회 역시 모든 좌표를 Java로 가져와 거리 공식을 반복 계산했다. PostgreSQL에는 기간 집계와 PostGIS 공간 index가 이미 있었지만 사용하지 않았다.

## 첫 번째 대응인 캐시는 왜 필요했고 왜 최종 해결이 아니었는가

운영 장애가 급했기 때문에 첫 대응은 같은 revision을 요청마다 다시 만드는 일을 멈추는 것이었다. `ActiveRevisionOdiiStoryQueryStore`에 revision 단위 single-flight cache를 추가했다. 현재 active revision ID가 캐시와 같으면 만들어 둔 projection을 재사용하고, 새 revision일 때만 한 번 다시 읽는다. 동시에 여러 요청이 처음 들어와도 동기화 구간에서 한 번만 적재하도록 했다.

이 변경은 같은 전체 snapshot을 42번 동시에 만드는 문제를 빠르게 줄였다. 기존 서비스 계약을 거의 바꾸지 않아 위험도 작았다. 장애 완화를 위한 올바른 중간 조치였다. 그러나 서버가 시작되거나 새 revision이 게시될 때는 여전히 story와 자막 전체를 메모리에 올려야 했다. 검색과 정렬도 여전히 Java가 담당했고 큰 객체 그래프가 JVM에 계속 남았다. 캐시는 비효율을 덜 자주 실행했을 뿐, 비효율 자체를 없애지는 않았다.

## 검토한 해결 방법

1. 서버 메모리를 늘린다. 구현은 쉽지만 같은 전체 조회가 더 큰 서버에서 계속될 뿐이고 비용과 GC 문제를 미룬다.
2. 전체 snapshot cache만 유지한다. 즉시 장애 완화에는 유효하지만 첫 요청과 revision 변경 비용이 남는다.
3. API 응답 전체를 Redis에 저장한다. 반복 응답은 빨라질 수 있지만 검색어·좌표·언어·cursor 조합마다 cache key가 늘고 PostgreSQL의 기능을 중복 구현하게 된다.
4. 별도 검색 서버나 Elasticsearch를 도입한다. 현재 6천 건에는 과하며 운영 복잡도와 저장공간이 더 커진다.
5. PostgreSQL이 활성 revision에서 필요한 행만 고르게 한다. 기존 DB와 revision 모델을 유지하면서 전송량과 Java 객체 수를 근본적으로 줄인다.

판단 기준은 간단했다. 데이터 정합성과 기존 API 응답 형식을 지키고, Neon 저장공간을 크게 늘리지 않으며, Render의 작은 메모리에서도 동시 요청을 견뎌야 했다. 그래서 다섯 번째 방법을 최종 방향으로 선택했고 cache는 아직 SQL화하지 못한 일부 경로의 안전망으로만 남겼다.

## 최종 해결: 리비전은 조건으로 쓰고 결과만 Java에 전달한다

새 `JdbcOdiiStoryReadStore`는 활성 revision을 PostgreSQL 안에서 먼저 선택한다. 기본 목록은 공개 가능한 데이터만 `WHERE`로 거른 뒤 최신순으로 정렬하고 `LIMIT + 1`만 가져온다. 화면이 12개를 요청하면 다음 페이지 존재 여부를 확인할 한 건을 포함해 최대 13개만 Java로 전달한다. 목록에는 script와 자막을 SELECT하지 않는다.

상세는 공개 story ID와 언어 index로 identity 한 건을 찾는다. story와 spot 한 건을 조합한 다음 그 story의 자막만 `(revision_id, story_id, position)` 기본 키로 조회한다. 전체 6,069줄을 읽고 버리는 작업이 사라졌다. 공개 ID는 기존 Java 계산과 같은 generated UUID로 DB에 저장해 기존 프론트엔드 ID를 바꾸지 않았다.

검색과 추천은 제목과 태그 조건, 일치 점수, 정렬, 개수 제한을 SQL에서 처리한다. 주변 조회는 Java가 모든 좌표의 거리를 계산하는 대신 PostGIS의 `ST_DWithin`으로 반경 안의 후보를 찾고 `ST_Distance`로 정렬한다. 인기 조회는 최근 재생과 저장을 PostgreSQL에서 story별로 집계하고 `2 × 재생 수 + 저장 수` 점수를 계산한 뒤 필요한 개수만 반환한다.

같은 요청을 처리하는 중 새 revision이 게시되어 앞뒤 데이터가 섞이는 것도 막았다. read-only `REPEATABLE READ` transaction을 사용해 한 요청 안에서는 같은 DB 시점을 본다. 페이지 cursor에도 revision ID가 들어 있어 다음 페이지를 요청하기 전에 revision이 바뀌면 오래된 cursor로 조용히 섞지 않고 만료 오류를 반환한다.

## 결과

기존 공통 시작점은 story 6,205건, spot 2,095건, 자막 6,069줄로 약 14,369개의 DB 결과 행과 긴 script 문자열이었다. 새 구조에서 목록 12건은 최대 13개 story row, 검색·추천·주변은 최대 50개 row, 인기 홈은 최대 20개 row, 상세는 story 한 건과 그 story의 자막만 읽는다. 목록 기준 story 후보 전송량은 6,205건에서 최대 13건으로 약 99.79% 줄어드는 구조가 됐다.

PostGIS Testcontainers에서 전체 migration을 적용해 목록, 상세, 검색, 주변, 인기 집계를 검증했다. 전체 `./gradlew check :apps:spring-api:bootJar --no-daemon`도 성공했다. 중요한 점은 “6천 건이 많아서 줄였다”가 아니다. PostgreSQL에는 6천 건이 작은 편이다. 결과가 6~20건인 요청에서 필요하지 않은 본문과 자막까지 전부 애플리케이션으로 옮긴 것이 문제였고, 데이터 선택을 잘하는 PostgreSQL에 그 책임을 돌려준 것이 해결이다.

## 남은 과제

지역과 category는 아직 완전히 SQL화되지 않았다. 현재 행정구역 판정 일부가 Java의 `RegionBoundaryStore`에 있고 category도 DB의 명시적인 조회 키로 정리되지 않았기 때문이다. 따라서 `regionCode/category` 필터 목록과 지역 그룹 집계에는 revision cache fallback이 남아 있다. 이것은 숨겨진 완료가 아니라 다음 스키마 작업이다. 향후 spot version에 versioned `region_id`, story에 `category_code`를 저장하면 `WHERE`와 `GROUP BY`로 마지막 fallback도 제거할 수 있다.

결론적으로 리비전 설계가 잘못된 것이 아니다. 동기화용 전체 snapshot 계약을 조회용 계약으로 재사용한 것이 잘못된 경계였다. 이제 리비전은 “어느 완성본을 조회할지”를 정하는 조건으로 남고, 실제 응답에는 SQL이 선택한 최소 데이터만 Java로 전달된다.
