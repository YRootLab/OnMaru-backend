# Production scheduled deploy 3연속 실패 — SSH host key 변경과 일시적 dirty checkout

- 날짜: 2026-11-10 (작성)
- 관련: Issue #819(completed), #822(not planned), PR #817·#820, Runbook `docs/operations/runbooks/ssh-access-hardening.md`

## 문제 상황

`deploy.yml`의 scheduled production deploy가 11-06, 11-07, 11-08(UTC) 3연속 실패했다. 운영 서비스 자체는 계속 정상이었지만 **새 코드가 운영에 3일간 반영되지 않은 상태**가 됐다. 11-10 아침(01:29 UTC) scheduled 실행으로 복구를 확인했다.

## 오류명 / 실패 증상

1. 1차 증상 — `production-preflight`의 "Prepare restricted production SSH" 단계:
   - `Host key verification failed.` / `Process completed with exit code 255`
   - SSH 연결 자체는 성공하나, 저장된 host key가 서버가 제시한 키와 불일치
2. 2차 증상(SSH 복구 후 수동 배포 1회) — `production-deploy` 단계:
   - `Production checkout is dirty` / exit code 1 (이후 미재현, 원인 미특정)
3. 부수 증상(운영자가 시도한 AI 배포 3건):
   - `Error response from daemon: error from registry: permission_denied: read_package`
   - GHCR 타 저장소 패키지 조회 실패 — 본 인시던트와 무관, #807 선행 조건 사항

## 배경과 원인 추적

- 서버(Lightsail, Ubuntu)의 SSH banner가 `OpenSSH_9.6p1 Ubuntu-3ubuntu13.19` → `Ubuntu-3ubuntu13.20`으로 바뀌었고 **ed25519 host key도 교체**됐다. 운영자가 11-06에 서버에서 무엇을 했는지 기록이 없어 근원은 미상(재생성/업그레이드/수동 재생성 후보). SSH banner만 바뀌는 패키지 업그레이드로는 host key가 재생성되지 않는 것이 일반적이라, 인스턴스 재생성 가능성이 있다.
- 배포 구조: `.github/workflows/deploy.yml`의 preflight/deploy 단계는 GitHub environment 변수 `PRODUCTION_SSH_KNOWN_HOSTS`(production), `STAGING_SSH_KNOWN_HOSTS`(staging)를 `~/.ssh/known_hosts`로 기록한 뒤 `-o StrictHostKeyChecking=yes`로 접속한다. 변수 값은 "주석 배너 1줄 + `ssh-ed25519` 키 1줄" 형식이다.
- 두 변수의 마지막 갱신일은 각각 2026-10-04 / 2026-10-01로, host key 변경 시점보다 오래됐다. staging도 같은 호스트를 공유하므로 함께 깨질 예정이었다.

## 관련 코드 맥락

- `infra/lightsail/production/deploy-blue-green.sh` 202~207행: root 소유 배포 스크립트가 `runuser -u ubuntu -- git -C /opt/onmaru/repo ...`로 (1) branch가 master인지, (2) `git status --porcelain`이 빈 문자열인지, (3) fetch 후 `origin/master`가 요청 SHA와 같은지, (4) fast-forward 가능한지를 순서대로 확인한다. 하나라도 만족하지 않으면 fail-closed로 중단한다. 202-203행의 가드는 트래킹되지 않은 파일까지 dirty로 판정하며, 이번 2차 증상의 판정 근거다.
- `.github/workflows/deploy.yml` preflight는 SSH로 서버 상태(배포된 SHA·healthy 여부)를 조회해 `deploy-required`를 판정한다. 같은 SHA가 healthy면 build 전에 no-op으로 끝난다. dirty 가드는 이 판정 이후 deploy 단계에서 동작한다.

## 기존 방식의 한계

- known_hosts를 GitHub variable으로 고정하는 방식은 서버 host key가 바뀌면 **배포 전체가 멈춘다**. 갱신 절차가 문서화돼 있지 않아 첫 대응에 진단 시간이 필요했다.
- 스케줄 실패가 3일간 알림 없이 누적됐다. 실패 모니터링은 별도 과제(#805 계열 CI 강화와 함께 검토 여지).

## 검토한 선택지

1. keyscan 결과로 두 환경 변수를 즉시 갱신 — 배포 복구가 최우선이므로 선택
2. Lightsail 콘솔(브라우저 SSH)에서 지문 대조 후 갱신 — 가장 안전하지만 운영자 대기 필요
3. 서버 재생성 가정 하에 키 재배포 — 근거 없음, 보류
4. SSH 22포트 구조 개선(터널) — #822로 분리, 당분간 보류(운영자 결정: Cloudflare 카드 등록 요구)

## 판단 기준

- 배포가 3일째 중단된 상태에서 복구 속도가 최우선. keyscan(TOFU) 값이라도 서버와 연결이 성립하고 이후 실제 배포가 성공하면 키가 실서버 키임이 행동으로 검증된다.
- known_hosts는 sshd 인증(권한)과 무관한 **서버 식별** 수단이므로, 잘못된 키라면 SSH가 거부될 뿐 권한 우표는 생기지 않는다.

## 최종 결정과 해결 방식

1. `ssh-keyscan`으로 현재 ed25519 키를 확보, `ssh-keygen -lf`로 지문finger 확인.
2. 두 환경 변수를 같은 형식(배너 주석 + 키 1줄)으로 갱신. 운영 메모: environment variable **갱신은 개별 PUT이 404를 반환**했고, DELETE 후 컬렉션 POST로 재생성해야 했다(GitHub API 동작 특이점).
3. 수동 `deploy_production=true` dispatch로 검증 시도 → 1차는 SSH 성공 후 dirty 가드에 걸렸고, 해당 dirty 상태는 원인 불명으로 해소(사용자가 서버에서 `git status`로 clean 확인). 이후 scheduled 실행(01:29 UTC)이 전 파이프라인 성공, 추가 dispatch(01:48 UTC)는 no-op + healthy(notify-production 성공)로 재확인.
4. `curl https://api.onmaru.site/auth/csrf` 200으로 운영 서비스 정상 재확인. (참고: `/actuator/*`는 production nginx `site.conf`가 의도 차단하므로 404가 정상이다.)
