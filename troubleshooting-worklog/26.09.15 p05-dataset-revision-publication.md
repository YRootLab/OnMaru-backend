# P05 dataset revision publication

날짜: 2026-09-15

## 문제 상황

Issue #95는 수집이 끝난 dataset revision만 공개하고, 마지막 page 실패나 stale worker가 active revision과 watermark를 바꾸지 못하게 하는 publish 경계를 요구했다.

## 오류명 또는 실패 증상

TDD RED에서 `DatasetPublicationService`, `PublicationStore`, `PublicationPlan`, `SourceWatermark` 등 publication application 타입이 없어 컴파일 실패했다. 검증 중 `apps:spring-api:test`를 같은 project task로 병렬 실행해 Gradle test binary 파일 `in-progress-results-generic.bin`이 사라지는 실행 충돌도 확인했다.

## 기존 구조나 방식의 한계

`modules/catalog`에는 sync scheduler와 qualification 정책은 있었지만, staging revision을 active pointer로 바꾸기 전 어떤 조건을 확인해야 하는지 application port가 없었다. DB contract에는 active pointer CAS와 watermark FK가 있었지만, application 계층에서 lease fence, expected active revision, watermark advance를 하나의 publish plan으로 묶는 책임이 빠져 있었다.

## 관련 코드 맥락

- `modules/catalog/src/main/java/com/yrootlab/onmaru/catalog/application/publication/DatasetPublicationService.java`
  - `StageValidation`이 없거나 ready가 아니면 store publish를 호출하지 않는다.
  - full sync 0건은 `emptyFullSyncReviewed=true`가 아니면 대량 삭제로 게시하지 않는다.
  - `PublicationPlan`에 staged revision, expected active revision, source watermark, tombstone count를 묶어 store port에 넘긴다.
- `PublicationStore.publishIfLeaseAndBaseRevisionMatch(...)`
  - persistence adapter가 구현해야 할 transaction 경계다.
  - lease generation/owner fence와 active pointer CAS가 맞을 때만 active revision, watermark, tombstone publish를 함께 반영한다.
- `DatasetPublicationServiceTests`
  - 마지막 page 실패 시 active revision/watermark 불변.
  - ready revision publish 시 watermark와 tombstone count 동시 반영.
  - stale lease writer와 stale base writer가 publish 결과를 바꾸지 못함.

## 검토한 선택지

1. sync coordinator 안에 publish 로직을 직접 넣는다.
2. catalog publication application service와 store port를 분리한다.
3. JPA/SQL persistence adapter까지 한 번에 구현한다.

## 판단 기준

ADR-0006의 핵심은 business decision과 DB transaction fence를 분리하되, 둘을 하나의 명확한 port 계약으로 묶는 것이다. 현재 repository에는 persistence-jpa 모듈이 아직 없으므로 adapter 구현보다 application contract를 먼저 고정하는 편이 다음 이슈와 충돌이 적다.

## 최종 결정

`modules/catalog/application/publication`에 publication service와 port를 만들고, fake store 기반 TDD로 원자 publish 계약을 고정했다.

## 해결 방식

- `PublicationCommand`로 lease, staged revision, expected active revision, mode, watermark, tombstone count를 전달한다.
- `StageValidation`으로 마지막 page까지 검증된 staging revision만 publish하도록 했다.
- full sync 0건은 명시 review flag 없이는 `EMPTY_FULL_SYNC_REQUIRES_REVIEW`로 막아 delta delete와 구분했다.
- store port가 `LEASE_LOST`, `ACTIVE_REVISION_CHANGED`, `PUBLISHED`를 반환하도록 하여 DB CAS/lease fence 결과를 application이 그대로 노출하게 했다.
- Gradle test 충돌은 같은 `:apps:spring-api:test` task를 병렬 실행한 것이 원인이라, Spring test 검증은 단독 재실행으로 확인했다.
