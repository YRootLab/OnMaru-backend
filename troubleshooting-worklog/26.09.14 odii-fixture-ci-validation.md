# Odii 실제 응답 fixture와 CI 검증 고정 작업 기록

## 날짜

2026-09-14

## 문제 상황

Issue #61의 목표는 Odii API의 spot/story/language/audio/script 계약을 실제 응답 fixture로 고정하는 것이었다. 문서 예시만으로는 원본 ID 계층, 언어별 `tlid/stlid`, 대본 존재 여부, 오류 envelope, 음원 URL 존재 여부를 확정할 수 없었다.

## 오류명 또는 실패 증상

- 첫 live capture 실패 증상: 모든 정상 시나리오가 HTTP 403으로 응답했다.
- 두 번째 capture 실패 증상: provider가 `NO_MANDATORY_REQUEST_PARAMETERS_ERROR1(langCode)`를 반환했다.
- 사전 reviewer 지적: `serviceKey=` query는 검출하지만 JSON 필드 `"serviceKey": "..."` 누출은 validator가 놓칠 수 있었다.
- CI gap: PR의 핵심 검증인 Node script test와 Odii manifest validation이 GitHub Actions에 묶여 있지 않았다.

## 기존 구조나 방식의 한계

기존 `docs/api/tour/tour_audio_guide_api.md`에는 Odii 응답 예시가 있었지만, 실제 서버 호출에서 필요한 필수 파라미터와 오류 형태까지 보장하지는 않았다. CI도 `git diff --check`와 문서 존재 확인만 수행해서, fixture hash drift나 secret redaction 실패를 PR에서 막을 수 없었다.

## 관련 코드 맥락

- `scripts/capture-odii-fixtures.mjs`
  - 담당 로직: `.env.local`의 `ODII_API_URL`, `ODII_API_KEY`를 읽고 Odii live API를 호출해 redacted fixture와 manifest를 생성한다.
  - 입력: scenario 목록, endpoint, query params, 로컬 API key.
  - 출력: `testing/fixtures/provider/odii/*.json`, `docs/reference-snapshots/odii/manifest.json`.
  - 핵심 분기: `omitServiceKey`가 true인 오류 fixture는 key 없이 호출한다. 정상 fixture는 key를 붙이지만 저장 전 `redactUrl()`로 `serviceKey` query를 제거한다.
  - 문제와 연결된 지점: `.env.local`의 Odii key는 URL-encoded 상태였고, `URLSearchParams`가 다시 인코딩하면서 403이 발생했다. `decodeURIComponent(apiKey)` 후 query에 넣도록 바꿔 실제 인증을 통과시켰다.

- `scripts/lib/odii-fixture-validation.mjs`
  - 담당 로직: manifest와 fixture를 읽어 JSON parse, SHA-256 hash 일치, 필수 scenario 존재, secret-like 문자열 누출 여부를 검증한다.
  - 입력: `manifestPath`, `fixtureDir`.
  - 출력: `{ fixtureCount, scenarios }` 또는 오류 throw.
  - 핵심 분기: manifest의 각 capture에 대해 fixture 파일을 읽고 hash를 다시 계산한다. 하나라도 다르면 `fixture hash mismatch`로 실패한다.
  - 문제와 연결된 지점: 처음에는 `serviceKey=`만 잡았기 때문에 JSON field 형태의 key가 새면 통과할 수 있었다. 테스트를 먼저 추가해 RED를 확인한 뒤 `["']?serviceKey["']?\s*[:=]` 패턴으로 query와 JSON key를 모두 잡게 했다.

- `scripts/test/odii-fixture-validation.test.mjs`
  - 담당 로직: validator가 실제로 secret 누출을 실패시키는지, capture URL redaction이 작동하는지 검증한다.
  - 입력: 임시 manifest/fixture와 `redactUrl()` 테스트 URL.
  - 출력: Node TAP test 결과.
  - 핵심 분기: `"serviceKey": "abc"`를 담은 fixture를 만들고, hash를 맞춘 상태에서 validator가 secret-like 오류로 실패해야 한다. hash mismatch가 먼저 나와 의도한 RED가 아니었던 한 번의 테스트 실패도 있었고, hash를 고친 뒤 진짜 RED를 만든 다음 validator를 수정했다.

- `.github/workflows/ci.yml`
  - 담당 로직: PR/push에서 repository hygiene과 script 검증을 실행한다.
  - 추가한 검증: `node --test scripts/test/*.test.mjs`, `node scripts/validate-odii-fixtures.mjs`.
  - 효과: 앞으로 fixture나 manifest가 깨지거나 `serviceKey`가 들어가면 PR CI에서 바로 막힌다.

## 검토한 선택지

1. 문서 예시만 기준으로 후속 Spring adapter를 구현한다.
2. live capture 결과를 fixture로 저장하되 수동 리뷰에 맡긴다.
3. Node script로 capture와 manifest validation을 자동화한다.
4. Java/Spring 테스트로 바로 provider adapter를 만든다.

## 판단 기준

- Issue #61은 runtime adapter 구현이 아니라 provider 계약 qualification이다.
- API key와 민감 query가 repository에 들어가면 안 된다.
- 후속 #96에서 Java/Spring adapter를 만들 때 실제 응답 shape를 기준으로 top-down 구현할 수 있어야 한다.
- 지금 단계에서는 DB/JPA/Flyway보다 fixture와 계약 검증이 먼저다.

## 최종 결정

Node 기반 live capture와 manifest validator를 먼저 만들고, 실제 fixture와 문서 근거를 PR에 고정했다. 이후 Java/Spring 구현은 이 fixture를 입력 계약으로 삼아 adapter/parser/revision publish 순서로 내려간다.

## 해결 방식

- Odii 정상/오류/언어/빈결과/빈대본 시나리오 8개를 capture했다.
- `langCode`가 필수라는 실제 provider 계약을 발견해 모든 정상 시나리오에 명시했다.
- `empty_script_story`에서 official transcript가 빈 문자열이고 `audioUrl`도 빈 문자열일 수 있음을 고정했다.
- `docs/reference-snapshots/odii/README.md`에 무료, 이용허락범위 제한 없음, 개발계정 1,000건, 운영계정 심의 필요, 공식 언어 범위를 기록했다.
- reviewer subagent가 지적한 JSON `serviceKey` blind spot을 테스트 먼저 추가해 재현하고 validator를 고쳤다.
- CI에 Node script tests와 Odii manifest validation을 추가했다.

## Java top-down 학습 관점

이번 작업은 Java 코드를 바로 짠 작업은 아니지만, Spring adapter를 만들기 위한 상위 계약을 고정한 단계다. top-down으로 보면 흐름은 이렇게 이어진다.

1. Product/Issue level: Odii story를 공개 API와 저장 기능에서 쓰려면 provider 응답 계약을 알아야 한다.
2. Contract level: fixture가 `tid/tlid/stid/stlid/langCode/script/audioUrl/pageNo/totalCount`의 실제 shape를 고정한다.
3. Spring application level: 후속 #96에서 `OdiiClient`가 provider HTTP 응답을 source record로 변환한다.
4. Domain/application level: official transcript가 있으면 `OFFICIAL`, 빈 문자열이면 `MISSING`, 나중에 AI가 만들면 `ESTIMATED`처럼 provenance를 분리한다.
5. Persistence level: `audio.odii_spots`, `audio.odii_stories`, `audio.story_versions`, `audio.subtitle_lines`에 revision 단위로 저장한다.
6. Public API level: 후속 #103에서 browser에 provider secret URL을 그대로 노출할지, proxy/cache를 쓸지 결정한다.

Java를 공부할 때는 먼저 “사용자 기능이 어떤 외부 계약에 의존하는가”를 보고, 그 다음 `Controller -> Application Service -> Port -> Adapter -> Parser -> Repository` 순서로 내려가면 된다. 이번 PR은 그중 `Port/Adapter`가 믿고 테스트할 fixture를 만든 작업이다.
