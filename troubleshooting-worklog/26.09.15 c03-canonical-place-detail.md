# C03 canonical place detail API 구현

날짜: 2026-09-15

## 문제 상황

Issue #99는 공개 가능한 현재 catalog projection을 canonical `placeId` 기준으로 상세 DTO에 노출해야 했다. raw provider row를 그대로 반환하면 한옥, 지도, Odii 연결 화면이 서로 다른 식별자를 바라볼 수 있고, 비공개/삭제/모호한 source mapping이 공개 API에 새어 나갈 수 있었다.

## 오류명 또는 실패 증상

- RED 테스트 실패: `PlaceDetailQueryService`, `PlaceProjection`, `SavedPlaceStateLookup` 등 query detail 타입이 없어 catalog module 테스트가 컴파일 실패했다.
- 웹 RED 테스트 실패: `InMemorySavedPlaceStateLookup` 및 `/api/v1/places/{placeId}`, `/api/v1/hanoks/{placeId}` controller wiring이 없어 Spring API 테스트가 컴파일 실패했다.

## 기존 구조나 방식의 한계

`modules/catalog`에는 sync, qualification, publication 로직은 있었지만 공개 상세 조회를 위한 query boundary가 없었다. Spring API에도 place/hanok detail endpoint가 없어 OpenAPI R1 fixture의 `CanonicalPlaceDetail`, `HanokDetail`, 공개 404, 503 outage envelope을 실행 가능한 테스트로 검증하지 못했다.

## 관련 코드 맥락

- `modules/catalog/.../query/detail/PlaceDetailQueryService`
  - 입력: canonical `placeId`, optional member UUID
  - 처리: `PlaceDetailStore`에서 현재 projection을 읽고 `PUBLIC` 상태이면서 ambiguous mapping이 아닌 경우만 DTO로 변환한다.
  - 출력: `CanonicalPlaceDetail` 또는 `HanokDetail` `Optional`
- `PlaceProjection`
  - 공개 projection에 region, address, coordinates, images, description, highlights, Odii 연결 여부, 공개 상태를 담는다.
  - provider 결측값은 조작하지 않고 `null` 또는 빈 배열 그대로 DTO에 전달한다.
- `SavedPlaceStateLookup`
  - catalog query service가 identity/session 저장소에 직접 묶이지 않도록 `savedByMe` 계산만 포트로 분리했다.
- `apps/spring-api/.../PlaceDetailController`
  - 세션 쿠키를 `MemberLifecycleService`로 optional member로 해석한다.
  - 조회 결과가 없으면 `NOT_FOUND`와 `details.resourceType=PLACE`를 반환한다.
  - `PlaceDetailUnavailableException`은 `SERVICE_UNAVAILABLE`와 `retryAfterMs=30000`으로 변환한다.

## 검토한 선택지

1. Spring controller에서 fixture JSON을 직접 반환한다.
2. DB adapter까지 바로 구현한다.
3. catalog module에 query service/port를 만들고 Spring은 in-memory projection store로 계약 경계를 구현한다.
4. saved 상태를 identity module 내부로 강하게 연결한다.

## 판단 기준

- Issue #99의 핵심은 공개 가능한 canonical projection 계약과 오류 경계다.
- 현재 저장소는 documentation-first scaffold이고 실제 DB read adapter는 별도 persistence 이슈로 분리될 가능성이 높다.
- `savedByMe`는 optional auth 상태를 반영해야 하지만 catalog가 session 구현을 몰라야 한다.

## 최종 결정

3번을 선택했다. catalog query service를 모듈 내부의 안정적인 application boundary로 두고, Spring API는 해당 service를 호출해 OpenAPI fixture와 같은 응답 envelope을 만든다.

## 해결 방식

- `PlaceDetailQueryServiceTests`를 먼저 추가해 nullable provider field 보존, 비공개/삭제/모호한 mapping 404 후보 처리, hanok linked card의 동일 canonical `placeId` 사용을 고정했다.
- `PlaceDetailQueryService`, DTO record, projection record, in-memory store, saved lookup port를 추가했다.
- `PlaceDetailWebBoundaryTests`를 추가해 `/api/v1/places/{placeId}`, `/api/v1/hanoks/{placeId}`, unauth saved false, 공개 404 envelope, source outage 503 envelope을 검증했다.
- `CatalogDetailConfiguration`에서 in-memory projection store와 query service를 wiring했다.

## 결과

- 결측 provider field는 `null` 또는 빈 배열로 유지된다.
- 비공개/삭제/모호한 mapping 및 없는 place는 공개 API에서 404로 숨겨진다.
- source outage는 503 envelope으로 변환된다.
- canonical place, hanok detail, map/Odii linked card가 같은 `placeId`를 사용한다.
