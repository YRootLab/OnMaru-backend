# TourAPI qualification fixture 작업 기록

날짜: 2026-09-14

## 문제 상황

Issue #66은 한국관광공사 국문 TourAPI를 서버에서 안전하게 호출하기 전에, 실제 응답 shape, quota, license/attribution, 오류 envelope를 redacted fixture로 고정하는 작업이었다. 핵심은 서비스 키를 저장하지 않으면서도, 다음 단계인 Java/Spring TourAPI HTTP client 구현(#73)이 테스트로 삼을 수 있는 입력 자료를 만드는 것이었다.

## 오류명 또는 실패 증상

- 초기 RED 테스트 실패: `ENOENT: no such file or directory, open 'docs/reference-snapshots/tourapi/manifest.json'`
- 리뷰 중 발견된 계약 오류: `liveCanonicalBlocked`가 `false`로 되어 있어 기존 문서의 "parser 검증 전 LIVE_CANONICAL 금지"와 반대였다.
- 리뷰 중 발견된 scope 누락: #66의 "국문/위치/상세 API" 중 `locationBasedList2`, `detailCommon2` fixture가 빠져 있었다.

## 기존 구조나 방식의 한계

기존 문서(`docs/api/tour/*.md`)에는 TourAPI 필드 설명과 예시가 있었지만, 서버 adapter가 그대로 신뢰하기에는 부족했다. 특히 FE 호출 성공은 서버 쪽 pagination, quota, 429, HTTP 200 오류 envelope, license 판단의 증거가 아니었다.

또한 CI는 repository hygiene만 확인하고 있었기 때문에, fixture가 추가되어도 서비스 키가 실수로 들어갔는지, manifest에 선언한 fixture가 실제로 존재하는지 자동으로 막아주지 못했다.

## 관련 코드 맥락

- `docs/reference-snapshots/tourapi/manifest.json`
  - 담당 로직: TourAPI qualification의 source of truth 역할을 한다.
  - 입력/출력: 코드 실행 입력은 아니지만, provider 이름, quota, license, LIVE_CANONICAL 차단 여부, fixture 목록을 기계 판독 JSON으로 제공한다.
  - 핵심 분기: `qualification.liveCanonicalBlocked: true`는 Issue #73 parser 검증 전 운영 공개 모드를 켜면 안 된다는 게이트다.

- `testing/fixtures/provider/tourapi/*.json`
  - 담당 로직: 다음 Java adapter 테스트가 사용할 provider 응답 표본이다.
  - 입력/출력: 각 파일은 redacted request params, HTTP status, provider body, expected classification을 담는다.
  - 포함 케이스: 정상 목록, 좌표 기반 목록, 상세 공통 정보, 빈 목록, 마지막 page, HTTP 200 오류 envelope, 4xx, 5xx, 429.
  - Java 구현 관점: #73의 HTTP client는 이 fixture들을 읽어 `success`, `provider-parameter-error`, `auth-or-permission-error`, `upstream-timeout-or-gateway-error`, `rate-limited` 같은 분기로 나누면 된다.

- `scripts/test/tourapi-fixtures.test.mjs`
  - 담당 로직: manifest와 fixture가 #66 acceptance를 만족하는지 검증한다.
  - 동작 방식: manifest의 필수 case set과 operation coverage를 확인하고, fixture 디렉터리의 모든 JSON이 manifest에 등록되어 있는지 비교한다.
  - 보안 분기: 모든 JSON 문자열을 재귀 순회하면서 긴 토큰 패턴, `serviceKey`, `encodingKey`, `decodingKey`, query key 흔적이 저장되지 않았는지 확인한다. 의도된 값은 `<REDACTED>`만 허용한다.

- `.github/workflows/ci.yml`
  - 담당 로직: PR에서 문서 fixture 테스트를 실행한다.
  - 변경 내용: `node --test scripts/test/*.test.mjs`를 추가해 GitHub CI에서도 fixture drift를 막는다.

## 검토한 선택지

1. 문서만 추가하고 테스트는 생략한다.
2. fixture만 추가하고 CI에는 연결하지 않는다.
3. manifest와 fixture를 만들고, Node 테스트로 redaction/schema를 검증한다.
4. 지금 바로 Java/Spring TourAPI adapter까지 구현한다.

## 판단 기준

- #66의 범위는 qualification이고, #73이 Java HTTP client 구현을 맡는다.
- 서비스 키와 원본 query string은 절대 저장하지 않아야 한다.
- 다음 Java 작업자가 fixture만 보고도 성공/오류 분기와 LIVE_CANONICAL gate를 이해할 수 있어야 한다.
- PR에서 자동 검증되지 않는 fixture는 시간이 지나면 drift될 수 있다.

## 최종 결정

manifest + redacted provider fixture + Node 검증 테스트 + CI 연결로 #66을 마무리하고, Java adapter 구현은 #73으로 넘겼다.

## 해결 방식

1. TDD 방식으로 `scripts/test/tourapi-fixtures.test.mjs`를 먼저 추가했다. 처음 실행했을 때 manifest가 없어 `ENOENT`로 실패했고, 이 실패를 RED로 확인했다.
2. `docs/reference-snapshots/tourapi/manifest.json`에 provider, quota, license, attribution, operation coverage, LIVE_CANONICAL 차단 조건을 기록했다.
3. `testing/fixtures/provider/tourapi/`에 9개 fixture를 추가했다. 실제 서비스 키 대신 `<REDACTED>`를 넣고 원본 요청 URL은 저장하지 않았다.
4. 리뷰에서 `liveCanonicalBlocked`가 반대로 들어간 문제를 발견해 `true`로 수정했다. 이 값이 true라야 #73 parser 검증 전 운영 공개가 막힌다.
5. 리뷰에서 위치/상세 API scope가 빠진 문제를 발견해 `location-list.json`, `detail-common.json`을 추가했다.
6. 테스트가 manifest 등록 fixture만 검사하면 미등록 파일의 secret을 놓칠 수 있어, fixture 디렉터리 전체 JSON 목록과 manifest case 목록이 정확히 같아야 통과하도록 보강했다.
7. CI에 `node --test scripts/test/*.test.mjs`를 연결했다.
