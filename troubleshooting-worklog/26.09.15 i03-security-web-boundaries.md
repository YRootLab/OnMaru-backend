# I03 security web boundaries

날짜: 2026-09-15

## 문제 상황

#87은 OAuth 구현 전 단계에서 unsafe request, private response, ownership mismatch가 공통 보안 경계로 고정되어야 했다. 현재 Spring API 앱은 아직 Spring Security를 도입하지 않았고 Web MVC 기반 scaffold만 있으므로, 후속 API들이 재사용할 최소 보안 컴포넌트가 필요했다.

## 오류명 또는 실패 증상

초기 RED는 `PrivateResponse`와 `OwnershipGuard`가 없어 compile 단계에서 실패했다. 첫 구현 뒤에는 `CsrfProtectionFilter`가 `ObjectMapper` bean을 요구하면서 `NoSuchBeanDefinitionException`으로 ApplicationContext가 뜨지 않았다.

## 기존 구조나 방식의 한계

기존 `shared-web`에는 오류 envelope, cursor, idempotency는 있었지만 CSRF, private cache, browser security header, 소유권 mismatch 404를 강제하는 web boundary가 없었다. 후속 저장/후기/여정 API가 각자 이 규칙을 구현하면 status code와 cache 정책이 갈라질 위험이 있었다.

## 관련 코드 맥락

- `apps/spring-api/src/main/java/com/yrootlab/onmaru/security/web/CsrfTokenController.java`
  - `GET /auth/csrf`에서 32바이트 난수 기반 token을 만들고 `__Host-onmaru-csrf` cookie를 `Secure; HttpOnly; SameSite=Lax; Path=/`로 발급한다.
- `apps/spring-api/src/main/java/com/yrootlab/onmaru/security/web/CsrfProtectionFilter.java`
  - `/api/**` unsafe method에 cookie token과 `X-CSRF-TOKEN` header 일치를 요구한다.
  - `Origin`이 현재 요청 origin과 다르면 같은 token이어도 403 `CSRF_INVALID`를 반환한다.
- `apps/spring-api/src/main/java/com/yrootlab/onmaru/security/web/PrivateResponseInterceptor.java`
  - `@PrivateResponse` handler에 `Cache-Control: no-store`와 `Pragma: no-cache`를 붙인다.
- `apps/spring-api/src/main/java/com/yrootlab/onmaru/security/web/OwnershipGuard.java`
  - actor와 owner가 다르면 `ResourceNotFoundException`을 던져 resource 존재 여부를 숨긴다.

## 검토한 선택지

1. Spring Security를 바로 도입해 CSRF/session까지 한 번에 묶는다.
2. 각 후속 API controller에서 CSRF와 no-store를 직접 검사한다.
3. 현재 Web MVC scaffold에 맞춰 servlet filter/interceptor와 작은 guard로 공통 경계를 먼저 둔다.

## 판단 기준

- #87의 out of scope는 OAuth provider flow이며, I01이 아직 #136에 막혀 있다.
- 현재 앱 dependency에는 `spring-boot-starter-security`가 없고, 도입 시 인증/session 정책까지 한 번에 커진다.
- 후속 API가 바로 재사용할 수 있는 annotation/filter/guard는 작고 테스트하기 쉽다.

## 최종 결정

Spring Security 도입은 후속 인증/session 구현으로 남기고, 지금은 Web MVC filter/interceptor 기반의 보안 경계를 구현한다.

## 해결 방식

- `SecurityWebBoundaryTests`를 먼저 작성해 CSRF 없음/불일치 403, cross-site origin 403, 유효 token 통과, private no-store, ownership mismatch 404, browser security header를 검증했다.
- `ApiErrorCode`에 `CSRF_INVALID`, `NOT_FOUND`를 추가해 오류 envelope code를 공통 enum에 맞췄다.
- 필터에서 Jackson bean 의존을 제거하고 고정 403 envelope를 직접 써서 Spring Boot 4 WebMVC auto-config와 충돌하지 않게 했다.

## 결과

- `./gradlew :apps:spring-api:test --tests '*SecurityWebBoundaryTests' --no-daemon` 통과.
- 후속 `/api/**` command endpoint는 CSRF token과 same-origin 검사를 기본으로 받는다.
- 개인 응답은 `@PrivateResponse`만 붙이면 no-store 정책을 공유할 수 있다.
