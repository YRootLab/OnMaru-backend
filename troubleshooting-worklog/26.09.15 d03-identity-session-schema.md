# D03 Identity session schema 작업 기록

## 날짜

2026-09-15

## 문제 상황

Issue #76은 Kakao subject와 OnMaru member ID를 분리하고, 회원·외부 OAuth 계정·opaque session·guest grant·삭제 ledger를 PostgreSQL 실행 schema로 만드는 작업이다. 최초 로그인 동시성에서 같은 provider subject가 여러 member에 붙지 않아야 하고, session/guest/state 원문 token은 DB에 저장되지 않아야 했다.

## 오류명 또는 실패 증상

- RED 테스트에서 `identity_members`, `identity_external_accounts`, `identity_sessions` 등이 없어 `relation does not exist` 오류가 발생했다.
- session 유효 조회 view가 없어서 만료·폐기 token 제외를 DB에서 증명할 수 없었다.

## 기존 구조나 방식의 한계

문서와 DBML에는 identity schema가 있었지만 D01/D02 이후 실행 migration에는 catalog까지만 있었다. 세션과 OAuth state를 저장할 테이블이 없으면 I01/I03에서 opaque cookie, CSRF, OAuth state를 application memory나 raw token 형태로 다루게 될 위험이 있었다.

## 관련 코드 맥락

- `apps/spring-api/src/main/resources/db/migration/baseline/V003__d03_identity_session_schema.sql`
  - `identity_members`와 `identity_external_accounts`를 만들고 `(provider,issuer,subject)` unique constraint로 최초 로그인 중복 member 생성을 막는다.
  - `identity_sessions`, `identity_guests`, `identity_oauth_states`는 64자리 hex SHA-256 hash만 저장하도록 CHECK constraint를 둔다.
  - `identity_valid_sessions`, `identity_valid_guests`, `identity_valid_oauth_states` view는 revoked/expired row를 제외한다.
  - `identity_exploration_grants`와 `identity_deletion_ledger`를 추가해 guest→member 승계와 탈퇴 lifecycle의 durable anchor를 만든다.

- `apps/spring-api/src/test/java/com/yrootlab/onmaru/testing/postgres/IdentityMigrationTests.java`
  - provider subject unique constraint로 두 번째 external account insert가 실패하는지 검증한다.
  - active/expired/revoked session을 넣고 valid view가 active hash 하나만 반환하는지 검증한다.
  - raw token처럼 보이는 값은 hash format CHECK로 거부하는지 검증한다.

- `db/migration/registry/migrations.json`
  - V003 path와 SHA-256을 등록해 migration SQL 변경을 CI에서 감지한다.

## 검토한 선택지

1. session 원문 token을 암호화해서 저장한다.
2. DB에는 SHA-256 token hash만 저장하고 원문은 cookie/OAuth flow에서만 사용한다.
3. expired/revoked 판정을 모든 repository query마다 직접 조건으로 붙인다.
4. `identity_valid_*` view를 만들어 구현자가 실수로 만료·폐기 token을 읽지 않게 한다.

## 판단 기준

- Issue #76 implementation note는 token hash만 저장하라고 명시한다.
- 동시 최초 로그인은 application lock보다 DB unique constraint가 최종 방어선이어야 한다.
- I01/I03 후속 구현이 안전한 조회 surface를 재사용할 수 있어야 한다.
- 비밀번호 로그인은 out of scope다.

## 최종 결정

opaque credential 원문은 저장하지 않고 64 hex hash만 허용한다. provider subject uniqueness와 valid session/guest/state view를 DB schema에서 제공한다.

## 해결 방식

- `IdentityMigrationTests`를 먼저 작성해 table 부재와 유효 session 조회 부재를 RED로 확인했다.
- V003 Flyway migration에 identity enum, table, index, valid view, deletion ledger를 추가했다.
- session/guest/state hash는 CHECK constraint로 raw token 저장을 방지했다.
- registry와 migration 소유권 문서를 갱신했다.

## 결과

- 같은 `provider/issuer/subject`는 한 member에만 연결된다.
- expired/revoked session은 `identity_valid_sessions`에서 조회되지 않는다.
- raw token-looking value는 `identity_sessions_token_hash_format_ck`로 거부된다.
- 검증:
  - `./gradlew :apps:spring-api:test --tests '*IdentityMigrationTests' --no-daemon`
  - `node --test scripts/test/migration-policy.test.mjs`
