# P03 sync scheduler lease checkpoint

날짜: 2026-09-15

## 문제 상황

#88은 서버가 03:00 KST에 잠들었다가 재기동해도 누락 일정을 한 번만 복구하고, page 실패 후 checkpoint에서 재개하며, lease를 잃은 worker의 늦은 write를 막는 application boundary가 필요했다.

## 오류명 또는 실패 증상

초기 RED는 `CatalogSyncScheduler`, `CatalogSyncRunCoordinator`, `SyncRunStore` 등 catalog sync application 타입이 없어 compile 실패했다. 구현 후에는 fake store가 차단된 stale write 시도를 카운트하면서 “late write 0” 기대와 충돌했지만, acceptance 의미가 저장된 late checkpoint 0건임을 기준으로 테스트를 정리했다.

## 기존 구조나 방식의 한계

D07 migration과 D08 DB matrix는 lease/checkpoint schema와 DB race를 증명했지만, 이를 호출하는 application use case와 Spring scheduling 진입점은 없었다. 후속 P05/A02 publish·Odii sync가 각자 due scan과 fence를 구현하면 재시도/lease 규칙이 갈라질 수 있었다.

## 관련 코드 맥락

- `modules/catalog/src/main/java/com/yrootlab/onmaru/catalog/application/sync/CatalogSyncScheduler.java`
  - repository에서 due schedule을 조회하고, `registerRunAndAdvanceSchedule`을 통해 run 등록과 다음 due 전진을 한 경계로 위임한다.
- `modules/catalog/src/main/java/com/yrootlab/onmaru/catalog/application/sync/CatalogSyncRunCoordinator.java`
  - `SyncRunStore`에서 lease를 획득하고 checkpoint의 `nextPage`부터 `SyncPageSource`를 호출한다.
  - page 저장과 terminal 전이는 모두 `saveCheckpointIfLeaseHeld`, `finishIfLeaseHeld`를 통해 generation fence를 다시 확인한다.
- `apps/spring-api/src/main/java/com/yrootlab/onmaru/scheduling/catalog/CatalogSyncSchedulingAdapter.java`
  - Spring `@Scheduled` 진입점이다. 실제 DB repository bean이 생기기 전에는 no-op으로 앱 context를 깨지 않는다.

## 검토한 선택지

1. JDBC repository까지 한 번에 구현한다.
2. scheduler와 run coordinator를 application module로 먼저 만들고 repository는 port로 둔다.
3. Spring scheduling adapter만 만들고 로직은 후속 issue로 미룬다.

## 판단 기준

- 현재 repository에는 `modules/catalog`가 아직 없고, D07/D08에서 DB invariant는 이미 검증됐다.
- P03의 핵심은 due scan·checkpoint 재개·lease fence라는 application protocol이다.
- 외부 HTTP 중 DB transaction을 잡지 않는 정책을 지키려면 source 호출과 checkpoint 저장 경계를 port로 분리하는 편이 안전하다.

## 최종 결정

`modules/catalog`에 sync application port/use case를 만들고, Spring 앱에는 얇은 scheduled adapter만 연결한다.

## 해결 방식

- `CatalogSyncSchedulerTests`로 03:00 KST due schedule이 sleep 후 재기동 scan에서 한 번만 run으로 등록되고 다음 due가 다음 03:00 KST로 전진하는지 검증했다.
- `CatalogSyncRunCoordinatorTests`로 page 2 실패 후 checkpoint page 2에서 재개하고, lease generation이 바뀐 worker의 late checkpoint가 저장되지 않는지 검증했다.
- Spring API가 `modules:catalog`를 의존하도록 연결하고, `CatalogSchedulingConfiguration`으로 scheduling을 활성화했다.

## 결과

- `./gradlew :modules:catalog:test --no-daemon` 통과.
- `./gradlew :apps:spring-api:test --tests '*OnMaruApplicationTests' --no-daemon` 통과.
- 실제 JDBC repository와 publish 전환은 #95에서 이어 붙일 수 있는 port 경계가 생겼다.
