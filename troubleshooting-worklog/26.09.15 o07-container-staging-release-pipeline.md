# O07 container·staging release pipeline 작업 로그

날짜: 2026-09-15

## 문제 상황

Issue #82는 Spring API와 FastAPI AI service를 재현 가능한 container image로 만들고, migration gate와 staging smoke, rollback까지 CI/CD 흐름으로 묶는 작업이다. 기존 저장소에는 Dockerfile, staging deploy workflow, credential 분리 계약이 없어 release gate에서 배포 가능성을 검증할 수 없었다.

## 오류명 또는 실패 증상

`node --test scripts/test/deploy-pipeline.test.mjs`를 먼저 추가해 실행했을 때 `Dockerfile missing`, `infra/staging/release-plan.json` ENOENT, `.github/workflows/deploy.yml` ENOENT로 실패했다. 이는 #82의 배포 산출물이 아직 존재하지 않는다는 RED 신호였다.

FastAPI image smoke에서는 두 차례 runtime 문제가 추가로 드러났다. 첫 번째는 `exec /app/.venv/bin/uvicorn: no such file or directory`였고, 원인은 builder 경로를 shebang으로 가진 venv script를 runner 경로에서 직접 실행한 것이었다. 두 번째는 `ModuleNotFoundError: No module named 'onmaru_ai'`였고, 원인은 `uv sync` 기본 editable install이 runner에는 없는 `/workspace/ai/src`를 참조한 것이었다.

## 기존 구조나 방식의 한계

기존 CI는 Gradle, FastAPI, 계약 검증을 잘 수행하지만 runtime image build, image scan, staging smoke, rollback evidence를 다루지 않았다. 또한 `application.yaml`에는 runtime DB credential과 Flyway migration credential이 분리되어 있었지만, staging release plan에서 runtime/migration/readonly/backup credential 경계가 명시되지 않았다.

## 관련 코드 맥락

- `Dockerfile`: Spring Boot `:apps:spring-api:bootJar`를 builder stage에서 만들고, JRE runner stage에서 non-root `onmaru` 사용자로 실행한다. `/actuator/health` healthcheck를 가진다.
- `ai/Dockerfile`: uv 기반 builder stage에서 FastAPI dependency를 설치하고, Python runner stage에서 non-root `onmaru` 사용자로 `uvicorn onmaru_ai.main:app`을 실행한다. `/ready` healthcheck를 가진다.
- `.github/workflows/deploy.yml`: GHCR image build/push, Trivy scan, migration gate, staging smoke, rollback-on-failure job을 순서대로 둔다.
- `infra/staging/release-plan.json`: build-scan → migration-gate → service deploy → smoke → rollback 순서와 credential 권한 경계를 배포 adapter 입력으로 고정한다.
- `scripts/test/deploy-pipeline.test.mjs`: Dockerfile, release plan, deploy workflow가 #82 acceptance를 담고 있는지 repository-local로 검증한다.

## 검토한 선택지

1. Dockerfile만 추가하고 배포 workflow는 후속으로 둔다.
2. 특정 cloud provider나 Kubernetes manifest까지 고정한다.
3. hosting adapter 중립 release plan과 GitHub Actions staging workflow를 함께 추가한다.
4. 문서로만 배포 순서를 설명한다.

## 판단 기준

#82의 범위는 multi-stage images, SBOM/scan, deploy order, migration gate, smoke, rollback, concurrency이고 Kubernetes 필수화는 제외한다. 따라서 특정 hosting으로 잠그지 않되 GitHub Actions에서 image build/scan과 staging smoke를 실행하고, 실제 배포 adapter가 읽을 release plan을 두는 방식이 가장 작고 검증 가능했다.

## 최종 결정

Spring/FastAPI multi-stage Dockerfile과 provider-neutral `infra/staging/release-plan.json`, GHCR+Trivy 기반 staging deploy workflow를 추가하고 Node 테스트로 구조 drift를 막는다.

## 해결 방식

- TDD로 `scripts/test/deploy-pipeline.test.mjs`를 먼저 추가하고 산출물 부재 RED를 확인했다.
- Spring API와 FastAPI AI service Dockerfile을 multi-stage/non-root/healthcheck 형태로 추가했다.
- `.dockerignore`를 추가해 build context에서 `.git`, cache, local venv, build output을 제외했다.
- FastAPI runner는 relocated venv script 대신 `python -m uvicorn`을 사용하고, builder는 `uv sync --frozen --no-dev --no-editable`로 app package를 non-editable install하도록 고쳤다.
- `.github/workflows/deploy.yml`에 image build/push, Trivy scan, migration gate, staging smoke URL 호출, rollback-on-failure job과 concurrency를 추가했다.
- `infra/staging/release-plan.json`과 README에 migration 실패 시 deploy 차단, 이전 image digest rollback, runtime/migration/readonly/backup credential 분리를 기록했다.

## 결과

- `node --test scripts/test/deploy-pipeline.test.mjs`: 3개 테스트 통과.
- `docker build -t onmaru-spring-api:issue82 -f Dockerfile .`: 성공.
- `docker build -t onmaru-ai:issue82 -f ai/Dockerfile .`: 성공.
- `docker run -e ONMARU_SECRETS_SOURCE=fake -p 18082:8000 onmaru-ai:issue82` 후 `/ready`: `{"status":"ready"}` 응답 확인.
