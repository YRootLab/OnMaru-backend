# Odii fixture secret redaction hardening TDD 작업 로그

## 날짜

2026-09-14

## 문제 상황

Issue #61의 Odii API qualification 산출물은 PR #145로 이미 `develop`에 merge되어 있었다. 다만 검증 계획에는 “긴 URL-encoded secret”까지 차단한다고 되어 있었지만, 실제 validator는 `serviceKey` 같은 이름 기반 패턴만 검사하고 있었다. 즉 provider request URL에서 `serviceKey` 이름은 제거됐더라도, 다른 query parameter 이름으로 긴 token 값이 manifest나 fixture에 남으면 놓칠 수 있는 상태였다.

## 오류명 또는 실패 증상

- 실패 증상: 긴 URL-encoded token query 값이 들어간 manifest를 `validateOdiiFixtureSet()`이 거부하지 않았다.
- TDD RED 확인: 신규 테스트 `rejects long URL-encoded token values in manifest URLs`가 처음에는 `Missing expected rejection.`으로 실패했다.
- 중간 조정: 첫 테스트 작성 때 fixture hash가 맞지 않아 `fixture hash mismatch for normal.json`이 먼저 발생했다. 이는 테스트가 의도한 secret 검출 경로까지 가지 못한 것이어서 hash를 실제 fixture 내용 `{}` 기준으로 고쳐 정상 RED를 만들었다.

## 기존 구조나 방식의 한계

기존 `scripts/lib/odii-fixture-validation.mjs`의 `assertNoSecretText(text, context)`는 전체 텍스트에서 다음과 같은 명시적 문자열만 찾았다.

```js
/["']?serviceKey["']?\s*[:=]/i
/ODII_API_KEY/i
/TOUR_API_KEY/i
/KAKAO_(?:MAP_KEY|CLIENT_ID)/i
/GEMINI_API_KEY/i
```

이 방식은 `serviceKey=...`나 `"serviceKey": "..."` 같은 직접 누출에는 강하지만, `redactedUrl` 안에 `token=<긴 인코딩 문자열>`처럼 이름을 바꿔 남은 값은 잡지 못한다. Issue #61의 out-of-scope가 “key·원문 민감 query 저장 금지”였고, Odii capture manifest가 후속 #96 수집 구현의 기준 데이터가 되므로 redaction 검증을 더 단단하게 둘 필요가 있었다.

## 관련 코드 맥락

- `scripts/lib/odii-fixture-validation.mjs`
  - 핵심 함수: `assertNoSecretText(text, context)`
  - 담당 로직: manifest와 fixture JSON 텍스트를 읽은 뒤 secret-like 문자열이 있으면 예외를 던진다.
  - 입력과 출력: 파일 텍스트와 context 경로를 입력받고, 문제가 없으면 반환 없이 통과한다. 문제가 있으면 `secret-like value found in <context>` 오류를 던진다.
  - 문제와 연결되는 이유: `validateOdiiFixtureSet()`이 manifest와 각 fixture를 검증할 때 이 함수를 호출하므로, secret leakage 방어의 중심 지점이다.

- `scripts/test/odii-fixture-validation.test.mjs`
  - 핵심 테스트: `rejects long URL-encoded token values in manifest URLs`
  - 담당 로직: 임시 fixture/manifest를 만들고, manifest의 `redactedUrl`에 `token=<긴 URL-encoded 값>`을 넣은 뒤 validator가 이를 거부하는지 확인한다.
  - 테스트가 잡는 생산 코드 변경: URL query 값 검사를 제거하거나 token-like 장문 값을 허용하도록 바꾸면 이 테스트가 실패한다.

- `scripts/validate-odii-fixtures.mjs`
  - 담당 로직: repository의 실제 `docs/reference-snapshots/odii/manifest.json`과 `testing/fixtures/provider/odii/*.json`을 대상으로 `validateOdiiFixtureSet()`을 실행한다.
  - 문제와 연결되는 이유: 단위 테스트만이 아니라 실제 Odii fixture 8개가 강화된 redaction 규칙을 통과하는지 확인하는 CLI다.

## 검토한 선택지

1. 이름 기반 패턴만 유지한다.
   - 간단하지만 `token`, `key`, 임의 이름의 장문 query 값 누출을 놓칠 수 있다.

2. 모든 URL query 값을 금지한다.
   - 가장 강하지만 `langCode`, `keyword`, `pageNo`, `numOfRows` 같은 정상 provider 계약까지 저장할 수 없어서 fixture의 재사용 가치가 떨어진다.

3. URL을 파싱한 뒤 query 값 중 장문 token-like 값만 차단한다.
   - 정상 pagination/language/search query는 유지하면서, 실제 secret에 가까운 긴 encoded credential 값을 막을 수 있다.

4. manifest schema를 크게 바꿔 request params를 allowlist화한다.
   - 장기적으로는 가능하지만 이번 PR의 범위에 비해 변경면이 크고, 이미 PR #145로 고정된 fixture 구조를 흔든다.

## 판단 기준

- Issue #61의 acceptance criteria인 redacted capture manifest validation을 강화해야 한다.
- 기존 fixture와 README의 provider 계약 정보는 유지해야 한다.
- 후속 #96 구현자가 실제 pagination, language, empty script/audio shape를 재사용할 수 있어야 한다.
- TDD로 실제 누락을 먼저 실패 테스트로 확인해야 한다.

## 최종 결정

URL query 전체를 금지하지 않고, `assertNoSecretText()`에서 URL을 파싱해 query value가 80자 이상의 token-like 문자열이면 `secret-like value`로 거부하도록 했다.

## 해결 방식

1. `scripts/test/odii-fixture-validation.test.mjs`에 실패 테스트를 먼저 추가했다.
   - `redactedUrl`에 긴 token-like query 값을 넣은 manifest를 만들었다.
   - fixture hash는 정상값으로 맞춰 secret 검출 단계까지 도달하게 했다.
   - RED 결과: `Missing expected rejection.`

2. `scripts/lib/odii-fixture-validation.mjs`에 URL query 검사 로직을 추가했다.
   - 텍스트에서 `http://` 또는 `https://` URL 후보를 찾는다.
   - `new URL()`로 파싱 가능한 URL만 검사한다.
   - `url.searchParams.values()`의 값 중 `/^[A-Za-z0-9+/=_-]{80,}$/`에 맞는 값을 secret-like로 본다.
   - 이 변경은 `serviceKey` 이름이 제거됐더라도 긴 credential 값이 다른 query key로 남는 경우를 막는다.

3. 작업 맥락을 운영 문서에 반영했다.
   - `handoff.md`에 현재 branch, PR #145 merge 상태, 이번 PR #147의 redaction hardening 성격, 검증 결과를 기록했다.
   - `CHANGELOG.md`에 Odii fixture validation 강화 항목을 추가했다.
