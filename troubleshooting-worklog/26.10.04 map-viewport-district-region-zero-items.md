# 지도 viewport DISTRICT/REGION 0건 반환 및 초기 진입 오류

- 날짜: 2026-10-04
- 상태: 수정 완료 (PR #615, 운영 배포 대기)
- 관련 작업: OnMaru-backend #604, hotfix/604-map-viewport-ux

---

## 문제 상황

운영 `https://www.onmaru.site/map` 지도 정보모드에서 두 가지 증상이 동시에 발생했다.

1. **초기 진입 시 "지도 정보를 불러올 수 없습니다" 오류** — 새로고침하면 갑자기 지도가 나오는 비일관적 동작
2. **줌 아웃 시 마커가 전부 사라짐** — Kakao 지도 level 8 이상(줌 아웃)으로 이동하면 직전까지 보이던 장소 집계가 모두 소멸

서버 팀의 직접 조회에서 서울 bbox(`126.9,37.5,127.1,37.7`)를 대상으로 level별 실측 결과가 다음과 같이 확인됐다.

| Kakao Level | 서버 모드 | totalCountInViewport | items 수 |
|---|---|---|---|
| 5 | PLACE | 1,569 | 60 |
| 6~7 | CLUSTER | 1,569 | 60 |
| **8~10** | **DISTRICT** | **1,569** | **0** |
| **11~12** | **REGION** | **1,569** | **0** |

CLUSTER(6~7)는 정상이지만 DISTRICT(8~10)와 REGION(11~12)는 `total=1,569 / items=0`이라는 모순된 응답을 반환하고 있었다. FE는 items가 비어 있으면 오류 화면을 표시하도록 구현되어 있어 초기 진입 시 level 8 이상인 경우 항상 오류가 발생했다.

---

## 오류 증상 목록

- 운영 서울 bbox + level 8~12 요청: HTTP 200이지만 `items: []`, `totalCountInViewport: 1569`
- 새로고침 후 level이 낮아지면(level 5~7) 정상적으로 PLACE/CLUSTER 응답
- 전국 bbox로 8개 병렬 요청 시 간헐적 `503 CATALOG_UNAVAILABLE`, `details.timeout: true`
- 운영 응답 헤더 `x-revision: unknown` — 배포된 컨테이너 SHA 식별 불가

---

## 기존 구조의 한계

### DISTRICT/REGION 집계가 행정경계 geometry에 의존

수정 전 `JdbcMapViewportQueryRepository.regions()` 메서드는 시군구·시도별 장소 집계를 위해 두 개의 테이블을 **필수(INNER) JOIN** 했다.

```
map_place_read_projection (장소 데이터)
    INNER JOIN administrative_boundaries (행정경계 geometry)
        ON administrative_boundaries.code = place.sigungu_code
```

이 구조의 핵심 문제는 **장소 데이터는 있어도 행정경계 row가 없으면 JOIN 결과가 0행**이라는 점이다. 운영 DB에서 행정경계 테이블의 row가 누락되거나 장소의 `sigungu_code`·`sido_code`와 경계 테이블의 코드가 불일치할 경우 집계 결과가 전부 사라진다.

### totalCount와 집계 items 쿼리가 분리

수정 전 코드는 총 건수와 집계 items를 **별도 쿼리로 실행**했다.

```java
// 1단계: 전체 count (공간 쿼리, 경계 JOIN 없음)
var total = totalCount(connection, snapshot.id(), query);  // → 1,569

// 2단계: 집계 items (경계 JOIN 있음)
var items = regions(connection, snapshot.id(), query, mode);  // → []
```

두 쿼리가 서로 다른 조건으로 실행되므로 total=1,569이지만 items=0인 상태가 조용히 통과됐다. 집계 없이 숫자만 있는 응답이 FE로 전달된 것이다.

### 배포된 버전 확인 불가

운영 응답 헤더에서 `x-revision: unknown`이 반환되어 실제 배포된 컨테이너의 커밋 SHA를 확인할 수 없었다. 구현 수준의 버그인지 데이터 수준의 버그인지를 공개 API만으로 특정하는 데 시간이 소요됐다.

## 진단 과정

### 1단계: CLUSTER가 정상인데 DISTRICT/REGION이 0인 이유 파악

CLUSTER는 장소의 좌표(PostGIS point geometry)를 격자로 직접 묶는다. 외부 테이블을 JOIN하지 않으므로 1,569건 모두 표현된다.

DISTRICT/REGION은 시군구·시도 경계 polygon을 기준으로 장소를 매핑하는 구조였다. 경계 polygon이 없으면 어떤 장소도 어느 집계 버킷에도 속하지 못해 결과가 0건이 된다.

**핵심 진단 포인트:** CLUSTER는 좌표만으로 집계하고, DISTRICT/REGION은 경계 polygon에 의존한다는 구조적 비대칭.

### 2단계: 장소 데이터 자체의 문제인지 확인

`map_place_read_projection` 테이블의 서울 장소들이 `sido_code`, `sigungu_code` 컬럼을 직접 보유하고 있는지 확인했다. 서버 팀 조회 결과 장소 row에는 `sido_code: '11'`(서울), `sigungu_code: '11:110'`(강남구) 형태로 코드가 정상 저장되어 있었다. **장소 데이터 자체는 손상되지 않았다.**

문제는 경계 geometry 테이블(`administrative_boundaries` 또는 동등한 테이블)이 조회 조건과 불일치하거나 row 자체가 없다는 것으로 좁혀졌다.

### 3단계: 두 쿼리의 결과 불일치 구조 파악

```sql
-- totalCount 쿼리 (경계 테이블 미참조)
SELECT count(*)
FROM map_place_read_projection place
WHERE place.revision_id = ?
  AND place.status = 'ACTIVE'
  AND place.location_geom && ST_MakeEnvelope(?)  -- bbox 공간 인덱스 활용
  AND (? = 'ALL' OR ...)

-- DISTRICT 집계 쿼리 (경계 테이블 필수 JOIN)
SELECT boundary.name, count(*), ST_Centroid(ST_Collect(place.location_geom))
FROM map_place_read_projection place
INNER JOIN administrative_boundaries boundary
    ON boundary.code = place.sigungu_code  -- 경계 row 없으면 JOIN 실패
WHERE place.revision_id = ?
  AND ...
GROUP BY boundary.code
```

`totalCount`는 1,569를 반환하고 집계 쿼리는 0행을 반환하는 이유가 명확해졌다. 두 쿼리가 서로 다른 테이블을 기준으로 실행되기 때문이다.

### 4단계: 503 timeout 원인 파악

전국 bbox에서 간헐적으로 발생하는 503은 두 쿼리의 직렬 실행 비용과 연관이 있었다.

- 1단계 totalCount: 전국 23,675건 공간 count → ~100ms
- 2단계 구버전 regions: 경계 JOIN + ST_Collect + GROUP BY → 경계 누락 시 full scan 가능

2단계 쿼리가 경계 테이블을 찾지 못해 full scan 또는 nested loop을 반복하면 2초 타임아웃을 초과했다. 전국 bbox 8개 요청을 동시에 보내면 DB connection pool이 고갈되어 대기 중인 요청이 타임아웃으로 503이 됐다.

## 수정 내용

### 핵심 변경: 경계 geometry 의존 제거

DISTRICT/REGION 집계 쿼리를 경계 테이블 JOIN 없이 `map_place_read_projection`의 `sigungu_code`·`sido_code` 컬럼만으로 직접 집계하도록 재작성했다.

**수정 전 구조:**
```sql
-- 경계 geometry JOIN 필수 → 경계 row 없으면 0건
SELECT boundary.name, count(DISTINCT place.place_id), ST_Centroid(...)
FROM map_place_read_projection place
INNER JOIN administrative_boundaries boundary
    ON boundary.code = place.sigungu_code
WHERE ...
GROUP BY boundary.code
```

**수정 후 구조:**
```sql
WITH candidates AS (
    SELECT place.sigungu_code AS region_code,  -- 장소 자체의 코드 사용
           place.place_id, place.location_geom,
           coalesce(category.canonical_category, upper(place.display_category)) AS canonical_category
    FROM map_place_read_projection place
    LEFT JOIN map_place_category_projection category  -- category도 LEFT JOIN으로 변경
      ON category.revision_id = place.revision_id
     AND category.place_id = place.place_id
    WHERE place.revision_id = ?::uuid
      AND place.status = 'ACTIVE'
      AND place.sigungu_code IS NOT NULL  -- 코드 있는 장소만 집계
      AND place.location_geom && ST_MakeEnvelope(?, ?, ?, ?, 4326)
      AND ...
), distinct_places AS (
    SELECT DISTINCT region_code, place_id, location_geom
    FROM candidates
), region_counts AS (
    SELECT region_code, count(*) AS place_count,
           ST_Centroid(ST_Collect(location_geom)) AS center,
           ST_Envelope(ST_Extent(location_geom)) AS bounds
    FROM distinct_places GROUP BY region_code
)
SELECT candidates.region_code,
       coalesce(max(region.name), candidates.region_code),  -- 이름 없으면 코드로 fallback
       max(ST_Y(center)), max(ST_X(center)), ...
       count(DISTINCT candidates.place_id), candidates.canonical_category,
       region_counts.place_count
FROM candidates
JOIN region_counts ON region_counts.region_code = candidates.region_code
LEFT JOIN catalog_regions region ON region.code = candidates.region_code  -- 이름 조회만 LEFT
GROUP BY candidates.region_code, candidates.canonical_category, region_counts.place_count
```

**변경 포인트:**

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 경계 테이블 | INNER JOIN (필수) | LEFT JOIN (이름 조회만) |
| 집계 기준 | 경계 geometry | 장소의 sigungu_code/sido_code |
| 경계 없을 때 | 0건 반환 | 코드 값으로 fallback |
| category projection | INNER JOIN | LEFT JOIN + display_category fallback |

### 자동 폴백 체인 추가

지역코드 없는 장소가 일부 섞이거나 집계 결과가 limit를 초과할 경우를 대비해 자동 폴백 체인을 구현했다.

```
DISTRICT 요청
  └→ items.size() > limit(60) → REGION으로 재집계
  └→ items.isEmpty() 또는 sum(items.count) ≠ totalCount → CLUSTER로 전환
     └→ CLUSTER는 좌표만 사용하므로 항상 모든 장소를 표현
```

이 폴백으로 운영 DB 상태가 어떠하든 사용자는 항상 무언가를 볼 수 있게 됐다.

### PLACE→CLUSTER 자동 전환 추가

zoom 1~5는 PLACE(개별 POI) 모드인데, bbox 안에 장소가 60개를 초과하면 limit를 초과한 60개만 임의 표시(PARTIAL)하는 대신 CLUSTER로 자동 전환해 모든 장소를 집계 버블로 표현한다.

```java
var total = totalCount(connection, snapshot.id(), query);
var mode = requestedMode == MapInfoRenderMode.PLACE && total > query.limit()
        ? MapInfoRenderMode.CLUSTER  // PLACE→CLUSTER 자동 전환
        : requestedMode;
```

이 변경으로 zoom 5에서 서울 전체를 보여도 임의의 60개만 찍히는 대신 전체 1,569개를 격자 클러스터로 표현한다.

### IllegalStateException throw 제거

기존 코드는 마지막에 items 합계가 totalCount와 다르면 `throw new IllegalStateException`으로 503을 반환했다. 실제 운영에서는 CLUSTER가 모든 장소를 커버하므로 이 조건이 달성될 수 없지만, 예상치 못한 엣지케이스(매우 넓은 bbox 등)에서 강제 503이 될 수 있어 PARTIAL coverage 200 응답으로 교체했다.

```java
// 수정 전 (503 위험)
if (representedCount != total) {
    throw new IllegalStateException("map viewport items do not represent the full viewport count");
}

// 수정 후 (graceful degradation)
var coverage = representedCount < total ? "PARTIAL" : "COMPLETE";
```

### timeout 로깅 추가

timeout·503 발생 시 원인 추적이 어려웠던 문제를 해결하기 위해 실패 경로에 구조화 로그를 추가했다.

```java
LOGGER.warn(
    "event=map_viewport outcome={} renderMode={} zoomLevel={} bbox={} category={} durationMs={}",
    outcome, renderMode, zoomLevel, bbox, category, elapsedMs, exception);
```

## 수정 후 시나리오별 동작

### 처음 진입 (Kakao level 8, 서울 bbox)

```
FE → 서버: zoomLevel=8, bbox=서울 전체, limit=60

1. totalCount = 1,569
2. requestedMode = DISTRICT
3. regions(DISTRICT) → sigungu_code 기준 직접 집계
   → 강남구 200건, 강서구 130건 ... 25개 시군구
4. sum(items.count) = 1,569 = totalCount → CLUSTER 전환 없음
5. 응답: renderMode=DISTRICT, items=25개, coverage=COMPLETE
```

이전: `total=1569, items=0` → FE 오류 화면  
이후: 25개 시군구 버블 정상 표시 ✅

### 줌 아웃 (level 8 → 12)

```
zoomLevel=12, bbox=서울 전체

1. totalCount = 1,569
2. requestedMode = REGION
3. regions(REGION) → sido_code 기준 집계
   → 서울(11) 1,569건
4. 응답: renderMode=REGION, items=1개 (서울 버블)
```

이전: `total=1569, items=0` → 아무것도 표시 안 됨  
이후: 서울 버블 1개 정상 표시 ✅

### 줌인 (level 8 → 6 → 3)

```
[level 8 → 6] DISTRICT → CLUSTER (bbox 좁아지며 자연스럽게 전환)
[level 6 → 5] bbox 안에 장소 200개 → totalCount(200) > limit(60) → CLUSTER 유지
[level 5 → 3] bbox 안에 장소 5개 → totalCount(5) ≤ limit(60) → PLACE로 개별 마커
```

### category projection 누락 장소 포함

카테고리 projection row가 없는 장소도 `display_category` 컬럼으로 fallback 집계되어 ALL/HANOK 조회에서 누락 없이 표현된다.

## 남은 확인 사항

- **zoom 5에서 CLUSTER 렌더링**: total > 60이면 PLACE 대신 CLUSTER 응답. FE가 zoomLevel=5에서 `renderMode=CLUSTER`를 올바르게 렌더링하는지 배포 후 확인 필요
- **운영 DB 지역코드 커버리지**: 장소 전체에 `sido_code`/`sigungu_code`가 채워져 있는지 확인. 누락 장소는 DISTRICT/REGION에서 제외되고 CLUSTER 폴백을 타므로 사용자는 항상 데이터를 볼 수 있지만, 시군구 집계 count가 실제 total보다 낮을 수 있음
- **운영 smoke 후 Issue #604 종결**: 수정 코드가 배포되고 level 5~12 전 구간에서 non-empty items가 확인되면 close
