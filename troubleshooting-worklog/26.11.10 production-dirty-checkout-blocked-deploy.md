# 운영 배포 차단: 운영 서버 체크아웃이 더러워서 발생한 배포 실패와 DB 이미지 드리프트

- 날짜: 2026-11-10 (사건 발생: 2026-11-09 UTC)
- 상태: 해결 완료 (PR #827 `develop` 머지, PR #828 릴리스 v0.3.56 `master` 머지, 운영 배포 실행 `42680478202` 성공)
- 관련 작업: Issue #811, PR #821, #823, #827, #828
- 정정: 이 문서에서 "더티"라고 판단한 대상은 **AI 엔진 저장소가 아니라 운영 서버의 BE 체크아웃**(`/opt/onmaru/repo`)입니다.

---

## 1. 문제 상황

운영 배포 워크플로(`Build Images and Deploy`, `deploy_production=true`)가 여러 번 실패했습니다. 실패 로그는 다음 한 줄이었습니다.

```
Production checkout is dirty
##[error]Process completed with exit code 1.
```

배포 자체는 같은 커밋에서 한 번 이상 성공하지 못했습니다. 그 사이 다른 실패 원인도 섞여 있어서 처음에는 원인을 구분하기 어려웠습니다.

## 3. 사고 과정

### 3.1 처음 가정: 코드나 CI 문제

`production-deploy` 잡이 실패해서, 처음에는 CI 게이트나 코드 문제를 의심했습니다. 실제로 `17:58` 실행은 `master` 머지 커밋의 `verify`가 아직 `in_progress`였기 때문에 게이트에서 막혔습니다. 이건 올바른 안전장치의 동작이었습니다.

잠깐 잘못 판단한 부분이 있습니다. 게이트 실패를 보고 "CI가 문제다"라고 한 번 더 추정했는데, 실제로는 게이트 실패와 더러운 체크아웃 실패가 서로 다른 시점의 다른 원인이었습니다. 로그 한 줄씩 원인을 구분하지 않고 실행 결과만 보고 묶어서 판단한 것이 혼선을 키웠습니다.

### 3.2 `Production checkout is dirty`의 의미

배포 스크립트(`infra/lightsail/production/deploy-blue-green.sh`)는 다음을 확인합니다.

```bash
[ -z "$(runuser -u ubuntu -- git -C "$REPO" status --porcelain)" ] || fail "Production checkout is dirty"
```

즉 **운영 서버의 `/opt/onmaru/repo` 체크아웃에 추적 파일의 수정이나 추적되지 않는 파일이 하나라도 있으면** 배포를 거부합니다. 이 가드는 운영 코드와 git 기록을 일치시키기 위한 의도된 안전장치입니다. 가드를 완화하거나 우회하는 것은 맞지 않다고 판단했습니다.

배포 계정(`deployer-command.sh`)으로는 `status <sha>`만 가능해서, 어떤 파일이 더러운지 GitHub 쪽에서는 알 수 없었습니다.

### 3.3 서버 확인 (읽기 전용)

로컬에 있던 Lightsail 관리 키로 운영 서버에 접속해 읽기 전용으로 확인했습니다.

- 브랜치는 `master`, HEAD는 `v0.3.54`
- 더러운 변경은 `infra/lightsail/compose.yaml` 한 줄
  - 변경 전: `image: postgis/postgis:17-3.5-alpine`
  - 변경 후: `image: onmaru/postgres:17-postgis-pgvector`
- 그 변경은 이미 **실행 중**이었습니다. `onmaru-lightsail-postgres-1` 컨테이너가 이 이미지로 2026-11-09 04:53 UTC에 재생성되어 14시간째 healthy 상태였습니다.

즉 누군가 운영 DB 컨테이너를 pgvector 이미지로 교체했고, 그 변경이 git에 반영되지 않았습니다. 이 불일치가 더러운 체크아웃의 정체였습니다. 이 pgvector 이미지는 AI RAG 임베딩이 들어 있는 DB 이미지입니다(사용자 확인).

### 3.4 되돌리기에 대한 판단과 정정

처음에는 "파일을 되돌리면 다음 `compose up`이 DB 컨테이너를 `postgis` 이미지로 다시 만들 수 있으니 위험하다"고 판단해서 되돌리지 않았습니다.

이 판단은 일반 원칙으로는 맞지만, 이 배포 스크립트에 대해서는 정정이 필요합니다. 배포 스크립트는 `compose up -d --no-deps spring-$TARGET`만 실행하고 Postgres는 건드리지 않습니다. 따라서 되돌리는 것 자체가 배포 중 DB를 바꾸지는 않았을 것입니다. 다만 사람이 서버에서 `compose up`을 전체로 실행하면 위험하다는 점은 여전히 유효합니다. 그래서 되돌리기 전에 "이 이미지가 실제로 실행 중인가"를 먼저 확인하는 절차가 맞다고 결론 내렸습니다.

### 3.5 AI 팀 메시지와의 연결

앞서 AI 팀이 보낸 안내에는 "PostgreSQL 17에 pgvector v0.8.0이 설치되어 `onmaru/postgres:17-postgis-pgvector`로 빌드되었고, 1,080건의 임베딩이 `ai` 스키마에 적재되어 활성화되어 있다"는 내용이 있었습니다. 저장소 compose가 이 이미지를 모르고 있었던 것이 드리프트의 직접 원인이었습니다.

## 4. 해결 과정

1. 저장소 `infra/lightsail/compose.yaml`의 Postgres 이미지를 실행 중인 이미지로 맞추는 PR #827을 만들었습니다. `verify`를 통과한 뒤 `develop`에 머지했습니다.
2. 릴리스 v0.3.56 PR #828을 `develop → master`로 머지했습니다. 머지 커밋의 CI `verify`가 성공한 뒤에 진행했습니다.
3. 서버에서 더러운 한 줄을 되돌렸습니다. 되돌리기 전에 그 줄이 새 저장소 버전과 **같은 이미지 값인지** 확인했고, 되돌린 뒤 `git status --porcelain`이 비었는지 확인했습니다. Postgres 컨테이너는 손대지 않았습니다.
4. 운영 배포 `42680478202`를 디스패치했습니다. `production-deploy` 성공, 마이그레이션 게이트 성공.
5. 배포 후 확인: 새 spring-green 컨테이너 healthy, 내부 `/actuator/health` `UP`, Postgres 컨테이너 생성 시각 그대로(2026-11-09 04:53 UTC), 체크아웃 `master 6e0cd9c3`, 더러운 항목 없음.

## 5. 아직 미확정인 것

- 실행 `42671555310`(잡 2개)와 `42671952702`(잡 0개)가 즉시 실패한 원인은 로그가 없어 확정하지 못했습니다. GitHub 측 일시 장애인지, 동시성 그룹(`image-deploy-refs/heads/master`) 때문인지 확인이 필요합니다.
- 운영 DB 컨테이너를 pgvector 이미지로 바꾼 작업의 주체와 절차는 기록이 없습니다. 이후에는 서버에서 직접 바꾼 변경을 git에 먼저 반영하는 것을 원칙으로 합니다.

## 6. 교훈

1. **운영 서버에서 손으로 바꾼 설정은 같은 날 git에 반영한다.** 이번 드리프트는 "컨테이너는 바뀌었는데 저장소는 그대로"인 상태에서 생겼습니다.
2. **배포 가드는 우회하지 말고 원인을 찾는다.** 더러운 체크아웃 가드는 드리프트를 드러내는 역할을 정확히 했습니다.
3. **실패 로그 한 줄씩 원인을 분리한다.** 게이트 실패, 더러운 체크아웃, 잡 미생성은 서로 다른 원인입니다. 묶어서 판단하면 방향을 잘못 잡습니다.
4. **되돌리기 전에 실행 상태를 먼저 확인한다.** 이번에는 컨테이너 생성 시각과 이미지 이름으로 실행 중인 상태를 확인한 뒤 되돌렸습니다.
5. **배포 스크립트의 실제 범위를 확인한 뒤 위험을 판단한다.** 일반 원칙과 이 스크립트의 실제 동작이 다를 수 있습니다.
