# Spring ArchUnit 모듈 경계 테스트 작업 로그

## 날짜

2026-09-14

## 문제 상황

GitHub Issue #68의 목표는 ADR-0003에서 정한 Spring modular monolith 경계를 CI에서 강제하는 것이다.
특히 `core`가 Spring/JPA/Reactor 타입에 의존하지 않아야 하고, module 간 의존은
`journey -> discovery -> catalog`, `community -> catalog` 방향을 기본 DAG로 유지해야 한다.

## 오류명 또는 실패 증상

- `Could not resolve all files for configuration ':apps:spring-api:testCompileClasspath'`
  - 원인: `archunit-junit5`를 추가했지만 Gradle dependency lock state에 없었다.
- `core_must_not_import_spring_jpa_or_reactor FAILED`
  - 원인 1: 의도적으로 만든 fixture의 `org.springframework.stereotype.Service` import가 전체 ArchUnit rule에 잡혔다.
  - 원인 2: 현재 production 코드에는 아직 `..core..` 패키지가 없어 ArchUnit이 empty should를 실패로 처리했다.
- `directCrossModuleCoreFixtureFailsConsumerOwnedPortRule()` 실패
  - 원인: consumer-owned port 규칙을 추가했을 때 기존 clean fixture가 다른 module port를 직접 import하고 있었다.
- `bridgeInternalImportFixtureFailsApiOnlyRule()` 실패
  - 원인: app bridge의 provider 내부 package 접근을 검증하는 위반 fixture가 아직 없어 negative test가 실패했다.

## 기존 구조나 방식의 한계

Spring API scaffold는 `apps/spring-api` 단일 모듈과 기본 Spring Boot smoke test만 갖고 있었다.
따라서 이후 `catalog`, `discovery`, `journey`, `community` core 코드가 추가될 때
framework import나 cycle이 들어와도 CI에서 자동으로 막을 장치가 없었다.

기존 CI의 `Spring API tests` step은 이미 `./gradlew test --no-daemon`을 실행하고 있었다.
그래서 새 CI step을 추가하기보다, ArchUnit 테스트를 JUnit test suite에 포함시키는 방식이 가장 작고 직접적인 연결이었다.

## 관련 코드 맥락

- `apps/spring-api/src/test/java/com/yrootlab/onmaru/architecture/ModuleBoundaryArchUnitTests.java`
  - 담당 로직: ArchUnit으로 production classpath와 test fixture classpath를 읽어 module boundary rule을 검증한다.
  - `core_must_not_import_spring_jpa_or_reactor`: `com.yrootlab.onmaru..` 아래 production `..core..` class가
    `org.springframework..`, `jakarta.persistence..`, `reactor..` package에 의존하지 못하게 한다.
  - `productionModulesStayAcyclic()`: test fixture를 제외한 production classpath만 import해서 module slice cycle과
    문서화된 의존 방향을 검사한다.
  - `frameworkImportFixtureFailsTheCoreRule()`: `fixture.framework.catalog.core.SpringLeakingCatalogCore`가
    Spring annotation에 의존할 때 rule이 실제로 실패하는지 증명한다.
  - `moduleDagFixtureAcceptsDocumentedDependencyDirection()`: clean fixture가
    `journey -> discovery -> catalog`, `community -> catalog` 방향으로만 의존할 때 통과하는지 확인한다.
  - `moduleCycleFixtureFailsModuleDagRule()`: catalog와 discovery가 서로 참조하는 cycle fixture가
    `Cycle detected`로 실패하는지 확인한다.
  - `directCrossModuleCoreFixtureFailsConsumerOwnedPortRule()`: consumer core가 다른 module package를 직접 import하면
    실패하는지 확인한다.
  - `bridgeInternalImportFixtureFailsApiOnlyRule()`: app bridge가 provider module의 `core/application/adapter`
    내부 package를 import하면 실패하는지 확인한다.

- `apps/spring-api/src/test/java/com/yrootlab/onmaru/architecture/fixture/**`
  - 담당 로직: ArchUnit negative/positive test가 실제 bytecode dependency를 읽도록 하는 최소 fixture class들이다.
  - framework fixture는 Spring import 위반을 일부러 만든다.
  - clean module fixture는 consumer-owned port와 app bridge 조합을 보여준다.
    예를 들어 `DiscoveryCore`는 catalog port가 아니라 자기 module의 `CandidateSearchPort`를 의존하고,
    `CatalogCandidateBridge`가 그 port를 구현하면서 catalog의 공개 `CatalogQueryApi`만 호출한다.
  - cycle fixture는 `catalog.core.CyclicCatalogCore <-> discovery.core.CyclicDiscoveryCore` 상호 참조를 만든다.
  - direct fixture는 `discovery.core.DirectDiscoveryCore`가 `catalog.core.DirectCatalogCore`를 직접 import해
    consumer-owned port 위반을 만든다.
  - bridgeviolation fixture는 `app.bridge.CoreReachingCatalogBridge`가 `catalog.core.InternalCatalogPolicy`를
    직접 import해 app bridge의 공개 API 경계 위반을 만든다.

- `gradle/libs.versions.toml`, `apps/spring-api/build.gradle.kts`, `apps/spring-api/gradle.lockfile`
  - 담당 로직: `com.tngtech.archunit:archunit-junit5:1.5.0`을 test dependency로 고정하고
    dependency locking 환경에서도 CI가 재현 가능하게 resolve하도록 한다.

## 검토한 선택지

1. CI workflow에 별도 ArchUnit step을 추가한다.
2. 기존 `./gradlew test --no-daemon` 경로에 ArchUnit JUnit 테스트를 포함한다.
3. Spring Modulith test를 도입한다.
4. 별도 `build-logic/architecture` 플러그인을 먼저 만든다.

## 판단 기준

- Issue #68의 acceptance criteria를 가장 작은 변경으로 만족하는가
- 의도적 위반 fixture가 실제 실패하는가
- 기존 CI test step에 자연스럽게 포함되는가
- 아직 production core package가 없는 초기 scaffold 상태에서도 불필요하게 실패하지 않는가
- 이후 실제 module code가 추가될 때 framework import와 cycle을 막을 수 있는가

## 최종 결정

기존 Gradle test suite에 ArchUnit JUnit 테스트를 추가하고, fixture 기반 negative/positive test로 rule의 감지력을 증명한다.

## 해결 방식

- `archunit-junit5` 1.5.0을 version catalog와 Spring API test dependency에 추가했다.
- dependency locking 때문에 compile/runtime classpath resolve가 실패해서 `--write-locks`로 `apps/spring-api/gradle.lockfile`을 갱신했다.
- production rule은 `architecture.fixture` package를 제외했다. fixture는 일부러 위반을 담기 때문에 전체 rule에 섞이면 정상 테스트가 실패한다.
- 현재 production에는 아직 `..core..` class가 없으므로 `.allowEmptyShould(true)`를 적용했다. 이렇게 해야 scaffold 단계에서는 통과하고,
  실제 core class가 생기면 해당 class를 대상으로 rule이 적용된다.
- `ImportOption.Predefined.DO_NOT_INCLUDE_TESTS`로 production module 검사에서 test fixture가 섞이지 않게 했다.
- module direction rule은 fluent chain 하나로 과하게 묶지 않고 catalog/discovery/community별 금지 방향을 나눴다.
  그래서 다음 세션이 어느 module의 어떤 방향을 막는지 바로 읽을 수 있다.
- consumer-owned port 규칙을 추가해 core가 다른 module package를 직접 import하지 못하게 했다.
  clean fixture는 consumer core가 자기 module port만 보고, app bridge가 provider module의 공개 `api`를 호출하는 형태로 고쳤다.
- app bridge 규칙을 추가해 bridge가 다른 module의 `core`, `application`, `adapter` 내부 package를 직접 import하지 못하게 했다.
  이 규칙은 provider 내부 구현을 bridge가 우회 호출하는 일을 막고, 공개 API 경계만 조합하도록 강제한다.

## 결과

- 테스트 코드 추가 완료:
  - `ModuleBoundaryArchUnitTests`
  - framework import 위반 fixture
  - clean DAG fixture
  - cycle fixture
  - direct cross-module core import 위반 fixture
  - app bridge internal import 위반 fixture
- CI 연결:
  - 별도 workflow 수정은 하지 않았다.
  - 기존 `.github/workflows/ci.yml`의 `./gradlew test --no-daemon`에서 ArchUnit 테스트가 자동 실행된다.
- TDD 진행:
  - 테스트와 fixture를 먼저 작성했다.
  - dependency lock 누락 실패, fixture 위반 실패, empty production package 실패를 순서대로 확인했다.
  - 각 실패 원인에 맞춰 lock 갱신, fixture 제외, empty should 허용, production/test import 범위 분리를 적용했다.
- 검증:
  - `./gradlew :apps:spring-api:test --tests com.yrootlab.onmaru.architecture.ModuleBoundaryArchUnitTests` 통과
  - `./gradlew test --no-daemon --rerun-tasks` 통과
  - `./gradlew check` 통과
  - `git diff --check` 통과
  - CI workflow의 Node fixture/planning/contract/FastAPI pytest 검증도 로컬에서 통과했다.
  - `scripts/verify-contracts`는 exit code 0이었지만, 로컬 Python 3.9 LibreSSL 관련 warning이 한 줄 출력됐다.

## 남은 과제

- 실제 `catalog`, `discovery`, `journey`, `community` production package가 추가되면 package naming이 현재 ArchUnit pattern과 맞는지 확인해야 한다.
- Issue #68 PR 생성 전에는 관련 Issue 링크, 변경 파일, 검증 결과를 PR 본문에 정리해야 한다.
