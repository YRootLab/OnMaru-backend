# 온마루 관광데이터 활용 공모전 평가

재평가일: 2026-10-07 · 관련 Issue: [#673](https://github.com/YRootLab/OnMaru-backend/issues/673) · 평가 대상: [공개 사이트](https://www.onmaru.site/)

## Verdict

**현재: C, 본선·장려상 경쟁력(잠정 63/100). 개선 후: B, 우수상 경쟁력(조건부).** 한옥 현장 해설의 이용·관광 행동 효과가 검증되면 A를 다시 검토한다. 점수는 수상 확률이 아니다. 아래 100점 표는 `tourism-contest-evaluator`의 **분석용 정규화 기준**이며, 한국관광공사의 공식 배점과 다르다. 실제 지원 자격·접수 상태·제출물은 확인하지 않았다.

한 문장 평가: **한옥을 보고 듣는 경험은 풍부하지만, 공개 추천의 비관련 장소와 비어 있는 K-콘텐츠 API 때문에 작품에서 실제 한옥을 찾아 이해하는 핵심 여정을 아직 입증하지 못했다.**

2026-10-07에는 공개 API와 저장소를 다시 확인했으나 동적 브라우저 화면을 재검증하지 못했다. 화면 관련 지적은 2026-10-02의 관찰 표본이며, 지속 여부는 별도 확인이 필요하다. K-pop/K-drama 라벨링은 **계획과 일부 코드 구현**으로 평가했고 공개 성과로 가산하지 않았다.

### FE·BE 개선을 공모전이 평가하는 방식

공식 심사는 FE 컴포넌트 수, BE 모듈 분리, LLM 파이프라인 자체에 독립 점수를 주지 않는다. 그런 작업이 **사용자 여정의 완료율, 정확한 관광데이터 연결, 서비스 완성도, 실용성**을 높였다는 시연·측정 결과로 평가된다. 예를 들어 증분 수집과 작품–장소 근거 검증은 유용하지만, 공개 카드의 오분류·허위 촬영지 주장·빈 결과를 실제로 줄여야 데이터 활용과 완성도 점수로 이어진다. 이는 공식 배점을 적용한 `[INFERENCE]`다.

## 심사위원이 높게 볼 점과 질문할 점

**높은 점수의 이유.** 한옥이라는 주제가 화면 전체에서 일관된다. 한옥 구조 체험은 단순 장소 목록보다 교육적 기억을 남긴다. TourAPI의 장소 식별·기본 정보와 Odii의 소리를 묶으면 ‘발견 → 현장 질문 → 이해·감상’이라는 관광 행동을 만들 재료가 있다. `/hanok`의 K-콘텐츠 화면과 스테이는 서로 다른 방문 동기를 접속시킬 가능성이 있다. 현재 K-콘텐츠 API는 비어 있으므로 실제 연결 성과로 가산하지 않았다. `[INFERENCE]`

**가장 큰 감점의 이유.** 추천의 제목과 내용이 어긋난다. 교통교육장이 한옥 추천에 들어오면 알고리즘 한 건의 실수보다 **서비스가 한옥을 정의하고 검수하는 방식**을 의심하게 된다. 재생 0인 오디오를 ‘인기’라고 부르면 통계와 에디토리얼의 구분도 불명확해진다. 관광데이터 공모전에서는 이 문제가 완성도와 데이터 활용 적절성을 동시에 낮춘다. `[OBSERVED + INFERENCE]`

### 제안된 K-콘텐츠 기능을 어떻게 봤는가

K-드라마·K-pop 라벨링은 검색 유입과 한옥 방문 동기를 연결할 수 있다. 하지만 **TourAPI의 장소 레코드에는 특정 작품의 촬영·등장 관계가 원래 들어 있지 않다**는 점을 [ADR-0010](../decisions/0010-screen-hanok-ai-auto-publish-without-review.md)도 인정한다. 따라서 `TourAPI 기반`은 장소 식별·위치·기본 관광정보에 적용되고, `이 작품의 실제 촬영지` 주장은 별도 신뢰할 만한 원문 출처와 장소 동일성 검증에 의존한다. LLM 라벨은 그 검증을 대체하지 못한다.

| 관계 유형 | 공개 표시 원칙 | 이유 |
|---|---|---|
| 공식 제작사·방송사·관광기관 자료가 정확한 장소와 작품을 명시 | `촬영 확인` 및 원문 링크 | 장소명·주소·장면 맥락이 일치해야 한다. |
| 신뢰할 만한 기사·기관 자료가 장소를 연결하지만 장면은 불명확 | `작품 관련 장소`로 범위를 좁혀 표시 | ‘그 장면을 여기서 찍었다’고 확장하면 허위 주장이다. |
| 한옥 분위기가 작품과 유사하거나 팬 게시물에만 등장 | 촬영지로 게시하지 않음 | 취향 라벨과 사실 관계를 분리해야 한다. |

**권장 데이터 파이프라인:** TourAPI `contentId`+정규화 주소·좌표로 고유 장소를 식별 → 한옥 관련성·관람 가능성을 분류 → 작품 후보를 검색 → 원문이 **해당 장소와 작품 관계를 실제 지지하는지** 추출 → LLM은 근거 기반 구조화·요약에만 사용 → 중복·동명이소·모순 탐지 → 게시 전 표본 감사 → 게시·정정·재검증 이력 저장. `출처 URL 존재`만 확인하는 현재 ADR의 자동 게시 조건은 오매칭을 막기에 부족하다. 사람 검수를 전량 붙이기 어렵다면 상위 노출·낮은 확신·동명이소 주장에 우선 적용하고, 나머지는 별도 독립 표본 감사를 한다. [개선 Issue #603](https://github.com/YRootLab/OnMaru-backend/issues/603)와 설계를 맞출 수 있다.

**K-pop은 후순위로 검증한다.** 먼저 K-드라마의 실제 한옥 촬영 장소가 얼마나 있는지 분모를 확보한다. K-pop까지 동시에 확장하면 작품·무대·뮤직비디오·콘셉트 사진·영감 장소가 섞일 위험이 있다. 매체별로 `검증 가능한 고유 장소 수 / 조사 후보 수`와 지역·장소 유형의 다양성을 공개한 뒤 화면 섹션 수를 결정한다. 이는 `[INFERENCE]`이며 현재 K-pop 관련 장소가 적다고 단정한 수치는 아니다.

## 네 평가자의 독립 판단

- **관광·정책:** 한옥과 지역 방문의 연결은 긍정적. 다만 실제로 어느 지역의 방문·체류를 늘렸는지, 주민 생활권을 어떻게 배려하는지 증거가 필요하다.
- **제품·사업:** 관광 수요를 서비스 사용·재방문·지역 사업자 전환까지 이어주는 경로가 불명확하다.
- **데이터·기술:** TourAPI·Odii 결합은 적합하다. 후보 선별 실패와 ‘인기’ 표현의 근거 부족이 데이터 신뢰를 훼손한다. RAG 주장은 인용 정확도·답변 불가 처리의 공개 시연으로 입증해야 한다.
- **UX·시연:** 한옥마루의 깊이는 좋다. 그러나 홈에서 입력 후 가치가 나오기까지 시간이 길고, 한옥 해설·질문 기능보다 코스 카드가 먼저 강조된다.

**합의:** 한옥 테마를 버릴 이유는 없다. 먼저 데이터 품질과 **한 장소의 질문→이해→감상 흐름**을 바로잡아야 한다. **이견:** 관광 평가는 현장 이용·지역 효과를 더 중시하고 UX 평가는 첫 30초의 답변 명료성을 더 중시한다.

## One Big Bet

**추천: ‘작품 속 한옥을 찾아, 현장에서 읽는다’는 하나의 여정.** 작품 카드에서 **검증된 실제 한옥**과 원문 근거·현재 관람 정보를 확인한 방문자가 현장에서 처마·마루·생활 이야기를 질문하면, 온마루가 **장소 확인 → 출처가 있는 짧은 설명 → 해당 부분의 3D 시각화·관련 Odii 음성 → 더 볼 지점**을 한 화면에 보여준다. RAG는 검수된 장소별 근거에 대한 질문을 돕고, TourAPI·Odii는 대상 장소·소리·기본 맥락을 연결한다. 답할 근거가 없으면 모른다고 말한다. 우선 작품 연결이 검증된 5~10곳으로 시연하고 넓힌다. `[INFERENCE]`

이것이 킥인 이유는 K-콘텐츠의 팬 관심을 **검증된 한옥 방문과 현장 이해**로 바꾸기 때문이다. 발표 데모는 `작품 선택 → 촬영 근거와 장소 확인 → 한옥 앞 QR → “왜 이 처마가 길어요?” → 근거가 붙은 30초 답변 → 3D·해설 재생`으로 만든다. 성공 지표는 페이지뷰가 아니라 **작품 카드에서 장소 확인, 현장 진입 대비 질문 시작, 근거 확인, 해설 완료, 체험 문의**다. 방문 확인은 QR·운영자 확인 등 덜 민감한 방식부터 시험한다.

### 자연어·RAG와 UI가 만나는 구체적인 화면

| 사용자 발화 | 화면에 즉시 보여줄 것 | 답변·행동 | 안전한 실패 방식 |
|---|---|---|---|
| “지금 보는 이 집은 어떤 곳이에요?” | 현재 장소명·사진·TourAPI 원본 식별자와 마지막 검수일 | 확인된 핵심 이야기와 관련 Odii 음성·3D 위치를 연결 | 현장 장소가 불명확하면 선택을 요청하고 비슷한 이름의 한옥을 추측하지 않음 |
| “이 집 처마가 왜 길어요?” | 현재 장소명과 근거 문단, 답변이 적용되는 범위 | 2~3문장 설명 뒤 3D 처마 시뮬레이션과 관련 음성으로 연결 | 해당 건물의 개별 사실 근거가 없으면 일반 한옥 원리로 범위를 좁혀 명시 |
| “지금 들어갈 수 있나요?” | 운영 정보의 출처·최종 확인 시각 | 공식 운영처 확인/전화 또는 예약 링크 | 실시간 운영 상태를 모르면 `확인 필요`로 표시; AI가 개방을 보증하지 않음 |

이 UI는 RAG를 대화창 하나로 숨기지 않고 **근거 카드·공간 조작·음성 감상**으로 풀어낸다. 위 사례는 제품 제안이며 현재 공개 사이트에 이미 구현됐다고 주장하지 않는다. 우선 20개 대표 질문에 대해 `장소 일치`, `근거 지지`, `답변 불가`, `3D/음성 선택`을 평가하면 RAG가 실제로 가치를 더하는지도 분리해 볼 수 있다.

## 최종 심사 코멘트

온마루는 한옥을 고른 이유가 화면과 콘텐츠에서 잘 드러납니다. 3D 구조, 관광 장소, 오디오를 하나로 잇는 재료도 충분합니다. 그러나 공개 카탈로그의 비관련 장소와 비어 있는 K-콘텐츠 API는 핵심 데이터의 신뢰를 깎습니다. 원천 약 1만 건보다 중요한 것은 **검수된 고유 한옥과 사실로 확인된 작품 관계**입니다. 전국 일정을 완성하려고 범위를 넓히기보다 한 작품에서 실제 한옥을 확인하고 현장에서 한 가지를 이해하는 흐름을 시연하세요. 실제 현장 이용·해설 완료·체험 연결을 보여줄 수 있을 때 상위권 논리를 다시 평가하겠습니다.
