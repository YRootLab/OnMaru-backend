1. 문제 정의 및 PRD (Product Requirements Document)

외부 SaaS 종속 문제 해결, 비용 절감, 데이터 무결성 보장을 위한 공동 편집 기능의 제품 요구 정의

1.1 배경 및 문제 정의 (Problem Statement)

기존 OnMaru 웹 클라이언트는 지도 공동 편집 기능 구현을 위해 서드파티 실시간 협업 SaaS인 Liveblocks를 사용하고 있었습니다. 하지만 서비스 규모가 확장됨에 따라 다음과 같은 핵심 엔지니어링 문제들이 발생했습니다:

1. 데이터 소유권 및 정합성 결여

Liveblocks 룸 내 상태(핀, 좌표, 순서)는 OnMaru 자체 RDBMS(PostgreSQL)에 즉시 저장되지 않아, 세션 종료 시 영속성 보장이 불안정하며 투어 카탈로그 검증 없이 클라이언트 입력 좌표가 그대로 반영되는 취약점이 존재했습니다.

2. 외부 종속 비용 급증

MAU 및 동시 접속 룸 증가에 따라 Liveblocks 월간 구독료가 지수적으로 증가했으며, OnMaru의 독자적인 회원 권한(호스트/에디터/뷰어) 및 방 수명(72시간) 정책과의 결합도가 떨어졌습니다.

3. 프론트-백엔드 간 계약 분리

실시간 상태 변경 이벤트와 기존 OnMaru 여행/코스 도메인 간의 이벤트 통합이 불가능하여, 공동 편집 결과를 여정(Journey)으로 변환하는 기능 개발이 차단되었습니다.

1.2 제품 목표 (Goals & Non-Goals)

구분항목상세 내용
Goals 자체 백엔드 기반 전환 Liveblocks를 완전 제거하고, Spring Boot 3.4 WebSocket + 모듈러 모놀리스 기반으로 실시간 공동 편집을 내재화
Goals 엄격한 데이터 무결성 핀 변경은 DB 트랜잭션(map_room_pins, map_room_events, last_event_seq) 선행 커밋 후 메모리 반영 및 브로드캐스트
Goals 신뢰할 수 있는 장소 정보 (D9) 클라이언트의 좌표/이름 조작을 차단하고, 서버 카탈로그(PlaceCatalogPort) 조회 데이터만 강제 사용
Goals 초대 보안 거버넌스 (D7) 256비트 난수 base64url 초대 토큰 발급, SHA-256 해시 저장 및 만료일자(72시간) 엄격 제어
Non-Goals 다중 노드 분산 클러스터링 이번 Phase 1~3에서는 단일 인스턴스 인메모리 Actor 큐로 처리 (Redis Pub/Sub은 Phase 4로 분리)
Non-Goals 코스 변환 저장 지도 편집 완료 후 여정으로 변환하는 작업은 후속 이슈로 분리

2. 사용자 스토리 및 인수 조건 (User Stories & AC)

호스트, 참여자, 시스템 관점에서의 상세 행동 정의 및 검증 가능한 인수 기준

2.1 사용자 스토리 (User Stories)

  • US-1 (방 생성 및 호스트 권한): 여행 플래너인 회원은 지도를 열고 새로운 공동 편집 방을 생성하여 방장(OWNER) 권한을 획득하고, 만료 시간(72시간)이 설정된 작업 공간을 확보할 수 있다.
  • US-2 (초대 링크 발급 및 입장): 방장은 친구들을 초대하기 위해 유효기간이 있는 초대 링크를 발급할 수 있으며, 초대 링크를 전달받은 회원은 간편하게 방 멤버(MEMBER)로 참여할 수 있다.
  • US-3 (실시간 핀 동기화): 방에 접속한 참여자들은 원하는 관광지를 검색하여 핀으로 추가할 수 있으며, 핀이 추가되거나 삭제되는 순간 방에 있는 모든 참가자의 화면에 100ms 이내에 실시간으로 반영된다.
  • US-4 (실시간 커서 공유): 참여자가 지도 위에서 마우스를 움직이면, 다른 참여자들에게 해당 사용자의 닉네임과 함께 부드럽게 마우스 커서 위치가 공유된다.
  • US-5 (네트워크 단절 및 재연결): 모바일 환경에서 일시적으로 네트워크가 끊겼다가 재접속하더라도, 마지막 수신 seq 이후의 누락된 이벤트를 자동으로 재수신(Replay)하여 상태를 동기화한다.

2.2 인수 기준 (Acceptance Criteria: AC-1 ~ AC-8)

ID검증 항목인수 조건 (Acceptance Criteria)테스트 결과
AC-1 상한 제약 (Capacity Limits) 방당 최대 20명, 활성 핀 최대 100개, 활성 초대 토큰 최대 5개, 회원당 동시 WebSocket 세션 최대 3개를 엄격히 강제하고 초과 시 409 또는 SUPERSEDED 종료를 수행해야 한다. Pass (단위 & V058 제약)
AC-2 동일 장소 중복 핀 방지 (D1) 동일 방 내에 이미 활성화된 placeId를 가진 핀이 존재할 경우, 신규 추가를 거절하고 PIN_ALREADY_EXISTS (409)와 함께 기존 핀 정보를 반환해야 한다. Pass (REST & WS 검증)
AC-3 서버 카탈로그 검증 (D9) 클라이언트가 보낸 name, lat, lng는 무시하고, 반드시 백엔드 PlaceCatalogPort에서 조회한 공인 좌표와 명칭만 저장해야 한다. Pass (RoomActor 단위테스트)
AC-4 트랜잭션 선행 기록 이벤트 행(map_room_events), 핀 행(map_room_pins), map_rooms.last_event_seq 갱신이 단일 트랜잭션으로 성공한 경우에만 메모리 반영 및 브로드캐스트해야 한다. 실패 시 메모리는 불변이어야 한다. Pass (Rollback 보장)
AC-5 opId 기반 멱등성 동일한 opId로 요청이 재전송될 경우, 중복 실행하지 않고 직전 성공 결과(동일 seq)를 반환해야 한다. Pass (RoomActor 멱등성)
AC-6 다자간 동시 동기화 3명 이상의 클라이언트가 동시에 핀을 추가 및 삭제할 때, 모든 클라이언트는 동일한 seq 순서로 실시간 EVENT를 수신해야 한다. Pass (3-Client E2E 검증)
AC-7 커서 쓰로틀링 (T9) 초당 20Hz 이하로 들어오는 커서 입력을 50~100ms 단위로 버퍼링하여 CURSORS 배열로 병합 브로드캐스트해야 한다. Pass (80ms 버퍼링)
AC-8 수명 만료 스위퍼 (T11) 방 생성 후 72시간이 경과하면 스위퍼가 방을 CLOSED 상태로 전환하고, ROOM_CLOSED 이벤트를 기록한 뒤 연결된 모든 웹소켓에 4010 종료 코드를 전송해야 한다. Pass (Sweeper 테스트)

3.2 방별 Actor 동시성 모델 (ADR-0020 핵심 런타임)

각 방(Room)은 동시 다발적인 핀 추가/제거 명령을 처리하기 위해 단일 처리 큐(Single-Threaded Execution Queue)를 가진 RoomActor 인스턴스를 메모리에 유지합니다. 이를 통해 방 내부의 동시성 락 경합(Pessimistic Lock / Deadlock)을 원천 방지하고, seq의 단조 증가성을 100% 보장합니다.

Transactional Write-Through 원칙 RoomActor는 메모리에서 먼저 상태를 바꾸지 않습니다. 반드시 roomRepository.addPin(...)을 통해 DB 트랜잭션 커밋이 완료된 것을 확인한 직후에만 메모리 활성 핀 맵(activePinsById)을 업데이트하고 참여자들에게 EVENT를 브로드캐스트합니다. DB 쿼리가 실패하거나 제약 위반이 발생하면 메모리 상태는 완전히 불변으로 유지됩니다.

4.2 핵심 데이터베이스 제약 조건 (V058 Constraints)

  • 활성 핀 중복 유니크 인덱스 (D1): CREATE UNIQUE INDEX uq_map_room_pins_active_place ON map_room_pins (room_id, place_id) WHERE removed_at IS NULL;
    동일한 방에서 이미 활성화된 장소에 중복 핀이 생성되는 것을 DB 레벨에서 물리적으로 차단합니다.
  • 좌표 유효성 체크 제약: 대한민국 영역(위도 33.0~43.0, 경도 124.0~132.0) 범위를 벗어난 이상 좌표 삽입을 차단합니다.
  • 멱등성 유니크 제약: CREATE UNIQUE INDEX uq_map_room_events_op_id ON map_room_events (room_id, client_opId) WHERE client_opId IS NOT NULL;
    네트워크 재전송으로 인한 동일 opId의 중복 이벤트 생성을 DB에서 차단합니다.

6. 아키텍처 결정 기록 (ADR & Decisions D1~D10)

ADR-0020 및 실시간 지도 협업 핵심 도메인 결정 사항 매트릭스

6.1 ADR-0020: 인메모리 룸 상태와 DB 트랜잭션 동기화 (요약)

  • 결정(Decision): 방 상태 관리는 복잡한 CRDT 대신 LWW(Last-Write-Wins) 단일 시퀀스(Sequence Log) 방식을 채택하고, 각 방의 런타임 큐는 RoomActor 인스턴스로 메모리에서 유지한다.
  • 이유(Rationale): 지도의 핀 추가/제거는 텍스트 문서처럼 글자 단위 충돌이 일어나지 않으며, "어떤 핀이 추가되었는가"의 순서 정합성만 지켜지면 충분합니다. 단일 Actor 큐를 통해 데이터베이스 Lock 경합을 없애고 초당 수백 건의 커맨드를 지연 없이 처리할 수 있습니다.
  • 트레이드오프: 서버 재시작 시 활성 핀과 seq를 DB에서 복구하는 초기 비용이 발생하며, 다중 인스턴스 확장을 위해서는 향후 룸 세션 라우팅(Sticky Session / Redis)이 필요합니다.

8.3 장애 대응 런북 (Operations Runbook)

  • Alert 1: map_collab_ws_closed_total{close_code="4029"} 급증
    • 원인: 모바일 클라이언트의 백그라운드 전환 또는 네트워크 지연으로 인해 256개 발신 버퍼가 가득 참.
    • 조치: 클라이언트 프론트엔드의 재연결( 지수 백오프 + lastSeq RESUME) 동작 여부 확인. 필요 시 커서 브로드캐스트 주기(80ms $\rightarrow$ 120ms) 상향 조정.
  • Alert 2: 서버 재배포 시 세션 종료 (4030)
    • 동작: Spring Boot Graceful Shutdown 시 모든 연결에 4030을 보내고 정상 종료.
    • 복구: 클라이언트는 4030 수신 시 스냅샷 또는 RESUME 쿼리를 통해 재접속하여 1초 이내에 상태를 무중단 복구함.
