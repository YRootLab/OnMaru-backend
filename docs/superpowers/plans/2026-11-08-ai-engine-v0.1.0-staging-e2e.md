# AI Engine v0.1.0 Staging E2E Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** AI Engine v0.1.0을 운영과 격리된 Lightsail staging Compose에 배포하고 Spring↔AI private 통신과 실제 Journey SSE/Snapshot 경로를 검증한다.

**Architecture:** `infra/lightsail/staging/compose.yaml`에 `staging-ai-engine`을 추가하고 staging Spring만 해당 service name을 사용한다. GitHub Actions는 검증된 `develop` commit과 사용자가 제공한 immutable AI digest를 제한 SSH deployer로 준비하며, operator start/stop은 Spring·AI·staging DB를 하나의 수명주기로 관리한다. 기존 정적 Journey gate는 유지하고 별도 Python live runner가 staging 공개 API의 CSRF/cookie 인증, SSE, terminal snapshot 및 저장 결과를 검증한다.

**Tech Stack:** Docker Compose, POSIX shell, GitHub Actions, Python 3.12 standard library, Node.js test runner, Spring Boot 3.x, FastAPI

## Global Constraints

- AI image는 `ghcr.io/yrootlab/onmaru-ai-engine/ai-engine@sha256:dfbda74a3e9f8bd1a86a81797f0c569aa3f537987f778d551fc62bcf1355a33d`를 사용한다.
- AI memory limit은 `512m`이며 healthcheck는 `http://127.0.0.1:8000/ready`의 HTTP 200을 요구한다.
- AI port 8000은 host에 publish하지 않는다.
- staging Spring은 `http://staging-ai-engine:8000`을 사용하고 AI callback/MCP는 `http://staging-api:8080`을 사용한다.
- staging 전용 내부 AI secret만 공유하며 production secret을 재사용하거나 로그에 출력하지 않는다.
- production AI가 실행 중이면 staging start는 fail-closed한다.
- 이번 계획은 production AI workflow를 dispatch하지 않는다.
