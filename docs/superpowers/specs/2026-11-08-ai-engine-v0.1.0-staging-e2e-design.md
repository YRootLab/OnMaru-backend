# AI Engine v0.1.0 Staging 격리 배포 및 E2E 설계

## 목적

`onmaru-ai-engine` v0.1.0 이미지
`ghcr.io/yrootlab/onmaru-ai-engine/ai-engine@sha256:dfbda74a3e9f8bd1a86a81797f0c569aa3f537987f778d551fc62bcf1355a33d`
를 운영 Spring과 분리된 staging 경로에서 검증한다. 대화 생성부터 AI 추론, progress callback과 SSE, 승인된 장소 조회, Snapshot 저장까지 실제 Lightsail 네트워크에서 확인한 뒤에만 같은 digest의 운영 승격을 별도 결정한다.

관련 작업은 GitHub Issue #807에서 추적한다.

## 관찰된 현재 상태

- root Compose의 `ai-engine`은 운영 Spring과 `app` network를 공유한다. 이를 바로 교체하면 staging 검증 범위를 넘어 운영 경로가 변경된다.
- staging Compose는 root Compose가 만든 외부 network `onmaru-lightsail_app`에 연결되며 Spring alias는 `staging-api`다.
- staging Compose에는 아직 AI service와 `ONMARU_AI_BASE_URL` 및 내부 AI 인증 secret 주입이 없다.
- `scripts/test/validate-journey-e2e-gate.py`는 원격 서버를 호출하지 않는다. manifest, fixture, runtime suite 및 evidence의 정합성만 검사한다.
- Spring progress callback의 구현 경로는 `/internal/v1/ai/runs/{runId}/progress`다. 요청서의 `/internal/ai/runs/{runId}/progress`와 다르므로 v0.1.0 이미지가 구현 계약 경로를 사용하는지 live gate에서 확인한다.
- 승인된 장소 조회 구현 경로는 `/internal/mcp/journey/tools/journey_execute_approved_lookup`이다.

## 선택한 구조

staging Compose에 `staging-ai-engine`을 추가한다. 이 service는 지정한 immutable digest를 사용하고 `512m` 메모리 제한, `/ready` healthcheck, host port 비공개를 강제한다. staging Spring은 `http://staging-ai-engine:8000`을 AI base URL로 사용한다. AI는 공용 private `app` network에서 `http://staging-api:8080`으로 callback과 MCP 요청을 보낸다.

운영 root Compose의 `ai-engine`과 production AI deploy workflow는 이번 단계에서 변경하거나 실행하지 않는다. 2GB host의 메모리 예산을 보호하기 위해 staging 시작 전 production AI가 실행 중이면 fail-closed하고, staging 중에는 production AI와 staging AI를 동시에 실행하지 않는다.

## 구성 및 secret 경계

- `ONMARU_AI_IMAGE`는 v0.1.0 digest 전체 문자열을 staging `.env` 계약에 기록한다.
- `ONMARU_AI_MEMORY_LIMIT=512m`을 명시하고 Compose 기본값도 `512m`으로 둔다.
- Spring과 AI에는 staging 전용 `ONMARU_SECRET_INTERNAL_AI_SERVICE_TOKEN_CURRENT`를 동일하게 주입한다. production secret을 복사하지 않는다.
- AI callback 및 MCP base URL에 `http://staging-api:8080`을 사용한다. 실제 AI 이미지가 요구하는 환경변수 이름은 이미지 문서와 config validation 결과로 확정한다.
- AI 이미지 pull에 필요한 GHCR credential은 제한된 staging deploy 경로에서만 전달하며 로그에 출력하지 않는다.

## 기동, 실패 및 정리

staging start는 production PostgreSQL health와 production AI 비실행을 먼저 확인한다. staging PostgreSQL과 migration 이후 `staging-ai-engine`을 기동하고 `/ready`가 healthy가 된 뒤 Spring을 기동한다. Spring health 실패 또는 AI health 실패 시 staging Spring, staging AI, staging PostgreSQL만 중지한다. 자동 종료 timer와 수동 stop도 세 service를 함께 중지한다.

이미 기동된 staging의 timer를 갱신할 때도 Spring과 AI가 모두 healthy한 경우에만 ready로 판단한다. status는 AI 상태도 함께 출력한다.

## Live E2E gate

기존 `validate-journey-e2e-gate.py`는 CI 정적 계약 gate로 유지한다. 별도 live runner는 `https://staging-api.onmaru.site`를 대상으로 다음을 순차 검증한다.

1. staging readiness와 필요한 인증/CSRF 준비
2. 대화 및 run 생성
3. run SSE 연결과 event sequence 수집
4. AI proposal 실행 완료 및 progress stage 관찰
5. 정형 장소 lookup 결과가 포함된 최종 Snapshot 조회
6. 저장된 Journey Snapshot의 식별자와 장소 참조 검증

runner는 base URL, credential 및 timeout을 명시적 환경변수로 받으며 secret이나 원문 token을 출력하지 않는다. 각 단계의 HTTP status, run ID, SSE stage, 최종 Snapshot 식별자만 release evidence에 남긴다. 실패 시 비영(0이 아닌) 종료 코드와 실패 단계를 반환한다.

## 검증 기준

- Compose 정적 검증과 배포 pipeline 테스트가 staging AI service, digest, memory, healthcheck, port 비공개 및 stop/cleanup 동작을 확인한다.
- Spring callback unit/integration test와 MCP controller test가 HMAC 거부/허용 및 approved lookup을 확인한다.
- 정적 Journey gate가 기존과 동일하게 통과한다.
- Lightsail에서 AI `/ready` 200, Spring→AI proposal, AI→Spring callback/MCP, SSE stage, Snapshot 저장의 live evidence가 모두 있어야 staging E2E를 PASS로 판정한다.
- 하나라도 실패하면 운영 AI 승격을 수행하지 않는다.

## 범위 밖

- 운영 root `ai-engine` 교체 또는 production workflow dispatch
- v0.1.0 이후 AI 애플리케이션 코드 수정
- 운영 secret 재사용
- callback URL의 호환 alias 추가. live 검증에서 경로 불일치가 확인되면 AI Engine 또는 Spring 계약 수정 Issue로 분리한다.
