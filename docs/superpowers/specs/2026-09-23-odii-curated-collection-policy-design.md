# Odii 전통문화 큐레이션 수집 정책 설계

- 작성일: 2026-09-23
- 관련 이슈: #355
- 상태: 설계 승인

## 목적

현재 Odii 동기화는 `한옥` 단일 검색어에 의존해 공개 가능한 story 수가 부족하다. 수집 범위를 전통문화·역사·지역해설로 확장하되, 레저·스포츠 중심 콘텐츠가 OnMaru의 핵심 경험을 흐리지 않도록 큐레이션 dataset에서 제외한다.

이번 작업은 공공데이터 원천을 삭제하거나 전체 관광 데이터의 카테고리를 제한하는 작업이 아니다. 원천 관측 결과와 OnMaru 공개용 큐레이션 결과를 분리한다.

## 현재 구조와 문제

`공공데이터 Odii API → page source → mapping → PostgreSQL staging → revision publish → 공개 API` 흐름을 유지한다. 공개 API 요청 시 원천 API를 직접 호출하지 않는다.

#307에서는 운영 PostgreSQL의 `audio_revision_stages`, `audio_story_versions`, `catalog_active_datasets`가 비어 있어 503이 발생했다. 따라서 정책 변경 전제조건은 먼저 정상적인 source fetch와 PostgreSQL revision publish를 복구하고, 이후 필터 정책을 적용하는 것이다.

## 추천 접근

`storyBasedSyncList` 기반의 전체 수집 source를 운영 기본값으로 사용한다. 언어별로 모든 페이지를 한 번씩 조회하고, Odii 고유 story ID로 중복 제거한 뒤 제외 정책과 품질 정책을 적용한다. 통과한 결과만 동일한 dataset revision으로 staging하고 원자적으로 publish한다. 기존 `storySearchList`와 키워드 설정은 테스트·점진적 롤백을 위한 호환 경로로 남긴다.

대안인 키워드별 별도 job은 관측성은 좋지만 lease·revision·실패 복구 단위가 복잡해진다. DB 공개 조회 시점에만 필터링하는 방식은 공개 경로에 부적합한 원천 결과가 섞일 수 있어 채택하지 않는다.

## 수집 정책

### 기본 수집 범위

전체 story를 수집한 뒤 제외 규칙만 적용한다. 따라서 한옥·고택뿐 아니라 지역 역사, 문화유산, 전통마을, 궁궐, 성곽, 전통시장 등 원천 데이터에 존재하는 콘텐츠를 함께 활용할 수 있다. 지역명을 무차별적으로 검색어로 조합하지 않아 호출량과 중복을 키우지 않는다.

### 제외 정책

다음 표현 또는 분류는 공개 큐레이션에서 제외한다.

- 레저
- 스포츠
- 골프
- 수상레저
- 액티비티
- 쇼핑 중심
- 일반 숙박·호텔·리조트 단독 콘텐츠 (한옥·전통문화 체험과 결합된 숙박은 허용)
- 음식점 단독 콘텐츠

축제·자연관광처럼 경계가 있는 콘텐츠는 제목·설명에 역사·문화·지역 해설성이 있으면 허용한다. 단순 카테고리 하나만으로 모든 결과를 제거하지 않고, 원천 분류와 텍스트 신호를 함께 사용한다.

## 데이터 흐름과 상태

1. 언어별 전체 페이지를 조회한다.
2. 응답 schema, page number, provider 오류를 검증한다.
3. story ID 기준으로 중복 제거한다.
4. 제외 분류·제외 키워드·품질 기준으로 판정한다.
5. 원천 관측과 판정 사유를 sync summary/quarantine에 남긴다.
6. 허용 결과만 `audio_revision_stages`에 staging한다.
7. 정상적으로 충분한 결과가 확인될 때 active revision을 교체한다.

원천 결과는 향후 일반 관광 기능을 위해 보존할 수 있어야 한다. 공개 dataset에서 제외된 결과를 곧바로 삭제하지 않고, 최소한 외부 ID와 제외 사유를 관측 데이터로 남긴다.

## 안전장치

- 전체 결과가 0건이면 기존 active revision을 유지한다.
- 기존 대비 결과가 급감하면 경고를 남기고 자동 publish를 보류한다.
- source fetch 실패, mapping 실패, 필터 결과 0건을 서로 다른 상태로 기록한다.
- 중복 제거 전·후 수, 제외 수, 최종 publish 수를 sync summary로 남긴다.
- #307의 API key/운영 환경 문제 복구와 정책 변경은 별도 검증 단계로 운영한다.

## Acceptance Criteria

- `storyBasedSyncList`로 단일 키워드에 종속되지 않고 전체 story를 동기화한다.
- 전체 수집 응답에서 발견된 동일 story가 한 번만 staging된다.
- 레저·스포츠 등 제외 대상이 공개 active revision에 포함되지 않는다.
- 축제·자연관광의 조건부 허용 규칙이 테스트로 고정된다.
- 결과 수와 제외 사유를 확인할 수 있다.
- source 실패나 비정상적인 결과 급감 시 기존 active revision이 보존된다.
- 실제 PostgreSQL에서 staging과 publish 결과를 검증한다.
- 복구 후 `trending-sounds`와 `odii/stories`가 정상 응답한다.

## 구현 범위 밖

- 일반 관광 장소 전체의 카테고리 정책 변경
- AI 기반 의미 분류 모델 도입
- 별도 검색엔진·데이터 웨어하우스 도입
- 레저·스포츠 콘텐츠의 영구 삭제
